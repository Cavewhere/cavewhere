Sync job progress — duplicate jobs & flat progress bar

CaveWhere · cwProject / cwSaveLoad sync orchestration · asyncfuture Restarter · operation queue
Status: root cause confirmed · verifying test written (failing by design) · design chosen
Scope: cavewhere (cwProject, cwSaveLoad) + asyncfuture (submodule, own fork)

1. Goal

Clicking Sync misbehaves in two ways, both surfaced while manually testing the #545 LFS-pull-progress fix:

  • Bug 1  Duplicate jobs. One Sync click shows three identical "Syncing" rows in the future-manager UI on a real GitHub (https) remote — two on a file:// remote.
  • Bug 2  Flat progress. The "Syncing" row's progress bar never moves, even though the underlying pullRebaseOrMerge() / push() (and the restored #545 LFS hydration) report byte progress.

Both trace to a single structural fact: the future registered as the "Syncing" job is the wrong future — it is re-created at every async gate, and every producer along the path completes with a value, which severs progress.

2. Root cause (confirmed by trace)

2a. Bug 1 — one addJob per async gate

cwProject::sync() runs through up to three async gates, and each reassigns the SyncFuture member and calls FutureToken.addJob(SyncFuture, "Syncing") with a fresh future. cwFutureManagerModel::addJob appends one row per call (cwFutureManagerModel.cpp:65-68), and the earlier deferreds stay alive until the next stage completes — so the rows coexist.

2b. Bug 2 — progress is severed at the operation queue (the first boundary)

Chain of custody, pull → job. Progress survives steps 1–2, then dies at the very first queue hop:

StageProgress?Why
1. repo->pullRebaseOrMerge() future cwSaveLoad.cpp:4925 ✓ has itthe setProgress / QFutureInterface path from #545

4. syncDeferred->complete(attemptResult) cwSaveLoad.cpp:5013 ✗ SEVER #2value completion again (already dead by here)
5. beginSyncOperation: observe(operationFuture).context(...) ✗ mootmirrors a source that now has no progress
Key mechanic: AsyncFuture::Deferred::complete(QFuture<T>) ends in track(future) (asyncfuture.h:598) — completing a deferred with a future forwards progress; completing it with a value does not. The three sever points are all complete(<value>) calls.

2c. Two things the trace ruled out

  • The Deferred<void> gap is not on this path. Every manual deferred that severs here is a Deferred<Monad::ResultBase> — the generic template, which already has setProgressValue/setProgressRange/track (asyncfuture.h:1556-1567). The void SyncFuture is an observe().context() chain that auto-mirrors, so its void-ness is fine. Adding progress to the Deferred<void> specialization (asyncfuture.h:1578-1621) is a legitimate symmetry fix but is not required for this bug — left as an optional follow-up.
  • QQuickGit's QFutureInterface progress is fine and stays. The pull/push futures already carry progress; we do not rewrite that plumbing.

3. Design decisions

Chosen

  • Single job (Bug 1): register exactly one "Syncing" job for the whole gated sync in cwProject; remove the per-gate addJob calls.
  • Queue-wide progress forwarding (Bug 2, linchpin): in runNextOperation, op->deferred.track(opFuture) forwards the active op's live progress into its deferred without completing — the existing observe().context() callback still value-completes with the (cancellation-rewritten) result. Lights up progress for all operations (SaveFlush / Bundle / Import too), not just sync.
  • Restarter for the attempt (aggregation): drive the sync attempt/retry loop through AsyncFuture::Restarter<ResultBase>. Its future() track()s whichever inner attempt is in-flight (asyncfuture.h:2006), so one progress bar follows the live phase and re-points cleanly across retries.

Confirmed mechanics

  • Deferred<ResultBase>::track() exists & forwards progress only (asyncfuture.h:470).
  • Restarter(context) · restart(fn) · future() · onFutureChanged(cb) · onResult(ctx, cb) (asyncfuture.h:1819-2075).
  • Each restart burst installs a fresh outerDeferred and fires onFutureChanged — the intended re-registration hook.
  • Cancel flows outer→inner (asyncfuture.h:2026-2032): a cancelled job stops the worker via QPromise::isCanceled().
Open design question — retry re-registration. Sync retries are triggered by an attempt finishing with a retryable error (push-rejected / epoch-changed), not by cancellation. With Restarter, each retry is a fresh restart() burst → new outerDeferred → onFutureChanged. If we re-register on every onFutureChanged we get one row per attempt (sequential, not simultaneous — still a strict win over today's 3 concurrent rows, and only on the uncommon retry path). If we register once and never re-register, the row vanishes when an attempt completes mid-retry. Decision to lock in Phase 3: register once at click; on onFutureChanged re-point the single job's watched future rather than adding a new row (may need a small cwFutureManagerToken/model affordance to "replace the future of an existing job"). Revisit if that affordance is heavier than expected.

6. Risks

  • Blast radius of the queue change. enqueueOperation backs SaveFlush, LoadProject, BundlePackage, ImportFiles, SyncProject, ReconcileExternal, RepairSave. Adding track() is additive (progress only, no completion change), but every op type must be re-verified green.
  • Restarter semantics vs. finish-triggered retries. Restarter is built around cancel-and-restart; our retries are finish-and-restart. Confirm the burst path (activeInner not running → fresh outerDeferred) behaves correctly when the previous attempt finished with an error, and that stale-generation guards (deliver()) don't drop the real result.
  • Job re-point affordance. Keeping a single row while future() changes per burst may need a small addition to cwFutureManagerModel/cwFutureManagerToken. Gauge cost before committing to Phase 3's approach.
  • #545 still uncommitted. The pull-progress fix this work builds on is unpushed across the QQuickGit submodule; sequence the gitlink bumps deliberately.
