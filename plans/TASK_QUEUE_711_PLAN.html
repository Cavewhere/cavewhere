Task Queueing — Benchmark and Plan

Issue #711 “One task at a time” · branch dev_codex1 · 2026-10-21

Goal. Opening a big project, especially a fresh clone like the Marble range, starts work from many places at once. All of it lands on the same thread pool, so tasks thrash each other's caches, and on mobile the combined working sets go past the memory limit and the OS kills CaveWhere.

Order of work. Measure first. Phase 0 builds a task-utilization benchmark on Apple signposts and Instruments. Philip clears the cache and picks a set of common projects; Claude records them with xctrace, exports the data and writes the analysis. The fixes in Phase 1 come after that, in the order the numbers support, and each one is re-measured with the same benchmark.

cwJobSettings::setThreadCountPrivate sets the user's thread count on the first two pools, so up to twice as many threads as cores can be runnable at once. Three places call releaseThread() while they block or orchestrate (cwKtx2Codec.cpp:147, :172, cwPointOctreeBuilder.cpp:1399), which lets the pool start a worker past its maximum.

How work enters

  1. The coordinator orders pipelines and admits all of their work at once. cwRootData.cpp:212-214 registers the line plot, then scraps and LiDAR, both depending on the line plot. The cascade makes those two wait for the solve. Because scraps and LiDAR are siblings, both start in the same turn once it finishes.
  2. Each pipeline fans out every item immediately.
    • Scraps: cwTriangulateTask::triangulate() (cwTriangulateTask.cpp:70) starts one crop → mipmap/upload → triangulateGeometry chain per dirty scrap, and cwScrapManager.cpp:1269 combines all of them.
    • LiDAR: cwTriangulateLiDARTask.cpp:126 submits one cwConcurrent::run per note. Each run decodes a whole glTF, morphs its vertices and prepares textures. This is the largest per-task working set in the app.
    • LAZ octree builds, tile and texture streamers, KTX2 encodes, project load and git all submit on their own schedules to the same pool.
  3. A restart keeps the superseded run's work going. cwScrapManager.cpp:1250 and cwNoteLiDARManager.cpp:671: “A restart cancels the combine, leaving these futures running, so the generation check drops their results.” A re-dirty during load runs a second generation alongside the first, and the first generation's output is discarded.
  4. Queued closures hold memory too. Each one keeps its captured inputs (cwTriangulateInData, cwTriangulateLiDARInData) from the moment it's submitted.
Today: every producer submits its full batch to a shared pool on its own schedule. The pool caps running threads, and the queue behind it accepts everything.

2. What the benchmark must answer

Each fix in Phase 1 rests on one of these. The benchmark has to confirm or rule out each one, so the recordings and the analysis are designed around them.

3. Phase 0 — Benchmark

Design. CaveWhere marks its work with Apple signposts through MarkScope. Instruments records them alongside the CPU samples, thread states and allocations the OS already collects. A runner script records each project with xctrace, exports the tables to XML and writes the analysis. Philip clears the cache and picks the projects; Claude records, exports and analyzes. This covers the Mac and the iPhone. Windows and Android are out of scope for the benchmark.

What a test recording showed (2026-10-21)

A small test program (four threads, each with a signpost interval and a 50 MB allocation) was recorded and exported with xctrace 16.0 to see what can be read without opening the Instruments app.

Two requirements surfaced:

  • Instruments can only attach to a binary signed with com.apple.security.get-task-allow. Recording an unsigned binary fails with “Failed to attach to target process.” The Release CaveWhere.app in build/ is currently unsigned. entitlements.plist already grants the entitlement, so an ad-hoc codesign -f -s - --entitlements entitlements.plist is enough.
  • The first recording on a machine shows a Developer Tools permission prompt. Until it's approved, the launched process stays suspended and the recording hangs.

Because the allocation list only holds what is live at the end, the memory curve comes from CaveWhere's own sampler (B2), which writes the footprint as signpost events. One trick follows from the same fact: a memory recording stopped at the moment of the peak lists what is live at the peak, with responsible callers. That part is untested.

B1MarkScope fixes and a signed build edit

Per-interval ids. MarkScope::Profiler generates one os_signpost_id_t in its constructor and reuses it for every interval. Instruments pairs a begin with its end by id, so overlapping intervals from different pool threads on one Profiler get matched to the wrong partner. Change start() to generate an id and return it as a small token that stop() takes back. ScopedProfiler holds the token, so its callers stay the same. FrameProfiler runs one interval at a time on the render thread and is unaffected.

Public arguments. The current format "task: %s" risks showing the name as <private>. Use %{public}s, as the test recording did.

Fixed names, variable arguments. os_signpost requires the interval name to be a string literal. Use a small fixed set of names (task, batch) and pass everything variable as arguments (ctx=%{public}s name=%{public}s wait_us=%llu). That matters for the export: the analysis groups by name and parses the arguments.

Events. Add Profiler::event() over os_signpost_event_emit for the sampler's values and the dropped marks. It is unpaired, so it needs no id.

Signing. The runner script signs the bundle ad hoc with entitlements.plist before each recording. That keeps the profiling step out of CMake. Check that signing the outer bundle is enough while Qt's frameworks load from the Qt install through rpath; --deep is the fallback. iOS development builds from Xcode already carry the entitlement.

ITT backend. Add the same token API to the ITT path, using __itt_task_begin and __itt_task_end, so MarkScope's interface stays the same on both backends.

B2Task tags and the sampler new

New files: cwTaskTrace.h/.cpp in cavewherelib/src, built on MarkScope with subsystem com.cavewhere.tasks.

Context tags. Every task is attributed to a short context name: scraps, lidar, lineplot, octree, ktx2, tiles, textures, load, git, sketch. An RAII scope sets a thread-local current context on the submitting thread:

{
    cwTaskContextScope scope(QStringLiteral("lidar"));
    const auto futures = cwTriangulateLiDARTask::triangulate(inputs, progressRoot);
}

cwConcurrent::run captures the context and the submit time, then on the worker reinstalls the context and opens a task interval whose arguments carry the context and the queue wait. Work submitted from inside a task inherits the tag, so only the top-level entry points need a scope: the three pipeline doRun()s, the octree build, the streamers, project load and the git operations. Untagged work shows up as untagged, which also shows which entry points still need a scope.

SourceMarked as
cwConcurrent::runA task interval on the worker thread, with ctx and wait_us.
cwConcurrent::map/mappedA batch interval from submit until the future finishes, with the item count. Items aren't marked one by one: the octree maps produce hundreds of thousands.
cwTask::start()A task interval named by cwTask::name().
Direct pool->start() (ktx2 lane, octree columns)A task interval at each of the few call sites.
QQuickGit, plain QtConcurrent::runCovered by thread state and CPU samples, plus a coarse interval around each git operation in cwSaveLoad. The submodule stays untouched.
Generation-check drops in scraps and LiDARThe pipeline's task intervals carry gen=N, and the generation check emits a dropped event naming the same generation. The analysis sums the CPU time of the task intervals whose generation was dropped. The check runs on the main thread after the future settles, so it has no CPU time of its own to report; matching by generation keeps that out of the result types and adds no member data to the managers.

Sampler. A dedicated thread emits one event per kTaskTraceSampleIntervalMs (50 ms):

  • mem: physical footprint and resident size, from TASK_VM_INFO. Footprint is the number iOS kills apps on, and the same call works on macOS. On iOS it also carries os_proc_available_memory(), the budget left before the kill, so the report can state the margin instead of guessing the device limit. macOS has no limit, so Mac runs show the shape of the curve and the phone is the only place the crash itself reproduces.
  • queue: queued and running counts per context, kept by the wrapper as atomics. QThreadPool doesn't expose its queue length, so the wrapper is the only source.
  • pool: activeThreadCount() and maxThreadCount() for each pool.

The sampler runs only while a recording is on. It checks os_signpost_enabled() once a second when idle and switches to 50 ms sampling as soon as Instruments starts recording. That works the same on the iPhone, where there is no command line to turn it on.

Idle mark. For scripted runs, the app emits an idle event once all of these hold continuously for kTaskTraceQuietWindowMs (2 s):

  • the project has loaded;
  • cwUpdateCoordinator::running is false, and needsUpdate is false when automatic update is on;
  • cwFutureManagerModel::count is 0;
  • every pool reports zero active threads and every context reports zero queued.

With --profile-tasks-quit it then quits, which ends an xctrace --launch recording. The quiet window catches work that starts a turn after the previous job ends, such as scraps starting after the solve.

Off cost. When nothing is recording, a submission costs one thread-local read and one clock read, and os_signpost calls return early.

Tests ([cwTaskTrace]): the context carries across a nested cwConcurrent::run; queued and running counts are correct with a saturated pool (pool of 1, two tasks); an untagged submission reports untagged. The counters are the sampler's real input, so the tests read them through the same API.

Cold starts. --cold deletes the project's .cw_cache before each recording. It removes cache files only. Clearing it by hand gives the same cold start. On the iPhone there is no shell and the cache sits inside the project directory, so a cold run there means deleting the project from the Files app and copying it over again; the runner prints that step and waits. An in-app “clear cache” action would make this repeatable, and is a candidate for later.

Protocol. The same steps for every row in §4:

  1. Clone or copy the project first. The recording measures the open, and the clone is network time. If the clone itself is wanted, record it separately with git as the only context.
  2. Clear the cache (--cold) or leave it (warm).
  3. Launch with the project as the positional argument and --page set to the 3D view, so tile and texture streaming starts the same way in every run instead of depending on which page the app opened on. Also pass --profile-log, so the existing lcProfileLoad numbers land in the same output folder as a cross-check.
  4. Three runs per row. One multi-minute recording is a single sample; the report prints the median and the spread, and --compare reports a difference only when it clears the spread.
  5. Automatic update stays on and the thread count stays at the default. Both persist in QSettings, so a lowered thread count on one machine would silently change H4.

Analysis. The script exports the tables listed in the test above and joins them on thread and time: a CPU sample or thread-state row belongs to the context whose task interval covers it on that thread. It writes <out>/report.md:

--compare baseline after-F1 prints the differences between two output folders. Claude reads the reports, checks anything surprising against the raw tables, and writes the findings into §4.

Release builds only, with debug info. Address Sanitizer in Debug inflates memory and changes timing too much for the numbers to mean anything. A plain Release build leaves our frames as addresses in the CPU samples, so the profiling build is configured with CMAKE_CXX_FLAGS_RELEASE="-O3 -DNDEBUG -g": the same code, plus symbols.

What the smoke run taught the runner (2026-10-22). xctrace --launch resolves a CaveWhere.app path by name and refuses when another copy is installed, so on the Mac the runner starts the app itself, holds it in SIGSTOP, attaches by pid, waits for xctrace's tracing-started notification and resumes it; that also puts the app's stderr in the log. Only one recording may run at a time: a second one is starved of kernel samples. The footprint plateaus after the peak because malloc keeps freed large blocks dirty, so B′ stops at the first sample on the plateau, where the blocks were still live.

5. Phase 1 — Fixes (after the baseline)

Each fix is a separate commit. Each one is re-measured with profile_tasks.py --compare against the baseline, and the numbers go in the commit body. Each fix has a pass line below; a fix that misses its line is reworked before the next one starts. Across all four, time to idle on the Mac stays within 10% of the baseline, and time to first scrap delivered stays within 2 s of it.

F1Cancel superseded runs edit H2

When a restart bumps the generation in cwScrapManager and cwNoteLiDARManager, cancel each in-flight future as well as the combine. Have triangulateOne and triangulateGeometry check for cancellation between meshes and between stages, so a canceled task stops early instead of running to the end. The smallest and most contained change.

Pass: dropped CPU time under 1% of total CPU time on the Marble cold open.

F2Bounded fan-out inside a pipeline new H1 H5

Replace “submit all N, then combine” with a windowed launcher: start K items, then start the next as each finishes. Admit by an estimated byte budget, not just a count, so mobile can admit one or two meshes while desktop admits a core's worth. Queued inputs are only built when admitted, which also covers item 4 in §1.

The pattern. This is a bounded fan-out, a weighted semaphore in front of a launcher. Every ecosystem has the count form (errgroup.SetLimit, p-limit, buffer_unordered, Parallel.ForEachAsync); the weight form is rarer (Go's semaphore.Weighted) and is the one CaveWhere needs, since LiDAR meshes differ in size by 100×. Qt only offers the pool-wide thread count, which is why three producers wrote their own:

SiteShape today
cwPointOctreeBuilder::runPassB (cwPointOctreeBuilder.cpp:1373-1485) Weighted: maxRunning plus inFlightBytes, and a rule worth keeping: the first item of a window always runs, so an item larger than the whole budget still builds, alone. Runs on a worker thread with no event loop, so it polls isFinished() with msleep(kMapPollMs) and releaseThread()s its slot. awaitMapped (:544-566) does the same for pass A.
cwTileStreamer (cwTileStreamer.h:73,181-192) kMaxConcurrentLoads = 4 plus m_inFlightBytes, a pending queue and a QWaitCondition. A streaming cache with eviction and supersede; it keeps its own loop.
cwKtx2Codec (cwKtx2Codec.cpp:173-192)A set of in-flight paths. Dedupe, not a limiter.
LiDAR (cwTriangulateLiDARTask.cpp:126), scraps (cwTriangulateTask.cpp:70) None. Both consumers observe per-item futures (cwNoteLiDARManager.cpp:671 delivers each note as it lands), so the limiter has to hand out one future per input, before admission.

Where it lives: asyncfuture. The limiter decides when to call a launcher and never touches a pool; cwConcurrent stays about where work runs and carries the trace tags. The fork already grows this kind of primitive (Restarter, shield(), CancelPropagation, the FailFast combine mode, chained progress), each with its own tests, and a limiter composes with all of them: a Restarter cancel stops admission, FailFast gives the octree's one-failure-stops-the-rest, chained progress feeds the flyout. The building block exists too: each input gets a Deferred<T> up front, and admission calls Deferred::complete(QFuture<T>, CancelPropagation::Propagate).

namespace AsyncFuture {
struct Limit {
    int maxRunning = 1;
    qint64 budget = 0;          // 0 = count only
};

template <typename T>
struct Limited {
    QList<QFuture<T>> items;    // one per input, in input order, observable before admission
    QFuture<void> all;          // settles when every item settles; cancel() stops admission and cancels running items
};

template <typename T, typename Input, typename Launch, typename Weight>
Limited<T> limited(QObject* context, const QList<Input>& inputs,
                   Launch launch /* Input -> QFuture<T> */,
                   Weight weight /* Input -> qint64 */,
                   Limit limit);
}

Semantics to pin down, each borrowed from the octree loop or from §1:

  • FIFO admission. The first item of a window always runs, whatever its weight.
  • launch runs only on admission, so a queued input is the cheap Input value and the heavy cwTriangulateLiDARInData is built inside the launcher.
  • Canceling all cancels the running items and every unadmitted item's future. Canceling one item's future before admission skips it.
  • Main thread only, documented the way Restarter is.
  • The byte estimate stays in CaveWhere: glTF file size for LiDAR, crop pixels × 4 for scraps.

CaveWhere's side is then small. cwTriangulateLiDARTask::triangulate returns limited(...).items with a Limit chosen per platform; scraps follow. cwConcurrent gains no API, and F3's cwJobQueue sits outside this as the one-job-at-a-time gate. A cwConcurrent::runLimited would weld admission to the pool and the trace, and could only be tested through cavewhere-test.

The octree move, and what to measure first. The octree is the third site, and the only one where F2 changes the threading model: the orchestrator would move off its worker thread onto main-thread observe().context() callbacks, which deletes the msleep poll and the releaseThread() pair. Before that, the baseline has to say what the poll costs today (H6):

  • Admission latency. The gap between a column's task interval ending and the next column's beginning on the pool. The poll bounds it at kMapPollMs (30 ms) per slot; across hundreds of columns that is seconds of idle slots on a build.
  • The orchestrator's own thread. Its thread-state rows: time Blocked in the sleep against Running. A healthy orchestrator is Blocked nearly all the time, which is the sign it should be an event-loop callback.
  • Oversubscription from the release. Running octree tasks above maxThreadCount while the orchestrator and its map run at once, from the pool and queue events.
  • Main-thread cost of the move. Each callback reaps one column result; the chunks move, so the work per callback is small, but the count is large. Run A on the LAZ project shows the main thread's load today, and the re-measure after F2 shows what the callbacks add.

If H6 comes back small, the cheaper fix is a wake on a QWaitCondition signaled by each column's completion, which keeps the orchestrator on its worker and removes only the sleep. The main-thread move still removes the releaseThread(), so H4 decides between the two.

Pass: on the iPhone the Marble cold open finishes with the budget at peak above 25% of the device's starting budget; on the Mac peak footprint drops by at least the LiDAR share H1 attributed, within the spread; octree admission latency at or below one scheduler quantum, and the LAZ build's time to idle no worse than baseline.

F3One top-level job at a time new H3

This is what #711 asks for. A cwJobQueue takes jobs as QFuture-returning callables and starts the next one only after the current one settles. A job may still use the whole pool, with F2 bounding it. Scraps, LiDAR, octree builds and project load go through the queue. Interactive work keeps its own lane: tile and texture streaming, saves (already on a single-thread pool) and git. Rules to keep:

  • A queued job never waits on a job behind it in the queue, or the queue deadlocks.
  • Cancellation and coordinator supersede still reach a job that's queued but not started.
  • Queued jobs report through cwFutureManagerModel, so the task flyout shows them as waiting.
  • Closing the project or quitting cancels every queued job and lets the running one settle, in the same place shutdownBlocking drains today. A queued job never starts after its project is gone.

Pass: the overlap matrix shows zero running seconds between any two queued contexts; time to first scrap within the limit above.

F4One pool, sized once edit H4

Move the plain QtConcurrent::run calls onto cwConcurrent::run so all CPU work shares one pool. Then review the releaseThread() sites: a thread blocked in a KTX2 encode makes room for another worker, which is the oversubscription H4 measures. Only do this if the baseline shows workers above the core count.

Pass: peak runnable threads at or below the core count, and Runnable-or-Preempted time per context under 5% of its Running time.

6. Risks and open questions

  • Export size on long runs. Thread state produced 14k rows for one second of five threads. A multi-minute Marble open with dozens of threads could produce millions of rows and gigabytes of XML. The script parses with iterparse and exports one table at a time. If that's still too slow, drop Thread State Trace from run A and use context-switch instead.
  • Signpost category. The test used OS_LOG_CATEGORY_POINTS_OF_INTEREST. Thousands of task intervals would bury the Points of Interest track in the Instruments app, so B2 uses its own category. Check that the os_signpost instrument records a custom category without extra configuration.
  • iPhone launch. Check that xctrace record --device … --launch passes arguments such as --profile-tasks-quit to an iOS app. If it doesn't, stop the recording on the idle event with --attach and a manual stop.
  • Cache location for bundled .cw files. A bundle is extracted to a temporary directory before it loads. Confirm where its .cw_cache ends up, and whether a bundle open always starts cold, before --cold relies on it.
  • Allocation overhead. Malloc stack logging on a large project slows the app, which can change the overlap seen in run B. Run A's timing is the reference; run B is for memory only.
  • Peak attribution is shared. Several contexts running at the peak share the blame. Footprint growth per context, measured while it ran alone, separates them. If no context ever runs alone, a temporary --profile-tasks-serial option that forces one context at a time would give per-context working sets, and would also preview F3.
  • Windows and Android aren't covered. MarkScope's ITT backend gives VTune on Intel Windows machines. Android would need an ATrace backend; add it only if the crash shows up there.
  • F3 and responsiveness. One job at a time can make the first scrap appear later than today. The report includes time to first delivery as well as time to idle, and the pass lines in §5 bound it.
  • MarkScope has no build switch. Profiler.h selects the signpost backend with #ifdef __APPLE__, so every Release build on Apple platforms already emits signposts and nothing in CMake needs to change. The calls are cheap while nothing records.
  • Counting cache misses directly. Instruments' CPU Counters template can count L2 misses on Apple Silicon. H4 is settled by thread state, so this is only worth a fourth run if the oversubscription numbers come back small and the slowdown is still there.
