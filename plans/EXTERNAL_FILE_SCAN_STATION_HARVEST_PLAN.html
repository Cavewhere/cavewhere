Scan-Time Station Harvest H1–H4 DONE

Per-attachment cavern run at scan time, so an attached centerline's station names are known before — and independently of — the region solve. Branch externalFiles. Follows the 6c creation-path/suggester slice (ebf5ca5d). Companion to plans/EXTERNAL_FILE_EQUATES_AND_SCOPING.html.

Status
Shipped as 71559eec (H1), 5afa18ea (H2), ca72e0fa (H3) and 261990e4 (review fixes). Sections below were reconciled with the shipped code after the H1–H3 review; where the built thing differs from the original design, the section says so rather than describing the draft. Two things remain open: the manual acceptance at the end of §4, and issue #651 (the harvest loses surveys not connected to netskel's single implicit fix — see §3.1).

1. The problem

Station names for an attached centerline are learned only from the region solve (cwTrip::solvedStations(), read back out of the run's .3d), and the solve is exactly what fails for the surveys that need tying. Cavern drops a survey nothing fixes and nothing ties in (netartic.c warning 45), so its stations never reach the .3d, so:

  • cwFindFloatingSurveys::Result::stations comes back empty (cwFindFloatingSurveys.cpp, appendFloatingSurveysOf reads SolvedScopes, which only sees the region network);
  • the banner says "none of its stations were placed" and can list nothing;
  • the tie suggester's localStations() falls back to solvedStations() for a chunk-less trip and finds nothing — for exactly the trips the suggester exists to rescue.

Real-world case (the acceptance test): Dusk Butte.cwproj has two TopoDroid attachments, Nimbus_D_survey and Nimbus_g_survey, neither with a *fix, plus a native trip (Trip 3) whose single shot g2 → d4 is the intended tie-in. Both attachments show an empty "This survey is not tied in" banner. The native side already works — localStations() reads native stations from chunks, no solve needed — so g2 and d4 are sitting there as candidates. Only the attachment side is blind. After this plan, each banner should offer a one-click exact-name tie (g2 ↔ g2, d4 ↔ d4).

Rejected approaches

  • Scrape cavern's log. The "not connected" info lines (netartic.c:328-373) enumerate stations from the reduced network — network reduction collapses degree-2 chains — so most stations never appear. The strings are also translated.
  • Auto-*fix the hanging survey in the main solve. Impossible: *fix takes a station name, and not knowing the names is the whole problem.
  • Parse the files ourselves. Means owning name-extraction parsers for Survex, Compass, and Walls, forever, in parallel with cavern's. The harvest run below gets cavern to do it with zero new parsing code.

2. The enabling mechanism

Cavern always solves a run with no fixed points

survex/src/netskel.c:102-137: when a run contains no fixed station at all and no coordinate system is set (!pcs->proj_str && !proj_str_out), cavern picks the first station and fixes it at (0, 0, 0) — message 72, "Survey has no fixed points. Therefore I've fixed %s at (0,0,0)" — and solves the whole file in that arbitrary frame.

So a driver that is nothing but *include "<entry file>" — no *fix, no *cs, no wrapper *begin — always solves, and its .3d carries every station name in the attachment. Coordinates come out in a meaningless local frame; we throw them away and keep the names.

Names match the trip's tails by construction. The main solve's driver wraps the same *include in the cave and trip *begin labels, producing <cave>.<trip>.hanging.h1; cwTrip::solvedStations() strips the scope prefix, yielding the tail hanging.h1. The harvest driver's bare *include of the same entry file produces the label hanging.h1 directly. Both are cavern's own labeling of the same bytes — the only difference is the wrapper, which is exactly what tail-stripping removes. This holds for Compass and Walls attachments too (cavern reads .dat/.mak/.wpj/.srv natively through *include, same as the main driver).

Corrected after H1 — the separator is not what carries Compass/Walls

This section originally argued the Compass/Walls case rested on the ':' separator those runs emit being normalized to '.' by cwSurvex3DFileReader (3f7ddbfe). H1 showed that argument is beside the point here: cavern's .dat/.wpj readers contribute bare tails (§3.1), so no harvested label ever contains a separator at all. The normalization still matters — for the region solve's own labels — but it is not what makes the harvest work for these formats, and no fixture in the H1 gate exercises it.

3. Design

3.1 The harvester — new free-function unit

cavewherelib/src/cwExternalStationHarvest.h/.cpp (new; globbed via CONFIGURE_DEPENDS, no CMake edit):

namespace cwExternalStationHarvest {

//! Every station name declared by an external centerline's entry file, learned
//! by running cavern over the file alone. ... Returns canonical
//! (cwStation::canonicalKey) sorted tails in the attachment's own namespace —
//! the same spelling cwTrip::solvedStations() yields for the trip once the
//! region solve places it.
CAVEWHERE_LIB_EXPORT Monad::Result<QStringList> harvest(const QString& entryFile);

} // namespace cwExternalStationHarvest

Implementation (as shipped — steps 1 and 2 are guards the original list omitted):

  1. Entry must exist. QFileInfo::exists on the absolute path, else a Monad::Result error naming it. Unreachable from the production caller, which checks the same thing first (§3.2) — it exists so the unit is safe standalone.
  2. Refuse a path Survex cannot quote. *include has no escape for an embedded ", and survex treats \n, \r and \032 alike as end of line (datain.c's SPECIAL_EOL table), so such a path would break the driver or smuggle in a second token. Same refusal cwSurvexExporterCaveTask::writeExternalInclude makes.
    Widened in the review: both guards originally rejected only " and \n. Both now reject all four characters — the duplication is left standing on purpose, since unifying the two copies is its own follow-up (§6).
  3. QTemporaryDir; write harvest.svx containing exactly one line: *include "<absolute entry path>". Nothing else — no fix, no cs, no begin. (Includes inside the entry resolve relative to the entry's own directory, so the attachment-dir closure that reconcile copied is what gets read.)
    Added in the review: the write is checked (QTextStream::status plus QFile::flush). A driver that only partly reached the disk is still valid Survex — an empty one just includes nothing — so a full disk would otherwise get the user's entry file blamed for "No survey data".
  4. cwCavernRunner::run(driverPath, out3dPath) — already serialized against the main solve by its internal mutex, already writes the .log sidecar.
  5. cwSurvex3DFileReader::readStationPositions(out3d); return its keys. cwStationPositionLookup canonicalizes on insert and keeps a QMap, so they are already canonical and sorted — and sorted the same way cwTrip::solvedStations() walks the cave lookup, so a trip's names don't reorder when the fallback swaps one source for the other.
    Added in the review: an empty lookup is an error, not a success. The reader only qWarnings on a .3d it cannot read and hands back an empty lookup, which would have this function report success with no names — the one answer it must never give, since no caller can tell it apart from a file that declares nothing. Cavern never writes an empty .3d: a run with no survey data is fatalerror 43 (netskel.c:93), so empty-after-success means the read failed.
  6. On cavern failure (a genuinely broken file): return the Monad::Result error with cavern's log text. The caller records empty names — the pre-harvest status quo.

Error codes, corrected in the review. Every failure path originally returned LinePlotErrorCode::ExportFailed, naming an operation the harvest never performs. As shipped: the two input guards return ValidationFailed, the three driver-writing failures ExportFailed (the same meaning cwSurvexExporterRegion gives it — "could not produce the survex input"), cavern's own failure passes its CavernFailed through untouched, and an unreadable .3d returns ParseFailed.

Two things the implementation settled

The error text is trimmed of the driver. Cavern prefixes the real error with In file included from /tmp/<random>/harvest.svx:1:. That path is deleted before anyone reads the message and is different on every run, so the same failure would look like a new one each time and §3.7's panel callout would name a file the user can't open. The survex_with_missing_include.svx case asserts two runs are byte-identical, which fails without the trim.

Corrected in the review (261990e4): the original approach — drop every line mentioning the working directory — rested on the claim that "the error itself points at the entry file and survives". That is false whenever cavern blames the driver rather than the entry, which is exactly what happens for an entry that exists but cannot be opened: harvest.svx:1: error: Couldn't open file "…" was the only line carrying the diagnosis, and dropping it left the user an echoed *include and a caret with no reason. The harvest now strips only the <file>:<line>:<column>: location prefix, drops In file included from lines, and falls back to dropping the whole line only if it still names the driver afterwards — so determinism is preserved and the reason survives. Covered by "Harvest keeps cavern's reason when cavern blames the driver".

Compass and Walls contribute bare tails. Cavern's .dat/ .wpj readers do not turn the file's own survey names into naming levels the way *begin does: compass_solvable.dat harvests as s1/s2/s3, not s.s1, and walls_simple.wpj as a1..a4. The region solve sees the same bare tails, so the by-construction match still holds — and §3.5's leaf comparison has nothing to strip for these two formats.

Known limitation — *cs without *fix
An entry file that sets a coordinate system but fixes nothing defeats the auto-fix (netskel.c requires no proj string) and cavern errors out. Harvest then returns an error and the names stay empty — exactly today's behavior, no regression. Not worth special handling: such a file is self-contradictory (a CRS with nothing positioned in it).
Known limitation — internally disconnected surveys (issue #651)

Found by the H1–H3 review, and the more serious of the two. netskel.c fixes exactly one station, and articulate() then drops every component that station cannot reach (netartic.c:337, warning 45) — while cavern still exits 0. So an entry file holding two surveys with no leg and no *equate between them harvests short, with no error at all. The survex_two_parts.svx fixture yields exactly parta.a1/a2/a3; PartB's three stations are simply gone, invisible to both the banner and the suggester, and untieable from the UI.

Fixing it means fixing one station per connected component rather than one per file — a change to the vendored cavern, hence its own commit and issue #651. Until then the header carries a \warning and "Harvest loses the components netskel's one fix cannot reach" pins the loss so it fails loudly when fixed. Note this also feeds the precedence split in §3.5.

3.2 Where it runs — the manager's existing scan pipeline

cwExternalCenterlineManager already has the right seam: the three-stage recompute (recomputeWatchSetAndProbeSources → worker scanOwners → main-thread applyScanResult) runs at attach, at detach, at project load (setRegion), on every watched-file change, and on every settings mutation — and is coalesced through m_scanRestarter so edit bursts cost one scan.

  • ExternalScanResult gains QHash<QUuid, QStringList> tripStations.
  • scanOwners (worker thread, static, pure): for each trip owner whose project-side entry resolves (the same projectEntry the scan already builds at cwExternalCenterlineManager.cpp:332), call cwExternalStationHarvest::harvest(projectEntry) and record the names. Project-side only — the project copy is the source of truth (Phase 2 direction change), and it is what the solve *includes. Cave-level owners are skipped (§6).
  • applyScanResult (main thread) pushes the names before the solveNeeded() emission, so the solve that follows snapshots fresh names.
    Built differently than drafted: this bullet originally said "resolve each ownerId to its live trip and push". The shipped applyHarvestToTrips inverts that — it walks every trip in the region and assigns result.tripStations.value(trip->id()), which is empty for any trip the scan did not harvest. The inversion is load-bearing, not incidental: resolving only the result's ownerIds would leave stale names on a detached trip, since a detached trip contributes no owner and so appears in no result. The wiring test's detach case asserts exactly this. Both setters early-return on equality, so assigning empty-to-empty across a region of native trips emits nothing.
Consequence the review flagged (open, 🟡)
Because the apply assigns per trip inside that loop and each setter emits synchronously, a bound cwTieSuggestionModel does a full beginResetModel rebuild per trip, and the first N−1 of those read a half-applied region — transient wrong rows in an open panel, with a correct end state. Batching the emissions (or applying under a single reset) would remove it.
A missing in-project copy is silent (open, 🟡)

The harvest only runs for an owner whose project-side entry resolves. When it doesn't — the in-project copy is gone, the reconcile hasn't run yet, the attachment directory was deleted out from under the project — the owner contributes nothing to tripStations, and applyHarvestToTrips' walk-every-trip inversion then assigns empty names and an empty error. Which is byte-identical to the state of a trip with no attachment at all.

So the one failure the user can actually act on — "the file this trip points at isn't there" — is the one that produces no banner, no complaint, and no station list, while ExternalCenterlineMissingSourceBanner speaks only for a missing source (the user's original), not a missing project copy. Wants the unresolved case to record an error rather than nothing, which also gives §3.7's banner something true to say. Fixing it means deciding what scanOwners knows about why an entry didn't resolve, so it is not a one-liner.

Cost: one cavern run per attached trip per recompute, off the main thread, serialized by cavern's mutex, coalesced by the restarter. Attachments are single-survey files — milliseconds each. An mtime-keyed skip cache is possible later if a project with dozens of attachments ever notices; not in this slice.

3.3 Where the names live — cwTrip

As shipped — the draft showed plain accessors and a single signal; the QML binds both fields directly (§3.7), so each is a Q_PROPERTY with its own NOTIFY:

Q_PROPERTY(QStringList externalStations READ externalStations
           NOTIFY externalStationsChanged FINAL)
Q_PROPERTY(QString externalStationsError READ externalStationsError
           NOTIFY externalStationsErrorChanged FINAL)

//! Station names declared by this trip's attached external centerline, in the
//! trip's own namespace — learned at scan time by running cavern over the
//! attachment alone, so they exist whether or not the region solve placed the
//! survey. Empty for a native trip, and for an attachment whose file cavern
//! cannot read. Derived state: rebuilt by every external-centerline scan,
//! never persisted.
QStringList externalStations() const;
void setExternalStations(const QStringList& stations);   // manager-only in practice

QString externalStationsError() const;
void setExternalStationsError(const QString& error);
...
//! Each signal covers only its own field — the two move independently.
void externalStationsChanged();
void externalStationsErrorChanged();
  • Plain member + explicit setter with the standard if (m_x == x) return; guard (no bindable properties).
  • cwTripData gains a QStringList externalStations field, filled by cwTrip::data() so the value rides the solve's region snapshot into the worker. Not serialized — no proto change; it is derived from files the project already owns, and persisting it would only add a staleness channel.
    Settled in H2: setData() deliberately does not read it back. Every cwTripData reaching that setter either came off disk — where the field is never written, so it is empty — or was just taken from the same trip, so assigning could only ever wipe the live harvest (on a load, or a sync-driven trip reload) and never carry anything in.
  • Setting it must not mark the project dirty or trigger a save — it is scan output, not user data. (Same reasoning that made the C2 review flag the save-trigger bug, from the other direction.)
Follow-up — derived scan output belongs in a group, not loose on the trip (🟡)

cwTripData now carries externalStations as a bare field that data() writes and setData() deliberately skips — a rule that lives nowhere but a comment, and that the next derived field will have to restate. The codebase already has the pattern for this: ExternalCenterlineInputs groups an attachment's scan-derived inputs behind one type, so "this rides the snapshot out but never rides back in" is a property of the group rather than of each field.

externalStationsError is the second such field and it arrived one commit later, which is the argument. Folding both into the existing group makes the asymmetry structural, and gives the missing-copy case above and the accessor below one place to land. Blast radius: cwTripData, cwTrip::data/setData, the manager's apply, and the consumers' reads.

3.4 Consumer — cwFindFloatingSurveys::fromExternalScopes

In appendFloatingSurveysOf (cwFindFloatingSurveys.cpp:220-250), the floating verdict is untouched — solving nothing still settles "adrift" on its own. Only the station list gains a fallback: 

result.stations = solved.solvedAnything(trip.id)
                  ? solved.stations(trip.id)
                  : caveLocalHarvestOf(trip, labels.tripLabels(cave.id));
Superseded by H4. The fallback above is now a union, and the choice of sources is no longer made here: caveLocalStationsOf calls cwTrip::knownStationNames(trip, solved.stations(trip.id)) and puts the trip's scope on the result. SolvedScopes::stations() changed with it — it now hands back scope-local names (a trip scope's own "*begin" head comes off), so both sources reaching the merge speak one namespace.
Settled in H3: the harvested names cannot be dropped in raw. A record's stations are cave-local — SolvedScopes strips only the cave head, so a solved attachment reads "<tripLabel>.<fileBegin>.<tail>" — while the harvest reads the file on its own and so carries only the levels the file itself opens. cwFloatingSurveyModel turns a record into handles by stripping the trip's scope prefix, so a trip whose label happens to match the file's own *begin (an attachment named after its file — the ordinary case) would have one level too many stripped and every tie would name the wrong station. appendFloatingSurveysOf therefore puts the trip's scope back on, through the same cwTrip::scopePrefix(data, labels) the live side uses, and Result::stations keeps one contract whichever pass named it.

Doc updates ride along: Result::stations' "Empty means the survey produced no solved station at all" contract (cwFindFloatingSurveys.h:70-75) becomes "Empty means the survey's stations could not be learned at all — cavern dropped it and the scan-time harvest failed." The same empty-means-dropped phrasing in cwFloatingSurveyModel.h:79-83 and cwFloatingSurveyStatus.h:75-79 gets the same correction.

Follow-up — the record should carry handles, not scope-prefixed strings (🟡)

Result::stations is a QStringList of cave-local names, so this pass has to add the trip's scope prefix (the H3 fix above) purely so cwFloatingSurveyModel can strip it back off to build the handles the UI actually uses. Two passes agreeing on an encode/decode of the same identity, with the ordinary case — an attachment named after its file — sitting one level away from silently naming the wrong station.

The A1 work already made identity travel as a cwStationHandle (project_qualified_name_ownership), and this record is the remaining place it doesn't. Carrying handles end to end deletes both the prefix add and the strip, and with them the class of bug the H3 note exists to prevent. Blast radius: cwFindFloatingSurveys, cwFloatingSurveyModel, cwFloatingSurveyStatus, and the QML that reads stations for display only.

3.5 Consumer — cwTieSuggestionModel

  • localStations() (cwTieSuggestionModel.cpp:63-84): for a chunk-less trip, prefer trip->externalStations() when non-empty; keep the solvedStations() fallback for the window before the first scan applies. (The chunk branch is untouched — native trips never harvest.) This upgrades both sides: the floating trip's own list and attached candidate trips elsewhere in the cave. Superseded by H4: the whole function is now three lines over cwTrip::knownStations(), which owns the policy and unions the sources rather than choosing between them.
  • setTripConnected(): add cwTrip::externalStationsChanged to the forEachSignal list, so a harvest landing on the bound trip rebuilds rows immediately. Candidate trips' harvests arrive through the existing pulses: every scan apply that changes anything requests a solve, and the solve fires solvedStationsChanged (cave-relayed) at the bound trip. If testing shows a candidate-only harvest that provokes no re-solve, add a cave-level relay then — not preemptively. Review note: the relay is still absent and the gap is still latent — no traced path changes a candidate trip's harvest without also requesting a solve — but that invariant is spread across four call sites and nothing enforces it. Closed by H4: the list is now knownStationsChanged (this trip's stations, the cave's solve included) plus cwCave::tripExternalStationsChanged (a candidate trip's harvest), so the latent gap is a wire rather than an invariant.
Follow-up phase H4 — one accessor owns "this trip's names" — DONE

The defect that forces it. This section prefers the harvest over the solve; §3.4 prefers the solve over the harvest. Both render into the same banner — the station list comes from the find pass, the suggestion rows from the suggester — so the two can disagree on one screen. With issue #651 live that is reachable rather than theoretical: a multi-component attachment the region solve did place fully (one equate per component) has solved names the harvest never learned, so the suggester can offer strictly fewer stations than the list above it shows.

The fix. One accessor on cwTrip — "this trip's names in its own namespace, best available source" — that every consumer calls, instead of the policy living in two anonymous namespaces that never had to agree.

Why it is its own phase rather than a fix here. It closes three separate items at once, and closing any one of them alone would put the policy in a third place:

  • the precedence split above (the suggester and the find pass disagreeing);
  • the missing cave-level externalStationsChanged relay below — with one accessor there is one thing to subscribe to, instead of an invariant spread across four call sites that nothing enforces;
  • the cwScopeStationListModel follow-up in §6, which is blind to harvested names for exactly the same reason: it reads one source directly.

Sequenced after the C7 scope-lens work, since that model is the third consumer and the accessor should land with all three converted rather than leaving a fourth reader of the raw fields.

What landed. cwTrip::knownStations() — one entry per station, the scope-relative name plus a std::optional<QVector3D> position that is set only where the solve placed it. The policy is a union, not a precedence: chunks, the scan's harvest, and the solve all contribute, deduplicated by canonical key keeping the authored spelling, sorted in natural order. Preferring one source was the bug — each of the three knows names the others cannot, so any choice among them lists strictly fewer stations than the trip has. A static knownStationNames(const cwTripData&, const QStringList& scopeLocalSolved) overload does the same for the worker-side snapshot, which carries no cave lookup and so is handed the solved names it cannot derive.

All three consumers converted: cwTieSuggestionModel::localStations (now three lines), cwScopeStationListModel::rebuildRows (which gained known-but-unplaced rows — PositionRole is undefined there, not the origin, closing the §6 item), and cwFindFloatingSurveys::appendFloatingSurveysOf.

The signal came out one step differently from the sketch above. cwTrip gained knownStationsChanged, chained from its own solvedStationsChanged and externalStationsChanged. The cave-level relay is a new cwCave::tripExternalStationsChanged aggregate, chained from each trip's harvest but deliberately not back into each trip's knownStationsChanged the way stationPositionPositionChanged is: a trip's harvest is its own field, so it already pulses for itself, and relaying it back doubled every one of those pulses (caught by the first run of the new signal test). So a consumer that reads only its bound trip subscribes to one signal, and one that reads across the cave — the tie suggester — subscribes to two, which is honest, since it genuinely reads two scopes.

Tests: [cwTrip][knownStations] pins the union, the authored-spelling rule, natural order, snapshot/live parity, and each pulse (including that a sibling's harvest reaches the aggregate exactly once and stops on removal from the cave). [FloatingSurveys] gains a direct fromExternalScopes case built from a hand-made snapshot — issue #651's shape without needing cavern to reproduce it. [ScopeStations] gains the known-but-unplaced row. [TieSuggestionModel] gains the candidate-trip harvest pulse, which nothing carried before.

One gap H4 opened, left open on purpose (🟢). Chunks are the one source with no pulse of their own — nothing on cwTrip watches chunk stations, so a chunk edit reaches knownStationsChanged only through the solve that follows it. That was invisible while cwScopeStationListModel listed solved stations only, and it is visible now that it lists unplaced ones: a station typed into a cave that will not solve stays out of the list until one does. Wiring it means per-chunk dataChanged/stationsAdded/stationsRemoved connections managed across insertChunk/removeChunks, and dataChanged fires per keystroke — so a naive wire would reset the autocomplete model under the very cursor that is typing into it. Wants debouncing, and is worth its own commit if anyone hits it.

3.6 Consumer — FloatingSurveyBanner.qml copy

The detail text branches on stations.length (FloatingSurveyBanner.qml:55-61). Today's non-empty branch — "its stations were placed in a frame of their own" — becomes false for a dropped survey whose names now arrive from the harvest: those stations were not placed anywhere. Reword so each branch is true in every state that can reach it:

BranchNew copy
stations.length > 0 "Nothing joins it to the rest of the cave, so it can't be placed with the others."
empty (now: harvest failed too — unreadable/broken file) "Nothing joins it to the rest of the cave, and its stations couldn't be read from its file."
The empty branch is rarer than "broken file" suggests. The review tried to pin it from test_aBrokenAttachmentSaysWhichFileIsBroken — the obvious candidate — and it does not hold: a file cavern cannot read fails the region driver too, so the cave solves nothing, no scope becomes the anchor, and appendFloatingSurveysOf returns at cwFindFloatingSurveys.cpp:247 before it can name anything adrift. A broken file therefore gets one complaint, about the file — which is the behavior worth having, and the test now asserts the floating banner stays down. What actually reaches the empty branch is narrower: a cave that did solve, holding a trip whose own harvest yielded nothing. Today that is the window before the first scan applies, and the unresolved-copy case in §3.2. The copy stays as written; the isolation test is what pins its wording.

3.7 Validation for free — per-attachment error attribution

The harvest is also the first pass that validates an attachment. The scanner only walks includes and best-effort-parses metadata — it never checks syntax — so today a broken .svx/.dat/.wpj surfaces only when the whole region solve fails, with one region-level cavern log that doesn't say which attachment poisoned it (and the floating records just carry forward, so even the banner goes quiet). The harvest runs cavern over each attachment alone, so a failure is attributed to the exact file, with cavern's own error text, at scan time — right after attach and on every watched-file edit.

  • ExternalScanResult gains QHash<QUuid, QString> tripHarvestErrors — cavern's error text from the harvest's Monad::Result, empty entry (or absent key) for a clean file.
  • cwTrip gains externalStationsError (QString + NOTIFY) beside externalStations, pushed in the same apply. The two are one fact from one run: names empty and error non-empty ⇔ cavern rejected the file. Derived state, never persisted, never a save trigger — same rules as §3.3.
  • Surface: ExternalCenterlineTripPanel shows an error callout when non-empty ("This file has errors" + cavern's message), which is the right home because a broken file is broken whether or not the trip floats — and because a broken file fails the region solve, the floating banner may be showing stale rows at exactly that moment. The banner's empty branch (§3.6) stays as the summary; the panel error is the explanation.
  • cwAttachedCenterlinesModel row error flag/count: optional, later — the per-trip panel is the surface users are looking at when they hit this.
Follow-up, not in this slice
Running the harvest in the attach dialog's preview (cwExternalCenterlineScanPreview) would catch a broken file before [Attach] is clicked. Deliberately deferred: detection lands seconds later anyway via the post-attach recompute, and the preview should stay fast.
Open question (carried from 6c) — answered in H3
The tieSuggestionsEmpty label promised "the tie has to be made by hand" — a path that doesn't exist. H3 replaced it with "…Renaming one to match will connect them", which the review then found false in turn: this banner renders only for an attached survey, and an attachment is always scoped (cwTrip::isScoped() is true whenever externalCenterline is non-empty), so matching names stay separate stations until a tie is actually made. Shipped wording (261990e4): "No station in the rest of the cave is named like one of these. Renaming one to match will offer a one-click tie here." Now pinned in tst_ExternalCenterlinePanelComponents beside the two sibling strings, along with both states that hide the label: a surface that offers no suggester at all, and a survey with no names to rename.
The error log is height-capped. Cavern reports every problem in a file, not the first, so a badly broken attachment produces dozens of lines — and the panel's way out of that state, Reload and Detach, sits below this banner. An uncapped log pushed them off the bottom, leaving the user reading a complaint they had no way to act on. The message now scrolls inside a fixed maximumMessageHeight; nothing is truncated, and the isolation test asserts both halves — the banner stops growing, and all 60 lines are still there to scroll to.

5. Ordering & races (why this is safe)

  • Load: the manager's contract already defers the initial solve until the scan applies ("the consumer's initial solve is requested through solveNeeded() after the scan applies", cwExternalCenterlineManager.h:65-69). Apply pushes trip names before emitting, so the first solve's region snapshot carries them.
  • File edit: watcher → recompute → apply (names refresh) → solveNeeded. Same ordering.
  • Solve triggered without a scan (shot edit, equate, rename): names are whatever the last scan cached — correct, since the attachment's bytes didn't change.
  • Worker purity: scanOwners stays static and value-in/value-out; the harvest touches only the filesystem and cavernlib (mutex-serialized). No live pointer crosses the boundary; the trip push happens in the main-thread apply.
  • Restarter supersession: a stale harvest never lands — same guarantee every other ExternalScanResult field already relies on.
  • Threading & job tracking come free: the harvest runs inside scanOwners, i.e. on the cwConcurrent worker the pipeline already uses, and the restarter's future is already registered with cwFutureManagerToken as the "External centerline scan" job (cwExternalCenterlineManager.cpp:97). No new AsyncFuture or token wiring.
Two claims this section overstated (corrected after the review)
  • "The only main-thread work is the apply-stage push" understates it. The apply runs two setters against every trip in the region, and each emission synchronously re-enters any bound model's reset (see §3.2). Still main-thread and still ordered before solveNeeded() — but it is model-reset work, not a field assignment.
  • Restarter supersession bounds correctness, not cost. A stale harvest indeed never lands. But scanOwners is a plain cwConcurrent::run with no isCanceled() check, so a superseded scan runs its whole owner loop to completion — and each iteration is now a cavern run on the same global mutex the region solve needs. On a load that fires several recomputes across event-loop turns, that is N serialized cavern runs per superseded scan. Bounded and correct; potentially slow on an attachment-heavy project. The mtime-keyed cache in §6 is the lever, and a cancellation check is the cheaper half.

6. Not in this slice

  • Cave-level attachments. No consumer: fromExternalScopes structurally can't see them (they unwrap into the cave scope, cwFindFloatingSurveys.h:103-108) and the suggester is trip-based. Harvesting for cave owners is a two-line extension when a consumer exists.
  • Source-side harvest. Live-link staleness is notify + one-click Update; the project copy is the source of truth, and it's what the solve reads.
  • Persisting harvested names (proto). Derived data; the scan rebuilds it at every load before the first solve needs it.
  • mtime-keyed harvest cache — and getting the scan off cavern's mutex. Measure first; attachments are small. But the coupling is structural, not just a cost: cwCavernRunner serializes every caller on one global mutex, so a scan of N attachments now queues N cavern runs behind whatever solve is in flight, and the scan's latency became the solve's latency the moment the harvest landed. scanOwners also has no isCanceled() check between runs, so a superseded scan runs every remaining harvest to completion before its result is thrown away — the restarter coalesces the starts, not the work already begun. A per-file cache keyed on mtime is the cheap half; a cancellation check in the loop is the cheaper half and worth doing first. Raised by the H1–H3 review.
  • Proximity ranking / coordinates. Harvest coordinates are an arbitrary auto-fixed frame — meaningless against the cave. Name-only ranking remains complete for the banner surface (the tie ends the float); proximity belongs to the future Connections list.
