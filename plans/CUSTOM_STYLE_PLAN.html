CaveWhere custom style: implementation plan

Direction D · Karst Soft · light and dark · Qt 6.11.2 · written 2026-10-01 · design reference: CUSTOM_STYLE_PROTOTYPES.html, direction D

Each package names its files, its steps, its code, and the commands that prove it is finished, so one agent can carry it out with this document and the repository alone. The architecture questions the earlier draft left open are answered here by a throwaway test project built on 2026-10-01; section 2 lists what it proved.

2. What the test project proved

A standalone project mirrored CaveWhere's structure: a shared library holding a QML module with a Theme singleton that reads a C++ singleton, a separate style module, and an executable that selects the style at run time. It ran on macOS natively and on the offscreen platform against Qt 6.11.2. Every snippet in section 6 comes from it.

The reference files from section 6, rendered by the test project. Top: dark. Bottom: light. The combo box behind the tooltip is Fusion's, drawn through the fallback with the application palette.

#FactConsequence for the plan
V1A static QML-only style module linked into the executable loads through QQuickStyle::setStyle(), and its files can import the application's own QML module to read Theme.Tokens stay in Theme.qml. No separate token module.
V2Under run-time style selection, an IMPORTS QtQuick.Controls.Fusion line in the style's CMake gives a Basic fallback. QQuickStyle::setFallbackStyle("Fusion") gives Fusion.The fallback is set in C++, next to setStyle. The CMake module has no IMPORTS.
V3A control starts from the palette of the Qt Quick Controls theme, which the fallback style (Fusion) supplies, and inherits only the roles an ancestor sets explicitly. A window whose palette is bound to Theme tokens hands them to its controls, menus, and popups, at creation and on a scheme flip. An ApplicationWindow updates existing popups live; a plain window updates only items. The test project's first reading, that the application palette alone does this, held only for items that already existed; WP3 and WP4 corrected it.ThemePalette.qml binds every role to a token. The style's ApplicationWindow.qml and every other window root take palette: ThemePalette {}. No C++ palette object.
V4The offscreen platform ignores QStyleHints::setColorScheme(). macOS honors it live.Theme.dark reads the Appearance setting first and the system second, so tests can force dark headless.
V5Palette changes reach items one event-loop turn after they are set.Tests that flip the scheme use tryVerify, never an immediate compare.
V6An inline background: on a control instance replaces the style's delegate cleanly when the style's delegate carries no id.Rule S3 in section 4.
V7A menu shown in its own window (Popup.Window, the type CaveWhere's menus get today according to the comments in tst_ManualScreenshots.qml) clips anything drawn outside the background item. Negative insets enlarge the background, and the popup window with it: a 141×106 menu got a 177×142 window with the shadow intact.Every popup uses the inset pattern in StylePopupPanel.
V8ColorImage with sourceSize: Qt.size(width, height) renders an SVG glyph crisply on a Retina display. A larger sourceSize becomes the item's implicit size and inflated menu rows from 25 to 34 px.Rule S10.
V9T.TextField and T.TextArea have topPadding, leftPadding, and friends, and lack horizontalPadding and verticalPadding.Rule S9.
V10With import QtQuick as QQ, a color property is declared property QQ.color.Rule S11.
V11QT_QML_INTERNAL_TYPE registers helper files as internal in the generated qmldir.Helpers live beside the controls as Style*.qml.
V12RectangularShadow from QtQuick.Effects draws the soft shadow. The window font reaches every control and popup by inheritance.No shadow image asset, no font code in the style.

4. Rules for every agent

Repository rules

  1. R1. Leave every change uncommitted unless the launch prompt says to commit. Never run git push, git commit --amend, or git reset. Commit messages carry no mention of Claude and no Co-Authored-By line.
  2. R2. Touch only the files your work package lists. When another file needs a change, stop and report it.
  3. R3. When a file, line, or symbol named in your card differs from the repository, stop and report the difference. The line numbers in this plan were read on 2026-10-01 at commit 3db25ddb.
  4. R4. American English everywhere. State facts positively in comments. Comment sparingly: explain a non-obvious why, skip the obvious what.
  5. R5. QML: import QtQuick as QQ; typed properties, never property var; text is QC.Label in app QML; no Canvas and no Shapes; custom painting is a C++ QCanvasPainterItem; body order is id, objectName, property declarations, property assignments, signals, functions, bindings, handlers, children, states.
  6. R6. C++: 4-space indent, braces on the next line, m_ members, k-prefixed constants in an anonymous namespace, function-pointer connect, QStringLiteral for constant strings, explicit setters with if (m_x == x) return; and no bindable properties, no test-only members on production classes.
  7. R7. Build with -j 10. Run the two test suites one after the other, never at the same time. Send test output to a log file with tee.
  8. R8. New QML tests wait with tryVerify and tryCompare; waitForRendering hangs on the offscreen platform. C++ tests use paths that include the process id or QTemporaryDir.
  9. R9. A test that fails after your change is fixed by correcting the style first. Change a test only when it asserts a pixel value that belongs to Fusion, and list each such change in your report with the old and new value.
  10. R10. New .qml files under cavewherelib/qml/, cavewherelib/style/, and test-qml/, and new .cpp/.h files under cavewherelib/src/ and testcases/, are picked up by CMake globs. Leave the CMake file lists alone.

Style-file rules

  1. S1. The root of X.qml is T.X with id: control, where T is QtQuick.Templates.
  2. S2. Allowed imports: QtQuick as QQ, QtQuick.Templates as T, QtQuick.Controls.impl, QtQuick.Effects, cavewherelib. A style file that imports QtQuick.Controls, Fusion, or Basic is wrong.
  3. S3. The object assigned to background, contentItem, indicator, handle, arrow, header, footer, or popup carries no id. Children nested inside it may have ids.
  4. S4. Every color and every metric is a Theme token. A style file contains no hex literal and no bare pixel number for a size that a token names. When a control needs a value the token block lacks, add the token to the block in section 5 with both a dark and a light value, and add it to the Colors page.
  5. S5. Text color goes through the control's palette: control.palette.buttonText on button-like controls, control.palette.windowText on labels beside indicators and on menu items, control.palette.text inside fields. This keeps per-instance overrides such as palette.buttonText: Theme.errorText working. Exceptions with a fixed token: primary button text, tooltip text, tab text, placeholder text.
  6. S6. Size comes from content. Keep the standard implicitWidth and implicitHeight formulas from the reference files. Text-bearing controls get their width from text plus padding, so they hold at every font family and base size from 10 to 28 px.
  7. S7. Disabled visuals use opacity: Theme.disabledOpacity. Keyboard focus shows StyleFocusRing bound to control.visualFocus. Hover reads control.hovered. Pressed reads control.down.
  8. S8. A style file may instantiate another control unqualified only when the style has that file. The pairs are: Menu uses MenuItem; MenuBar uses MenuBarItem; ComboBox uses ItemDelegate and ScrollIndicator; Dialog uses DialogButtonBox and Label; DialogButtonBox uses Button; ScrollView uses ScrollBar. Each pair lands in one work package.
  9. S9. T.TextField and T.TextArea take topPadding, bottomPadding, leftPadding, rightPadding. The horizontalPadding and verticalPadding shorthands exist on T.Control descendants only.
  10. S10. Glyphs are ColorImage items from QtQuick.Controls.impl with sourceSize: Qt.size(width, height) and a color token. Bundled glyphs: qrc:/twbs-icons/icons/check-lg.svg, dash.svg, chevron-down.svg, chevron-up.svg, chevron-left.svg, chevron-right.svg, x.svg. To use another Bootstrap icon, add its line to cavewherelib/cwResources.qrc.
  11. S11. With the QQ alias, value types are qualified in declarations: property QQ.color, property QQ.font. bool, int, real, and string stay bare.
  12. S12. Every popup-type control (Menu, ToolTip, Popup, Dialog, the ComboBox list) sets all four insets to -Theme.popupShadowMargin and uses StylePopupPanel as its background.
  13. S13. Take the template plumbing for a control from Qt's own implementation at /Users/cave/Qt/6.11.2/macos/qml/QtQuick/Controls/Basic/X.qml, with Fusion's at .../Controls/Fusion/X.qml as a second reference: implicit-size formulas, indicator positioning, validator wiring, delegate model expressions, states for scroll bars. CaveWhere is GPL v3, so adapting that code is license-compatible. Replace every color, image, and metric with tokens.

#include "cwAppearanceSettings.h"

//Qt includes
#include <QCoreApplication>
#include <QGuiApplication>
#include <QSettings>
#include <QStyleHints>

namespace {
    QString colorSchemeKey() { return QStringLiteral("colorScheme"); }
}

cwAppearanceSettings* cwAppearanceSettings::Settings = nullptr;

cwAppearanceSettings::cwAppearanceSettings(QObject* parent) :
    QObject(parent)
{
    QSettings settings;
    const int stored = settings.value(colorSchemeKey(), System).toInt();
    m_colorScheme = (stored == Light || stored == Dark) ? static_cast<ColorScheme>(stored) : System;

    //System leaves the style hints as they are at startup: the QML test main
    //pins a light scheme for manual screenshots before this runs.
    if (m_colorScheme != System) {
        applyToStyleHints();
    }

    connect(QGuiApplication::styleHints(), &QStyleHints::colorSchemeChanged,
            this, &cwAppearanceSettings::updateDark);
    updateDark();
}

void cwAppearanceSettings::setColorScheme(ColorScheme colorScheme)
{
    if (m_colorScheme == colorScheme) {
        return;
    }
    m_colorScheme = colorScheme;

    QSettings settings;
    settings.setValue(colorSchemeKey(), static_cast<int>(colorScheme));

    emit colorSchemeChanged();
    applyToStyleHints();
    updateDark();
}

//Asks the platform to follow, so native title bars and dialogs match where the
//platform supports it. The hint is advisory: dark() below is computed from the
//setting itself and holds on every platform, including offscreen.
void cwAppearanceSettings::applyToStyleHints()
{
    QStyleHints* hints = QGuiApplication::styleHints();
    switch (m_colorScheme) {
    case System:
        hints->unsetColorScheme();
        break;
    case Light:
        hints->setColorScheme(Qt::ColorScheme::Light);
        break;
    case Dark:
        hints->setColorScheme(Qt::ColorScheme::Dark);
        break;
    }
}

void cwAppearanceSettings::updateDark()
{
    const bool systemDark = QGuiApplication::styleHints()->colorScheme() == Qt::ColorScheme::Dark;
    const bool dark = m_colorScheme == Dark || (m_colorScheme == System && systemDark);
    if (m_dark == dark) {
        return;
    }
    m_dark = dark;
    emit darkChanged();
}

cwAppearanceSettings* cwAppearanceSettings::instance()
{
    return Settings;
}

void cwAppearanceSettings::initialize()
{
    if (Settings == nullptr) {
        Settings = new cwAppearanceSettings(QCoreApplication::instance());
    }
}

8. Work packages

Packages run in order, one at a time, in one working tree. Each ends with a build and a test run, so the app is shippable after every package from WP4 on: the Fusion fallback covers whatever the style has yet to draw. Three gates pause the pipeline for Philip to look at the result.

How to run the pipeline

  • One implementer, then one reviewer, per package. The implementer gets the first prompt below with the package id filled in. The reviewer gets the second. A FAIL verdict goes back to a fresh implementer together with the reviewer's numbered list; two failed rounds on one package stop the pipeline for a person to look.
  • Difficulty tags. low and medium packages suit a smaller model. high packages touch C++, CMake, or control plumbing with many interacting properties; give those to the strongest model available, or expect a second round.
  • Commits. The orchestrator commits after a package passes review only when Philip's launch prompt says so, one commit per package, subject in the imperative, such as "Add the System, Light, Dark color scheme setting". Nothing is pushed.
  • Running packages side by side. WP5 through WP9 create disjoint files, so they can be written in parallel. They share one build directory and one gallery, so build and review them one at a time in the order shown.

What "matches the prototype" means

  • Colors equal the token values in section 5. Sample a pixel when in doubt: magick shot.png -format "%[hex:u.p{120,80}]" info:.
  • Shape: corner radius, border weight, and shadow softness look the same as the prototype at the same zoom.
  • Metrics are within 2 px of section 7. Qt lays out text with its own font metrics, so a button can be a pixel or two wider than its HTML counterpart.
  • States: rest, hover, pressed, checked, disabled, and keyboard focus each differ visibly from the others.
  • Both modes, always. A control checked in one mode only counts as unchecked.

11. Background

Why a style module. Qt offers three routes: per-instance customization, a custom style module, and the new Qt.labs.StyleKit. The style module is the stable public mechanism and restyles about 340 QML files with zero edits to them. StyleKit is a labs API in Qt 6.11 and leaves out Menu, MenuItem, MenuBar, Dialog, DialogButtonBox, ToolTip, RoundButton, Drawer, and SplitView. If it matures, the tokens carry over and only the per-control files would be replaced.
