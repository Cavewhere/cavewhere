Degrees, Minutes and Seconds for Fix Stations

Issue #654. The free-form coordinate field learns to read 46°07'16.1" N and 46 07.268 N alongside the decimal degrees it takes today. A parser change, essentially: the coordinate string is already the only thing stored (ef346e2b), so a coordinate typed in DMS survives save and load with no schema change at all.

The whole feature lives behind one function. cwCoordinateText::parse() (cavewherelib/src/cwCoordinateText.cpp:76) is the only place any coordinate text is read. Everything downstream — cwFixStation, the survex exporter, the diagnostics, the local projection — consumes decimal doubles out of it and never sees the text. Three surfaces are dragged in by consequence, not by design: swapHorizontal(), the validator's messages, and the invariant that readability is independent of axis order.

2. What was decided, and what it rules out

DecisionChoiceWhat it buys
Disambiguation
the core question		 Explicit markers required. A run of numbers is one angle only when it carries ° ' ", a colon, d/deg, or a hemisphere letter. 46 07 16 keeps meaning (46, 7, elev 16m), which is what it means today. Zero regression risk on the legacy forms, and the refusal message has something concrete to teach.
Hemisphere letters Authoritative. N/S marks a latitude, E/W a longitude, whatever position it sits in. 115°35'W, 46°07'N reads correctly. It isn't inferring order from the numbers — the letter is an explicit statement — so the "order is never guessed" rule survives. Bonus: lettered text needs no axis-order prompt at all (§7.3).
Non-geographic rows Refused. An angle on a projected CS, or on a row with no CS at all, is an error with its own message. A wrong coordinate system is a far likelier cause than a user wanting degrees in an easting. Costs one invariant — see §5.
Display Input only. format() keeps writing decimal degrees. Smallest change, and provably drift-free (§6). The FixStationPage cell shows decimal; the editor and the popup re-offer the DMS text as typed.

Two smaller rulings, both narrowing scope on purpose:

500000 E, 4649776 N stays refused

That is ordinary UTM notation, and under EastingNorthing those letters mean easting and northing rather than a hemisphere. Reading them that way is a separate feature with its own unanswered questions — what would W or S mean on a projected grid? So on a projected row a hemisphere letter keeps the rejection it gets today: "Only the elevation can carry a unit." Worth its own issue.

' and " never mean feet and inches

Angle markers are legal only on the horizontal groups, so 1000' as an elevation stays refused and the elevation keeps needing ft. The collision is contained by position rather than by guesswork.

3. The grammar

Today's parse() is a flat scan: one regular expression over numbers, with a check that whatever sits between two matches is a comma or whitespace. It becomes three layers.

tokenize()        numbers, angle markers, hemisphere letters, unit words, gaps
    ↓
group()           numbers assembled into 1-3 number groups
    ↓
readComponents()  groups classified as latitude / longitude / elevation

Markers

RankSpellingsNote
degrees° º d deg º is the masculine ordinal — a common substitution, since ° is awkward to type. d is the survex/PROJ spelling.
minutes' ′Apostrophe and the Unicode prime.
seconds" ″ '' Two apostrophes is what a keyboard gives you when the double-prime isn't reachable.
infix: Position rather than rank: 46:07:16.1. This is how Walls and survex write it, so it is also what a #FIX line copied out of a project file looks like.

Within a group, marker rank must strictly increase. A marker of rank less than or equal to the previous one means a new group started — which is what lets 46°07'16.1" 115°35'56.5" split with no comma between the two angles.

Group boundaries

A new group begins at any of:

  • a comma in the gap;
  • a hemisphere letter closing the previous group (46 07.268 N, 115 35.941 W);
  • a hemisphere letter opening this one, glued or spaced (N46 07 16, N 46 07 16);
  • a marker rank that fails to increase;
  • three numbers already in hand.
The trailing-letter case is the subtle one. In 46 07.268 N nothing between the two numbers says they belong together — the evidence arrives afterwards, as the letter. So a trailing hemisphere letter claims the run of numbers back to the last boundary, up to three of them. This is the same mechanism that makes the issue's degree min.decimal case work without symbols.

Structural rejections

Each of these is a message, not a silent reinterpretation:

  • a sign on the minutes or seconds — only the degrees carry one, and it negates the whole angle;
  • a sign and a hemisphere letter on the same group (-115°35'56" W) — a typo far more often than an intent, and the two can contradict;
  • a fraction on any component followed by another (46°07.5'16");
  • minutes or seconds at 60 or above;
  • two groups claiming the same axis (46°07'N, 115°35'N);
  • a marker or a hemisphere letter on the elevation group;
  • a colon with nothing after it (46:07:16:22) — the colon is the one marker that speaks about what follows rather than about the number it sits on, so a group can't end on one. Added during commit 2: without it, that string read as 46°07' and 16°22' — a coordinate, and not the one anybody typed.

Magnitude is deliberately not checked here. A latitude past 90° or a longitude past 180° already has a reporter — the CS-domain diagnostic from 7d297150 — and two voices on the same complaint is worse than one.

3.1 The property that protects the legacy forms

A group grows past one number only when a marker or a hemisphere letter says so.

This is the load-bearing claim of the whole plan. For any text containing no marker character and no standalone N/S/E/W, grouping is exactly the flat list of numbers parse() produces today — so every current verdict, every current message, and every one of the 60-odd existing test sections is reproduced by construction rather than by hoping the rewrite got it right.

Note what this rules out: commas are not group separators in the marker-free case. They stay what they are today, interchangeable with whitespace. Had grouping split on commas, 46.12113 -115.59902 304m — all spaces, three components, accepted today — would have become a single group of three and broken.

5. The invariant that changes

cwCoordinateText currently documents, and test_cwCoordinateText.cpp:463 asserts by name, that whether text parses is independent of the axis order — the order decides what the numbers mean, never whether they can be read. Geographic-only DMS breaks that: 46°07'16", -115°35'56" reads under LatitudeLongitude and is refused under EastingNorthing.

Three places lean on the old invariant and have to move in the same commit as the rule that breaks it:

PlaceChange
cwCoordinateText.h:203-207
validator doc comment		 Keeps its claim about the unit system — which genuinely cannot change a verdict — and drops the one about order.
cwCoordinateText.cpp:206-209
swapHorizontal's readability probe		 Probes under LatitudeLongitude instead of EastingNorthing. After the change that is the strictly permissive order, and it is also the right order for what swap exists to do: answer a question about a row that was just named geographic.
test_cwCoordinateText.cpp:463
"judges readability, not meaning"		 Loses its order loop, keeps its units loop, and gains the DMS case that shows why: readable under one order, refused under the other.
One message has to serve two situations. parse() receives an AxisOrder, never the CS string, so it cannot tell a UTM row from a row with no coordinate system — axisOrderFor("") collapses both to EastingNorthing. Widening the signature to take the CS would push coordinate-system knowledge into a text parser, so instead one wording covers both:

"Degrees, minutes and seconds are a latitude and longitude. Set this station's coordinate system to a geographic one, or write the coordinate in the units its own system uses."

On a CS-less row that message is the only thing the user sees, which is worth stating plainly: cwFixStationModel::setCoordinateText() refuses before the text reaches the model, so the row never enters the NoSystem state and its diagnostic never gets a turn. This is also a small behavior change beyond DMS — today a CS-less row accepts 1, 2, 3 and stores it as NoSystem; it will still do that, but 46°07', 115°35' it will refuse.

6. Display: why input-only doesn't drift

The two entry surfaces already disagree about what they show, on purpose:

SurfaceShowsWhy
FixStationPage.qml:404-411
table cell		 format() of the parsed numbers So the elevation renders in the project's units. A stored 304m shows as 997.38ft in an imperial project.
FixStationPage.qml:413
the cell's editor		 coordinateText — the stored string An editor opens on the coordinate as it was written.
FixStationPopup.qml:173-181 the stored string It is always an editor; there is no display half.

So a DMS coordinate shows as decimal degrees in the table and as DMS everywhere it can be edited. The thing to verify rather than assume is that this cannot drift the stored value: the editor opens on editValue: coordinateText, not on the cell's rendering, so opening a cell and committing it untouched re-commits the original DMS string, textToStore() returns it unchanged, and setCoordinateText() compares equal and does nothing. A test pins this.

7. Commit sequence

Three commits, reviewed one at a time. The split is chosen so that the risky part — restructuring a parser that 60 test sections depend on — happens in a commit that adds no features and is therefore judged purely on "did anything change?".
