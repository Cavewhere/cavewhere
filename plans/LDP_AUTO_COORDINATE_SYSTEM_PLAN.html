Automatic Local Coordinate System (LDP) DRAFT

Replaces the user-chosen project coordinate system with an automatically derived low-distortion projection (LDP). Dissolves #618 rather than solving it. Builds directly on the fix-station coordinate-string source-of-truth work (commits 7bd98d2…ad2d6c21 on dev_3) — the string stays the only stored form; the LDP is purely derived state downstream of it.

Idempotence guard: if the computed median equals the current origin, do nothing. Threshold analysis: at 50 km a tmerc k₀=1 frame carries ~31 ppm scale error and ~0.4° convergence (below instrument noise), and float32 scene rendering degrades only to ~4–8 mm vertex quantization with cm-scale close-up jitter at worst — no depth-buffer impact (depth precision is eye-space, travels with the camera). Median derivation also halves the worst-case offset for spread-out data. A softer "off-center" trigger was rejected: it reintroduces reload churn for precision gains below the noise floor.

2. The LDP recipe

Derived once at anchor time from the anchor's position (lat₀, lon₀) and datum:

+proj=tmerc +lat_0=<lat₀> +lon_0=<lon₀> +k_0=1 +x_0=0 +y_0=0
+datum=<from first input: LAZ header datum, else WGS84> +units=m +no_defs +type=crs

Properties this buys, all consequences of the origin sitting on the data:

  • Convergence ≈ 0 at the origin (exactly 0 on the central meridian); ~0.14° at 15 km, ~0.4° at 45 km — applied internally, never shown (D3).
  • Scale distortion: ~1 ppm at 10 km, ~11 ppm at 30 km, ~120 ppm at 100 km (1 ppm = 1 mm/km). UTM's designed worst case is ~400 ppm.
  • Small coordinates → float32-safe on the GPU with no offset hacks; worldOrigin becomes unnecessary (§3).
  • Analytic + invertible via the persisted PROJ string — any point round-trips to lat/long/h exactly, which is the single load-bearing requirement for the future VadoseEarth globe morph (§8).

3. Current architecture → target

Today cwGeoReference (owned by cwCavingRegion) bundles two things: a user-or-auto globalCoordinateSystem string and a worldOrigin offset (with an explicitlySet flag) that translates scene-local points into that CS. cwCavingRegion::recomputeWorldOrigin() averages the fixes (skipping outliers) and re-arms on CS change; cwLazLayerModel auto-adopts a LAZ's CS + bbox center into an empty project (covered by test_cwLazLayerAutoAdoptCS.cpp and test_cwCavingRegion_worldOrigin.cpp).

The target collapses the pair into one value. The LDP is the origin — scene-local coordinates are LDP coordinates directly:

On load, always use the persisted string — never re-derive at load time (two machines with different PROJ data must not disagree, and determinism matters for tests and Git sync). Every state transition in §4 writes the new string transactionally with the edit that caused it, so undo restores the identical LDP. It is a stored value that changes on events, never a live function of the data.

4. When the LDP updates — the state machine

Three states. Anchor = the identity (not the value) of the first georeferenced input: the first fix station whose coordinate is readable (state() == Valid — an Unreadable/NoSystem row must never anchor), or the first LAZ layer with a CRS. Threshold R = 50 km (proposed; scale error there ≈ 30 ppm, and real mistakes — zone errors, hemisphere flips — are always far larger).

Worked mistake scenarios

Entrance refined by 3 m after lidar loadedAnchor edited ≤ R → LDP untouched, zero churn. (S1 gray loop)

5. Vertical datum (D5, explained)

Two different "zero elevation" surfaces exist:

  • The ellipsoid — the smooth mathematical WGS84 surface. GPS chips measure height above this.
  • The geoid — the bumpy mean-sea-level surface. Lidar (NAVD88), topo maps, and Google Earth's displayed altitude are heights above this.

They disagree by the local geoid separation N — roughly −30 m in the eastern US. CaveWhere's z axis is geoid height, adopted from whatever the lidar declares; typed elevations are assumed to be the same kind. We never convert z to ellipsoidal height — doing so would shift the whole project ~30 m and disagree with every typed elevation.

PROJ trap: never request a 3D compound transform
Handing PROJ the lidar's full compound CRS (e.g. "NAD83 / KY single zone + NAVD88 height") with a 3D target will make it apply the geoid model and return ellipsoidal heights — silently, and only on machines where the geoid grids happen to be installed. Build the transform from the horizontal CRSs only; handle z as a pure unit scale (US survey ft → m). This matches what the existing project-CS reprojection implicitly does.

What we record (not apply): the lidar's vertical-datum name from the LAZ header, stored on the geo-reference. That single string is the bridge a future globe renderer needs to reconstruct ellipsoidal height (h = H + N) for ECEF placement (§8). Optionally cache N₀ at the origin when geoid grids are available. Mixed vertical datums across tiles (NAVD88 vs NGVD29, ~0.3 m) are detectable from headers → import-time notice, deferred.

8. VadoseEarth openness (future, design-only)

VadoseEarth is an ECEF WGS84 globe engine (EarthEllipsoid, Geodetic3D, high/low float split). The globe↔LDP zoom morph is proven technique (Cesium's 3D↔Columbus morph; Google Maps globe↔Mercator): both worlds map analytically from (lat, lon, h), and a per-vertex blend between the two mappings is a smooth deformation. Requirements this plan must preserve — all already satisfied by the design above:

  1. LDP analytic + invertible via the persisted PROJ string (§3).
  2. Vertical-datum name recorded so ellipsoidal height is recoverable (§5).
  3. One frozen origin per project = the tangent point (§4).
  4. Doubles on CPU interchange types (both projects use QDoubleVector3D).

Half landed: the anchoring

  • Distance is measured in the current frame: with x_0 = y_0 = 0 a point's distance from the origin is just its magnitude once transformed into the LDP, so "did the anchor move more than R" needs no second derivation.
  • Only witnessed disappearances count as deletions. Statement order inside setData is no longer load-bearing.
  • Inputs are enumerated by one gatherInputs() returning a QList<Input>, in a fixed order so the frame doesn't depend on load timing. Gathering every input on every call is cheap enough for a keystroke in a coordinate field: isValidCS memoizes the PROJ database lookup per thread, so per input it is a hash lookup.

10. Cache ownership refactor (decided 2026-08-03, sequenced before P2.2, part B revised 2026-08-03)

cwLocalProjectionManager carries three kinds of member state. Only one of them belongs there:

StateWhat it isVerdict
m_anchorSeen / m_lastAnchor / m_sawAnyInput Witness bookkeeping — "not loaded yet" vs. "deleted" is not derivable from current inputs. Keep. Irreducible session state; the only data the manager should own.
m_transform + m_transformSourceCS + m_transformLocalCS Single-slot cache of a built PROJ transform (~7.7 ms per build, keystroke path). Move down into cwCoordinateTransform as a memoized static — part A below. That class already memoizes isValidCS and isGeographic in capped thread-local caches; construction — the most expensive PROJ call of all — is the inconsistency. Other data sources will use cwCoordinateTransform too, so the memo pays for every future caller, and the keyed cache kills the single-slot thrash in the anchor-deleted any_of walk for free.
m_layerProbes + probe() Cache of cwLazLoader::probeHeader() results, keyed by layer id. Delete — part B below. The loader already reads every one of these facts while decoding; the layer keeps them from the load and the probe cache goes away entirely, taking the id-keying, the pruning pass, the "never remember a pointer" discipline, and a live staleness bug (see the callout) with it.
Live bug fixed by part B: probe() caches a derived value
cwLocalProjectionManager.cpp:166 writes the user's sourceCSOverride into the cached entry, overwriting the header's own reading. Set an override, then clear it: sourcePath is unchanged so the header is not re-probed, the override branch no longer fires, and the cache returns the old override as if it were the file's own CS — permanently, until the path changes. Part B's revised design removes the bug rather than patching it: the resolved CS comes from the load, which recomputes it from the override every time it runs, so there is no stored derived value anywhere to go stale.

End state: the manager keeps m_region plus the three witness fields — nothing mutable, no caches, pure policy. Part A moves a cache down to the class that should own it; part B deletes a cache outright because the data was never missing, only unpublished. They are independent; land them as two separate commits, each green on the tagged tests before the next. (Note: cwGridConvergence also builds an uncached transform per keystroke at cwGridConvergence.cpp:186; do not port it to part A — the whole display path is deleted in P6.)

Part A — cwCoordinateTransform::transformPoint (memoized static)

A1. API — in cwCoordinateTransform.h, next to the other statics (isValidCS/isGeographic). Add #include <optional> to the header's Qt/std include block.

/**
 * Transform a point between two systems, memoizing the built transforms
 * per thread (same pattern and cap as isValidCS). Empty when either CS is
 * empty, the systems can't be related, or the result's x/y isn't finite —
 * an unanswerable question must not read as an answer. z passes through
 * untouched by the finiteness check.
 */
static std::optional<cwGeoPoint> transformPoint(const QString& sourceCS,
                                                const QString& destCS,
                                                const cwGeoPoint& point);

A2. Implementation — in cwCoordinateTransform.cpp, near isValidCS. Constraints that matter:

  • The memo must be thread_local std::map<std::pair<QString, QString>, cwCoordinateTransform>, not QHash. cwCoordinateTransform is move-only with no default constructor (cwCoordinateTransform.h:42), which QHash can't hold; std::map::try_emplace(key, src, dst) constructs the value in place. QString already has operator<. Thread-local also honors the class's "one transform, one thread" contract.
  • Trim both CS strings first; if either is empty, return std::nullopt without touching the memo.
  • Reuse the existing kCsCacheLimit (anonymous namespace, same file): when map.size() >= kCsCacheLimit, clear() before inserting. Nothing escapes the memo (the point is returned by value), so a full clear is safe.
  • Invalid transforms are cached too — negative caching. A pair that fails to build must not re-pay the build cost on every keystroke. A memo hit whose isValid() is false returns std::nullopt.
  • After transforming, return std::nullopt unless std::isfinite holds for x and y (only those two — matches the behavior being replaced).

A3. Caller rewrite — cwLocalProjectionManager::distanceFromOrigin collapses to:

std::optional<double> cwLocalProjectionManager::distanceFromOrigin(const Input& input) const
{
    const QString localCS = m_region->geoReference()->localCoordinateSystem();
    if (localCS.isEmpty()) {
        return std::nullopt;
    }
    const auto local = cwCoordinateTransform::transformPoint(
        input.coordinateSystem, localCS, input.point);
    if (!local.has_value()) {
        return std::nullopt;
    }
    // x_0 = y_0 = 0, so a point's distance from the frame's origin is just its
    // magnitude once it is in the frame.
    return std::hypot(local->x, local->y);
}

A4. Deletions — from cwLocalProjectionManager.h: the three members m_transform / m_transformSourceCS / m_transformLocalCS with their doc comment, and the #include "cwCoordinateTransform.h" (the .cpp already includes it and keeps it).

A5. Tests — new cases in test_cwCoordinateTransform.cpp under the existing [cwCoordinateTransform] tag: a known UTM→WGS84 point round-trips through transformPoint; empty source or dest → nullopt; garbage CS → nullopt (call twice — the second call exercises the negative-cache path); identical src/dst returns the point unchanged (identity short-circuit). The existing [cwLocalProjectionManager] cases must stay green untouched — behavior is unchanged by design.

Part B — the header's facts ride the load revised 2026-08-03

Supersedes the probe-cache design
Part B was originally specified as a lazily probed, fingerprint-keyed cwLazLoader::ProbeResult cached on cwLazLayer. That was still a cache of something the loader already knows. cwLazLoadResult::sourceCS is already the resolved CS (override > embedded > "", cwLazLoader.cpp:275) — byte-for-byte what the probe recomputed. The only fact the load did not carry was the bounding box in the file's own CRS, because bboxMin/bboxMax are written after transformInPlace into the region frame and narrowed to float. So the fix is to widen the load's result, not to cache a second read of the same header.

B1. cwLazLoadResult carries the source-CRS bbox. Two cwGeoPoints, sourceBboxMin / sourceBboxMax, filled from headerReader->header.min_x…max_z during the header pass the load already performs (cwLazLoader.cpp:263–278). Doubles, untransformed. Free — the header is open at that point either way.

B2. cwLazLayer stores them from applyResult as m_sourceBboxMin/m_sourceBboxMax, exposed as sourceBboxMin()/sourceBboxMax()/sourceBboxCenter(). No mutable, no lazy probe, no fingerprint key, no invalidation rule — the value is written by the one event that can change it.

B3. The manager gates on a finished load. A layer is an anchor candidate only when loadStatus() == Loaded and its sourceCS() is valid; the point is sourceBboxCenter(). cwLocalProjectionManager also connects loadStatusChanged — sourceCSChanged alone misses a reload that resolves to the same CS it had before.

11. Follow-ups from the P2.2 simplify pass (2026-08-04)

A four-angle review (reuse / simplification / efficiency / altitude) ran over the P2.2 working tree. Most findings were applied in place — see the list at the end of this section. Four were deliberately not applied, because they are behavior or architecture changes rather than cleanups. They are recorded here so they aren't lost.

F1 — The LAZ bootstrap anchors from outside cwLocalProjectionManager

cwLazLayerModel::deriveFrameFromLaz calls cwLocalProjection::deriveFrom + cwGeoReference::anchorTo itself, duplicating cwLocalProjectionManager::anchorTo — after this phase those are the only two production callers of anchorTo. The manager documents itself as the single owner of how the frame moves, and this write bypasses it, so the manager's witness bookkeeping (m_lastAnchor, m_anchorSeen) is not updated. Two consequences, both found by reading rather than by a failing test:

  • evaluate() misreads the model's own write as "a load restored this anchor". Self-heals once the layer reaches Loaded and appears in gatherInputs(), so it is latent today.
  • The real one: deriveFrameFromLaz runs regardless of the layer's enabled bit, while gatherInputs() only accepts LoadStatus::Loaded. A disabled layer can therefore become the project's anchor but can never be an Input — so m_anchorSeen stays false and clearFrame() is unreachable for it. That violates the "only witnessed deletions count" invariant this plan's §4 rests on.

Reachability (re-verified 2026-08-04): narrower than the paragraph above sounds. deriveFrameFromLaz only anchors when the geo-reference has no coordinate system, and a layer that is disabled at insert time means a persisted .cwlaz with enabled=false — so the bad state needs an ungeoreferenced project that already carries a persisted, disabled, CRS-bearing layer (e.g. anchor fix deleted → frame cleared → save → reopen). Re-enabling the layer self-heals it: the load lands, the layer appears in gatherInputs(), and m_anchorSeen flips true. The invariant violation holds only while the layer stays disabled until its deletion.

Fix (the deeper one): have cwLazLayer::setSourcePath run the header-only probeHeader and publish sourceCS / sourceBboxCenter as soon as it lands, plus a Probed status that gatherInputs() accepts alongside Loaded. The model then does no anchoring at all, one class owns the frame, and the enabled/loaded disagreement disappears. This is the principled way to break the D15 bootstrap cycle — D15's current shape was the expedient one.

Design revised 2026-08-04, after reading both probe paths. Two corrections to the paragraph above, which originally said "run probeHeader synchronously":

  • Every layer has to be probed, and the reason is deletion detection, not anchoring. Anchoring needs only one usable input, so a first-match probe would do. But evaluate() also asks two questions about the whole set: inputs.isEmpty() → clearFrame(), and the somethingNearby std::any_of that decides between freezeFrame() and re-anchoring. Both are set-membership tests, and a partially probed set makes both answer "no" spuriously — which clears or re-derives a frame that was stored precisely so it would never have to be. Universality is forced by §4's "only witnessed deletions count" invariant.
  • So the probe must not be synchronous. Today it is rare: deriveFrameFromLaz returns before probing once hasCoordinateSystem() is true, so N tiles probe once if any of them carries a CRS. Making it universal and synchronous would put N header opens on the GUI thread — turning F2's secondary complaint from a corner case into the normal path. An async probe with a Probed status costs nothing on the GUI thread and reaches layers the current design can't: a layer disabled in its .cwlaz never starts a load at all (cwLazLayerModel.cpp:415), which is the whole mechanism behind F1's invariant violation and V1's.
F2 — Frame derivation inside the rescan insert loop restarts in-flight decodes

cwLazLayerModel::rescan() derives the frame per file, inside the loop that inserts layers. Anchoring emits localProjectionChanged → setRegionFrameCS → reload() on every layer already in m_layers — including ones whose decode started earlier in the same rescan. Triggers on a mixed multi-file add where the first file carries no usable CRS and a later one does: a 100M-point tile already being read is cancelled and re-decoded, and for a CRS-less source the second decode is byte-identical. Secondary: the probe guard is per-file rather than per-rescan, so a directory of N CRS-less tiles opens N LAZ headers on the GUI thread.

Fix: establish the frame once before the insert loop (what the pre-P2.2 code did with maybeAdoptRegionDefaultsFromLaz(entries.first())), or skip the reload when the layer's own sourceCS is empty. Naturally folded into F1.

Status check 2026-08-04: still entirely live. Introducing cwLocalProjectionManager did not supersede this path — deriveFrameFromLaz (cwLazLayerModel.cpp:526-556) still calls cwGeoReference::anchorTo at :555, from the rescan insert loop at :448, so two classes hold authority over one frame. It is benign only by call ordering: the model anchors before endInsertRows, so the manager's first evaluate() reads an anchor it didn't write, drops m_anchorSeen to false, and returns at the not-seen-yet guard (:228) instead of acting on it. That is the hazard the comment at cwLocalProjectionManager.cpp:168 warns about, arriving from outside the class. F1 retires this half. The secondary half — N header opens on the GUI thread — F1 retires only if its probe is async; a synchronous one makes it worse. See F1's revised design.

F3 — *cs CUSTOM "…" is write-only fixed in 13.1

P2.2 added toSurvexCS(), which quotes a raw PROJ string behind survex's CUSTOM keyword. There is no inverse: cwSurvexImporter::parseCS stores the *cs argument verbatim, so importing a .svx that CaveWhere itself exported puts the literal string CUSTOM "+proj=…" into cwFixStation::inputCS. PROJ can't parse that — isValidCS is false, gatherInputs() skips the fix, and the picker shows nothing.

Fix: a fromSurvexCS() in the importer that unwraps CUSTOM "…", making the pair a real encoding rather than a one-way escape. Small and self-contained; belongs with P5's export work.

F4 — anchorToFirstUsable() has no failure memo

Each rejected input re-pays a full cwLocalProjection::deriveFrom (two PROJ contexts, ~6 proj_create* calls). Bounded before D18, unbounded after. Low priority: it runs only on the two re-anchor branches of evaluate(), never the common Anchored path. A QSet<QString> of already-failed CS strings caps it.

12. Code-review findings on the P2.2 working tree (2026-08-04)

A correctness-focused review ran over the uncommitted P2.2 tree (three reviewers split by area, findings re-verified against the code before recording). The QML tree and the rewritten tests came back clean — no dangling references to removed API, no weakened tests. F1–F4 above were adversarially re-checked and all four hold; F1 gained the reachability paragraph in its callout. Six new findings, none applied yet — V1 and V2 are the ones that bite:

V1 — A witnessed LAZ anchor that transiently leaves Loaded is treated as deleted

gatherInputs() only accepts LoadStatus::Loaded, and its comment promises m_anchorSeen protects a disabled/loading layer from being read as deleted — but it only protects a never-witnessed anchor. Once the anchor layer has been seen, any synchronous drop out of Loaded looks like deletion: setSourceCSOverride / setEnabled / setRegionFrameCS call reload(), which emits loadStatusChanged(Loading) before the load starts, and that signal runs evaluate() mid-reload. With fix stations near the origin the Anchored branch hits freezeFrame() — and Frozen never re-anchors, so a CS correction on the anchor layer silently orphans the frame for good. With no other inputs it hits clearFrame() → the region pushes an empty frame → the in-flight load restarts untransformed → re-anchor → third reload: converges, but the project is transiently un-georeferenced and pays two extra full point loads. No test reloads or disables a witnessed LAZ anchor.

Fix direction: the evaluate triggered by a status change to Loading must not treat the absent anchor as deleted — e.g. gather layers by "has a probed header" rather than "load finished" (the F1 deeper fix covers this too), or have evaluate() ignore an anchor layer whose status is Loading.

Confirmed retired by F1's revised design (2026-08-04). Once the header numbers are published on their own — and stay published across a reload, because a reload re-reads points, not the CRS — a layer never leaves the input set for a transient Loading. There is no absence to misread, so V1 needs no separate fix and should be closed by F1 rather than patched ahead of it.

V2 — WorkingFrame solve regression for fixes whose CS only survex understands fixed in 13.1

A fix entered under a survex-keyword spelling (UTM16N, S-MERC — the exact round-trip the shareableCSForFix fallback exists for, since parseCS stores *cs verbatim) is Valid (its coordinate parses) but PROJ-invalid, so gatherInputs() skips it and no LDP ever derives. V3 — toSurvexCS cannot represent a CS containing a double quote

Survex's quoted-string reader has no escape syntax, so CUSTOM "PROJCS["…"]" truncates at the first embedded quote and cavern parses garbage. WKT always contains quotes, and WKT is reachable both as a fix inputCS (the custom dialog accepts anything PROJ parses) and as the frame itself (cwLocalProjection::derive's WKT fallback — the very case the bare-name test was built for quotes it, but quoting truncates it). 13. Importers normalize the coordinate system (settled 2026-08-04)

Decision: an importer converts its format's coordinate-system spelling into one PROJ can parse, or into none at all. cwFixStation::inputCS then carries a single invariant — a PROJ string, or empty — instead of the two incompatible contracts it grew: "any survex spelling" for the writer, "a PROJ string" for every reader. V2 is where those two met, and V5's verbatim fallback exists only to accommodate the un-normalized form.

The premise the survex importer records at cwSurvexImporter.cpp:1055 — "the rest of the pipeline (export, picker) handles those forms downstream" — is false for both handlers it names. cwCoordinateTransform's parseCS recognizes only EPSG:4326 and EPSG:326xx/327xx, so the picker shows "Custom…" for what is plainly UTM zone 16 North; and P2.2 added a third consumer, the LDP anchor path, which silently skips anything PROJ can't read.

Walls half — DONE 2026-08-04

cwWallsImporter wrote EPSG:26900 as a deliberate "pick your zone" placeholder. PROJ rejects it ("crs not found") and so does cavern, so it poisoned the solve both before and after P2.2. The datum and zone were available the whole time: dewalls parses the project's .REF line into GeoReference (zone signed positive-north, datumName), and WpjEntry::reference() already inherits it from the parent book — cwWallsImporter::convertEntry was discarding it with a "can't currently be imported" warning.

The datum-name-to-CRS mapping is survex's own, reused rather than reinvented: img_parse_compass_datum_string / img_compass_utm_proj_str / img_compass_longlat_epsg_code from img.h, which cavewherelib already links. Traps

OSGB's letters are a false origin, not a CRS variant. The square shifts x_0/y_0 in 100 km steps, so OSGB:SD is not EPSG:27700 — coordinates under it are offsets within that square. Decode as cavern does (:2637–2645): from the letter pair build x, y, then x_0 = (14 - x) × 100000 and y_0 = (y - 20) × 100000. Checkable: this yields x_0=400000, y_0=-100000 for OSGB:SV, which is exactly EPSG:27700 — so OSGB:SV ≡ EPSG:27700 makes a good test.

Axis order rides on the CS string. cwCoordinateText::axisOrderFor is isGeographic(cs) ? LatitudeLongitude : EastingNorthing, and cwFixStation re-reads its stored coordinate text under whatever the current CS implies. So rewriting the CS silently reinterprets the numbers. The swap goes the way the struct comment says, not the way an earlier draft of this paragraph did: cwFixStation::setCoordinate takes easting (longitude) first whatever the system, so LONG-LAT — which survex already writes longitude first — passes straight through, and LAT-LONG is the one whose pair transposes. Getting this backwards puts the cave in the wrong hemisphere, and nothing downstream can detect it.

A geographic CS can't be *cs out. Cavern calls proj_get_type and rejects PJ_TYPE_GEOGRAPHIC_2D_CRS/_3D_CRS with error 435 (:2700–2707). So normalizing a fix to EPSG:4326 makes it a fine input and still an unusable output — which is what shareableCSForFix's existing "leave it to the next fix" comment is about. Don't let step 4's cleanup weaken that.
