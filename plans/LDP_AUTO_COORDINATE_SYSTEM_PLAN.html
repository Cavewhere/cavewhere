2. The LDP recipe

Derived once at anchor time from the anchor's position (lat₀, lon₀) and datum:

+proj=tmerc +lat_0=<lat₀> +lon_0=<lon₀> +k_0=1 +x_0=0 +y_0=0
+datum=<from first input: LAZ header datum, else WGS84> +units=m +no_defs +type=crs

Properties this buys, all consequences of the origin sitting on the data:

  • Convergence ≈ 0 at the origin (exactly 0 on the central meridian); ~0.14° at 15 km, ~0.4° at 45 km — applied internally and shown on the cave page at three decimals (D3).
  • Scale distortion: ~1 ppm at 10 km, ~11 ppm at 30 km, ~120 ppm at 100 km (1 ppm = 1 mm/km). UTM's designed worst case is ~400 ppm.
  • Small coordinates → float32-safe on the GPU with no offset hacks; worldOrigin becomes unnecessary (§3).
  • Analytic + invertible via the persisted PROJ string — any point round-trips to lat/long/h exactly, which is the single load-bearing requirement for the future VadoseEarth globe morph (§8).

3. Current architecture → target

Today cwGeoReference (owned by cwCavingRegion) bundles two things: a user-or-auto globalCoordinateSystem string and a worldOrigin offset (with an explicitlySet flag) that translates scene-local points into that CS. cwCavingRegion::recomputeWorldOrigin() averages the fixes (skipping outliers) and re-arms on CS change; cwLazLayerModel auto-adopts a LAZ's CS + bbox center into an empty project (covered by test_cwLazLayerAutoAdoptCS.cpp and test_cwCavingRegion_worldOrigin.cpp).

4. When the LDP updates — the state machine

Three states. Anchor = the identity (not the value) of the first georeferenced input: the first fix station whose coordinate is readable (state() == Valid — an Unreadable/NoSystem row must never anchor), or the first LAZ layer with a CRS. Threshold R = 50 km (proposed; scale error there ≈ 30 ppm, and real mistakes — zone errors, hemisphere flips — are always far larger).

5. Vertical datum (D5, explained)

Two different "zero elevation" surfaces exist:

  • The ellipsoid — the smooth mathematical WGS84 surface. GPS chips measure height above this.
  • The geoid — the bumpy mean-sea-level surface. Lidar (NAVD88), topo maps, and Google Earth's displayed altitude are heights above this.

They disagree by the local geoid separation N — roughly −30 m in the eastern US. CaveWhere's z axis is geoid height, adopted from whatever the lidar declares; typed elevations are assumed to be the same kind. We never convert z to ellipsoidal height — doing so would shift the whole project ~30 m and disagree with every typed elevation.

PROJ trap: never request a 3D compound transform
Handing PROJ the lidar's full compound CRS (e.g. "NAD83 / KY single zone + NAVD88 height") with a 3D target will make it apply the geoid model and return ellipsoidal heights — silently, and only on machines where the geoid grids happen to be installed. Build the transform from the horizontal CRSs only; handle z as a pure unit scale (US survey ft → m). This matches what the existing project-CS reprojection implicitly does.

What we record (not apply): the lidar's vertical-datum name from the LAZ header, stored on the geo-reference. That single string is the bridge a future globe renderer needs to reconstruct ellipsoidal height (h = H + N) for ECEF placement (§8). Optionally cache N₀ at the origin when geoid grids are available. Mixed vertical datums across tiles (NAVD88 vs NGVD29, ~0.3 m) are detectable from headers → import-time notice, deferred.

8. VadoseEarth openness (future, design-only)

VadoseEarth is an ECEF WGS84 globe engine (EarthEllipsoid, Geodetic3D, high/low float split). The globe↔LDP zoom morph is proven technique (Cesium's 3D↔Columbus morph; Google Maps globe↔Mercator): both worlds map analytically from (lat, lon, h), and a per-vertex blend between the two mappings is a smooth deformation. Requirements this plan must preserve — all already satisfied by the design above:

  1. LDP analytic + invertible via the persisted PROJ string (§3).
  2. Vertical-datum name recorded so ellipsoidal height is recoverable (§5).
  3. One frozen origin per project = the tangent point (§4).
  4. Doubles on CPU interchange types (both projects use QDoubleVector3D).

10. Cache ownership refactor (decided 2026-08-03, sequenced before P2.2, part B revised 2026-08-03)

cwLocalProjectionManager carries three kinds of member state. Only one of them belongs there:

Part A — cwCoordinateTransform::transformPoint (memoized static)

A1. API — in cwCoordinateTransform.h, next to the other statics (isValidCS/isGeographic). Add #include <optional> to the header's Qt/std include block.

/**
 * Transform a point between two systems, memoizing the built transforms
 * per thread (same pattern and cap as isValidCS). Empty when either CS is
 * empty, the systems can't be related, or the result's x/y isn't finite —
 * an unanswerable question must not read as an answer. z passes through
 * untouched by the finiteness check.
 */
static std::optional<cwGeoPoint> transformPoint(const QString& sourceCS,
                                                const QString& destCS,
                                                const cwGeoPoint& point);

A2. Implementation — in cwCoordinateTransform.cpp, near isValidCS. Constraints that matter:

  • The memo must be thread_local std::map<std::pair<QString, QString>, cwCoordinateTransform>, not QHash. cwCoordinateTransform is move-only with no default constructor (cwCoordinateTransform.h:42), which QHash can't hold; std::map::try_emplace(key, src, dst) constructs the value in place. QString already has operator<. Thread-local also honors the class's "one transform, one thread" contract.
  • Trim both CS strings first; if either is empty, return std::nullopt without touching the memo.
  • Reuse the existing kCsCacheLimit (anonymous namespace, same file): when map.size() >= kCsCacheLimit, clear() before inserting. Nothing escapes the memo (the point is returned by value), so a full clear is safe.
  • Invalid transforms are cached too — negative caching. A pair that fails to build must not re-pay the build cost on every keystroke. A memo hit whose isValid() is false returns std::nullopt.
  • After transforming, return std::nullopt unless std::isfinite holds for x and y (only those two — matches the behavior being replaced).

A3. Caller rewrite — cwLocalProjectionManager::distanceFromOrigin collapses to:

std::optional<double> cwLocalProjectionManager::distanceFromOrigin(const Input& input) const
{

A four-angle review (reuse / simplification / efficiency / altitude) ran over the P2.2 working tree. Most findings were applied in place — see the list at the end of this section. F1 — The LAZ bootstrap anchors from outside cwLocalProjectionManager probe landed 2026-08-05

cwLazLayerModel::deriveFrameFromLaz calls cwLocalProjection::deriveFrom + cwGeoReference::anchorTo itself, duplicating cwLocalProjectionManager::anchorTo — after this phase those are the only two production callers of anchorTo. The manager documents itself as the single owner of how the frame moves, and this write bypasses it, so the manager's witness bookkeeping (m_lastAnchor, m_anchorSeen) is not updated. Two consequences, both found by reading rather than by a failing test:

  • evaluate() misreads the model's own write as "a load restored this anchor". Self-heals once the layer reaches Loaded and appears in gatherInputs(), so it is latent today.
  • The real one: deriveFrameFromLaz runs regardless of the layer's enabled bit, while gatherInputs() only accepts LoadStatus::Loaded. A disabled layer can therefore become the project's anchor but can never be an Input — so m_anchorSeen stays false and clearFrame() is unreachable for it. That violates the "only witnessed deletions count" invariant this plan's §4 rests on.

Reachability (re-verified 2026-08-04): narrower than the paragraph above sounds. deriveFrameFromLaz only anchors when the geo-reference has no coordinate system, and a layer that is disabled at insert time means a persisted .cwlaz with enabled=false — so the bad state needs an ungeoreferenced project that already carries a persisted, disabled, CRS-bearing layer (e.g. anchor fix deleted → frame cleared → save → reopen). Re-enabling the layer self-heals it: the load lands, the layer appears in gatherInputs(), and m_anchorSeen flips true. The invariant violation holds only while the layer stays disabled until its deletion.

Fix (the deeper one): have cwLazLayer::setSourcePath run the header-only probeHeader and publish sourceCS / sourceBboxCenter as soon as it lands, plus a Probed status that gatherInputs() accepts alongside Loaded. The model then does no anchoring at all, one class owns the frame, and the enabled/loaded disagreement disappears. This is the principled way to break the D15 bootstrap cycle — D15's current shape was the expedient one.

Design revised 2026-08-04, after reading both probe paths. Two corrections to the paragraph above, which originally said "run probeHeader synchronously":

  • Every layer has to be probed, and the reason is deletion detection, not anchoring. Anchoring needs only one usable input, so a first-match probe would do. But evaluate() also asks two questions about the whole set: inputs.isEmpty() → clearFrame(), and the somethingNearby std::any_of that decides between freezeFrame() and re-anchoring. Both are set-membership tests, and a partially probed set makes both answer "no" spuriously — which clears or re-derives a frame that was stored precisely so it would never have to be. Universality is forced by §4's "only witnessed deletions count" invariant.
  • So the probe must not be synchronous. Today it is rare: deriveFrameFromLaz returns before probing once hasCoordinateSystem() is true, so N tiles probe once if any of them carries a CRS. Making it universal and synchronous would put N header opens on the GUI thread — turning F2's secondary complaint from a corner case into the normal path. An async probe with a Probed status costs nothing on the GUI thread and reaches layers the current design can't: a layer disabled in its .cwlaz never starts a load at all (cwLazLayerModel.cpp:415), which is the whole mechanism behind F1's invariant violation and V1's.

Implemented 2026-08-05 (the probe half). cwLazLayer now runs cwLazLoader::probeHeader off the GUI thread from setSourcePath and setSourceCSOverride, on its own AsyncFuture::Restarter so results arrive in the order they were asked for, and on the global thread pool rather than cwTask's. That pool choice is scheduled for revert — see §14. Its stated reason was that a header open queued behind a 100-million-point decode would hold up the frame that decode is waiting on; the decodes turn out not to be waiting, because deriveFrameFromLaz orders them behind the frame with a blocking call. Once §14's gate makes that ordering explicit, the probe leaves the critical path and cwConcurrent::run is correct. The result publishes sourceCS (override > embedded, the loader's own precedence) and the source bounding box, sets a new hasReadHeader(), and raises Idle to the new LoadStatus::Probed. setEnabled(false) falls back to Probed rather than Idle, so turning the points off no longer withdraws the layer's position.

gatherInputs() now tests hasReadHeader() in place of loadStatus() == Loaded. A status enumeration would have left Loading and Error out, and those are exactly the transient absences that read as deletions — so this is V1's and V6's fix as much as F1's. Three tests pin it: a disabled layer reads its header and reports Probed; disabling the only layer leaves the frame anchored while removing it clears the frame; and a reload of the anchor layer leaves the frame untouched for the whole of it. The anchoring half — deriveFrameFromLaz, still in cwLazLayerModel — comes out with F2.

F2 — Frame derivation inside the rescan insert loop restarts in-flight decodes

cwLazLayerModel::rescan() derives the frame per file, inside the loop that inserts layers. Anchoring emits localProjectionChanged → setRegionFrameCS → reload() on every layer already in m_layers — including ones whose decode started earlier in the same rescan. Triggers on a mixed multi-file add where the first file carries no usable CRS and a later one does: a 100M-point tile already being read is cancelled and re-decoded, and for a CRS-less source the second decode is byte-identical. Secondary: the probe guard is per-file rather than per-rescan, so a directory of N CRS-less tiles opens N LAZ headers on the GUI thread.

Fix: establish the frame once before the insert loop (what the pre-P2.2 code did with maybeAdoptRegionDefaultsFromLaz(entries.first())), or skip the reload when the layer's own sourceCS is empty. Naturally folded into F1.

Status check 2026-08-04: still entirely live. 14. The LAZ load chain — what F2 actually removes (settled 2026-08-05)

F1's async probe landed (§11). The follow-up question was whether the probe needed to be faster — it runs on the global thread pool rather than cwTask's, which is a departure from house style — and answering that turned up a bigger finding: the blocking probe F2 deletes is currently the only thing that orders the frame ahead of the decode, and the only thing that makes the anchor deterministic. F2 was written as a tidy-up ("one class owns the frame"). It is really a scheduling change, and it needs a replacement mechanism, not just a deletion. The replacement, settled on review: an epoch future — cwLocalProjectionManager::frameFuture() — plus a gate on the manager's own anchor path.

What the synchronous probe is actually doing

cwLazLayerModel::rescan(), at cwLazLayerModel.cpp:447-458:

// The load below has to have somewhere to load into, and on a project
// with no fix stations this layer is the only thing that can say where
// that is.

layer->setRegionFrameCS(m_regionFrameCS);
...
layer->setSourcePath(path);   // starts the load

deriveFrameFromLaz runs cwLazLoader::probeHeader synchronously on the GUI thread, derives the frame and anchors it, and only then does setSourcePath start the decode. That comment is the dependency edge, written in prose.

Confirmed by measurement, not by reading. Running the [cwLazSourceBbox] tag with QT_LOGGING_RULES="cw.laz.layer.debug=true" prints reload()'s frameCSSet flag. Every model-managed layer reports frameCSSet= true on its first reload. The only false in the run belongs to a bare cwLazLayer constructed with no region at all — not a bootstrap. So the earlier suspicion that today's code decodes once into an empty frame and again into the real one is wrong: there is no wasted decode, precisely because of the blocking call.

The determinism invariant nobody wrote down

cwLocalProjectionManager::evaluate() is connected to every layer's sourceCSChanged (cwLocalProjectionManager.cpp:316), and on the Ungeoreferenced path it calls anchorToFirstUsable(inputs) — the first usable input in gatherInputs() order among the layers that hold a header at that instant.

Today the synchronous probe guarantees exactly one layer has a header when the frame is derived, and it is the first in rescan order. Make the probes async without a barrier and the anchor becomes whichever header read wins the race. The derived projection is then a function of disk timing — and it is persisted, into a Git-backed .cwproj. Two people importing the same directory get different frames, different scene coordinates, and a diff that looks like real work.

And the gate must live inside evaluate(). An earlier draft had the model "drive one evaluate() per batch" — not enough. evaluate() has other callers that fire mid-batch: the model's rowsInserted/rowsRemoved/modelReset (cwLocalProjectionManager.cpp:51-53), fix-station dataChanged (:293), caveCountChanged (:37), and each layer's loadStatusChanged (:321). Any of them would anchor from the landed subset. So the Ungeoreferenced path defers anchorToFirstUsable while the epoch is open, and every existing connection stays.

Invariant to add to §4: the anchor may depend on the set of inputs and on their order in the model, never on the order in which their I/O completes. This is the sibling of §4's "only witnessed deletions count" and of the stored-not-computed rule in §3 — same motivation, different axis.

The chain

frameFuture() — the epoch future

cwLocalProjectionManager gains one accessor:

QFuture<QString> frameFuture();   // the current epoch's future; value = the settled frameCS

The epoch is open exactly while the frame is Ungeoreferenced and at least one layer probe is in flight. frameFuture() returns the open epoch's pending future, or an already-finished one otherwise — so "settled" has a one-line definition, settled ⇔ the future is finished, and the three cases an earlier draft enumerated collapse into it:

  • Anchored or Frozen → finished, carrying the current frameCS. A tile dropped into a georeferenced project chains on a finished future and decodes immediately — it does not wait for its own probe; the load reads the header itself (read #3 above, kept for exactly this reason).
  • Ungeoreferenced, no probes in flight → finished, carrying an empty string. Empty is a legitimate settled value: the clouds load untransformed, in their own units — exactly what deriveFrameFromLaz's early return promises today.
  • Ungeoreferenced, probes in flight → pending. Decodes chained on it wait.

Getting the second and third cases confused is the failure mode: treat "no frame" as settled and a CRS-bearing project decodes every tile untransformed before its own headers arrive; treat it as unsettled forever and a CRS-less directory never loads at all. The future makes the distinction mechanical, and its completion is the notification — the case a changed-value signal can never deliver, because the settled value may be the same empty string the layer started with.

The future also carries the frame, and that is the only way a layer gets one. An earlier draft pushed the value down separately (setRegionFrameCS) and used the future purely as a "now it's final" bell, which left one fact traveling two channels and an ordering contract between them written only in a comment. Taking the value off the future deletes the second channel, the duplicate m_regionFrameCS member in both the layer and the model, and the contract.

The frame is computed at most once per epoch, because the gate defers all layer-driven anchoring while the epoch is open. An epoch ends one of two ways, and each completes the AsyncFuture::Deferred<QString> behind the future exactly once:

  • The last probe lands → one evaluate() → anchorToFirstUsable over the full set → complete with the result (or the empty string).
  • A fix station anchors mid-epoch → complete early with the fix's frame. Safe because it is order-identical to waiting: gatherInputs() lists fix stations ahead of layers, so the batch-close path would have picked the same fix. A user edit is allowed to decide the anchor; I/O timing is not. So the gate is not "anchor nothing while the epoch is open" but "anchor nothing a header could have decided": the Ungeoreferenced path filters the inputs down to the fix stations and anchors on those, then settles because the frame is no longer Ungeoreferenced.

Epochs extend or complete — they never supersede. A probe starting while the epoch is open joins it (the future just completes later); a probe starting after settle opens a fresh epoch with a fresh Deferred, and the old future is already finished. That is why this is a Deferred and not an AsyncFuture::Restarter: Restarter's machinery is "cancel the superseded run, deliver only the latest," and no epoch is ever superseded. The Restarter already sits where superseding actually happens — each layer's m_loadRestarter, which handles a frame that moves after settle. The split: the Deferred guards when a decode may first start; the load Restarter guards replacing one already running.

A frame that moves after settle reaches the layers as cwGeoReference::localCoordinateSystemChanged → cwLazLayerModel::reloadAll() → each layer reads the new frame back off its token. The signal is deliberately narrower than localProjectionChanged: a freeze or a change of anchor leaves every coordinate in the project exactly where it was, and re-decoding a directory of point clouds is the most expensive thing the frame can cause. That narrowing is what the deleted setRegionFrameCS early-return used to provide, moved to where the change actually happens.

The one abort: project close / clear() mid-epoch cancels the Deferred rather than completing it, so waiting continuations never fire and nothing decodes into a dying region.

Subscription is three lines, and identical for any future GIS layer type (GeoTIFF, DEM, shapefile):

AsyncFuture::observe(m_frameFuture)
    .context(this, [this](const QString& frameCS) { startDecode(frameCS); });

A layer asks for the future at the moment it needs it, through a cwLocalProjectionToken — the same shape as cwFutureManagerToken, a QPointer to the manager behind one method. Pushing the future instead reads simpler and is wrong in exactly the case that matters: rescan() starts a new layer's probe and its reload() before the row is announced (deliberately — cwLazLayerModel.cpp:451-457), so any push driven by the epoch opening would arrive after the layer had already asked. Asking has no ordering to get right at all. The contribute side — telling the manager a probe is in flight — stays cwLazLayer-specific until a second GIS type exists; one consumer is too early for an abstraction.

Accounting note: the model keys the probing layers by identity, in a QSet<cwLazLayer*> wired up in connectLayer() — which is called at creation, so a layer counts from before it is a row, which is when its probe starts. A set rather than a counter because the probe Restarter delivers only the latest run: counting starts would leak a decrement every time a restart superseded a probe mid-flight, and a layer destroyed mid-read would leak one permanently. It drops out on QObject::destroyed instead, where the pointer is only ever a key.

Cancel propagates upstream — keep the wait out of the load Restarter

The obvious shape for "decode after the frame" is to put the chain inside m_loadRestarter.restart(), so a newer reload supersedes the older wait for free. It is a trap. asyncfuture's Private::execute watches the derived future and propagates a cancel up to its parent (futurePtr->cancel()), so the Restarter cancelling one layer's run would cancel the shared epoch future — and every other layer waiting on it would stop dead.

So the wait sits outside the Restarter and a monotonic m_frameWaitGeneration drops the superseded continuation. Layer destruction is safe either way: the context object's destroyed handler deletes the watcher before the cancel it triggers can be delivered.

Thread-safety: probes and decodes run on the pool, but their results are delivered on the GUI thread, and evaluate(), the gate, and the Deferred's completion are all GUI-thread-only. The races this section closes are logical ordering races — which input anchors first — never data races.

F1 — committed as bae40559 (2026-08-05). It carries two debts until F2 lands, both deliberate and named in its commit message: the duplicate header read on the first layer, and the QtConcurrent::run call on the global pool.

Why not a priority queue or a second pool (researched 2026-08-05)
  • asyncfuture cannot hold priority. asyncfuture.h contains zero references to QtConcurrent or QThreadPool: it composes completion and never schedules anything, and even Restarter takes a lambda returning an already-started future. Priority can only attach where work enters a pool, which is the one line in cwConcurrent::run.
  • Adding it there is cheap if ever needed. QTaskBuilder (Qt 6.0+) already has it: QtConcurrent::task(f).onThreadPool(*cwTask::threadPool()).withPriority(p).spawn() returns a QFuture. No custom scheduler.
  • But it wouldn't buy the guarantee. Per QThreadPool::start's docs, priority "can be used to control the run queue's order of execution" — it reorders the queue and never preempts a running thread. With every thread mid-decode on a 100M-point tile, a max-priority probe still waits for one to finish.
  • The only single-pool mechanism that bounds it is reserveThread() + startOnReservedThread() (6.3+), which runs the probe immediately by exceeding maxThreadCount by one. It returns void, so it would need a hand-rolled QPromise to stay composable.
  • The global pool is not free. cwJobSettings::setThreadCountPrivate sets both pools to the user's thread count and threadCount() asserts they are equal — that setting is the app's CPU budget, and riding the global pool quietly spends twice it.
  • All of it is moot once the decode can't start early, which is why part 5 above is a revert rather than a redesign.

What the layer stopped storing (settled 2026-08-06)

With the frame arriving on the future, cwLazLayer was reviewed for the rest of its shadow state. Two more facts turned out to be stored copies of things it could derive, and both were costing branches:

  • The header is one value, not four fields plus a bool. The probe already produces a coherent cwLazLoader::ProbeResult; the layer used to shred it into m_sourceCS, m_sourceBboxMin, m_sourceBboxMax and an m_hasReadHeader flag that only restated "those three mean something". It now holds std::optional<ProbeResult>: hasReadHeader() is has_value(), and the override precedence (override > embedded > empty) moved into sourceCS(). That last move is why setSourceCSOverride no longer re-reads the file — the header did not change, only which CRS it is read as, and precedence is now applied on the way out.
  • Probed is a name, not a state. Two independent things happen to a layer — the header read and the point decode — and they were interleaved into one stored enum plus two bools. The layer now stores only PointState (Idle / Loading / Loaded / Error) and loadStatus() folds in the header: Probed is what "header in, points out" is called. That deletes applyProbe's "only ever an upgrade from Idle" guard and both copies of the m_hasReadHeader ? Probed : Idle fallback — all three existed only to hand-maintain a derivable value.

m_headerProbeInFlight stays an explicit member: it is the epoch's input, and it is genuinely dynamic rather than derived from anything else the layer holds.

Verification

  • A frame that moves takes its clouds with it: correcting the anchor fix station by 100 km re-derives the frame and every loaded tile decodes again into it — the case the value-on-the-future change has to keep working, since nothing pushes a CS any more.
  • A frame that only changes hands leaves its clouds alone: deleting the anchor while a tile sits near the origin freezes the frame, and no layer emits loadStatusChanged. This is what pins reloadAll() to localCoordinateSystemChanged rather than localProjectionChanged.
  • Determinism: a project with several CRS-bearing layers anchors to the first in model row order, and repeated imports of the same directory produce a byte-identical stored projection. Worth forcing probe completion out of order rather than trusting that a fast local disk happens to finish them in sequence.
  • No decode outruns the frame: with any CRS-bearing layer present, no cwLazLoader::load runs with an empty frameCS. Observable without new scaffolding via QT_LOGGING_RULES="cw.laz.layer.debug=true", which is how the current ordering was confirmed.
  • CRS-less directory still loads: N tiles with no embedded CRS all reach Loaded, untransformed; frameFuture() completes with the empty string; rescan performs no synchronous LAZ read.
  • No wait for an anchored project: adding one tile to an Anchored project chains on an already-finished future and decodes immediately — before its own probe lands.
  • Mid-epoch fix station: adding a valid fix while probes are in flight settles the epoch early to the fix, and the stored frame equals what batch-close would have produced.
  • Clear mid-epoch: clearing the project while probes are in flight cancels the epoch; no decode continuation fires afterward.
  • F1's three existing tests keep passing unchanged — they pin the probe's own behavior, which this does not alter.
Barrier scope — settled 2026-08-05

The earlier open question — per-rescan-batch vs. a global "no probes anywhere in flight" — dissolves: with the join rule (a batch arriving while the epoch is open extends it), batch identity stops mattering, and the two formulations are the same predicate. The epoch is open while the frame is Ungeoreferenced and any layer probe is in flight, whatever started the probe. The global predicate also covers any probe a rescan did not start — whatever restarts one on an Ungeoreferenced project opens an epoch, so the anchor waits for it rather than racing it.

One case that used to need this no longer reaches it: setSourceCSOverride stopped re-reading the file (see "What the layer stopped storing"), so it updates sourceCS() synchronously and evaluate() then runs against a complete input set. No I/O means no order to race.

The manager watches only the model (settled 2026-08-06)

syncLayerConnections() is gone, and with it the three per-layer connections. Everything evaluate() reads off a layer arrives through cwLazLayerModel, so the manager's whole layer dependency is three model-level facts: membership (the row signals), headers (the headerProbeInFlightChanged edges — the falling edge is ordered after the header is published, so hearing "probing ended" always means the header is readable; cwLazLayer::finishProbe() owns both writes so the ordering is a choke point rather than two adjacent statements in its caller), and the override (dataChanged filtered on SourceCSRole — setSourceCSOverride applies its precedence in memory with no probe behind it, so neither of the other two would fire for it).

The deleted loadStatusChanged connection had gone dead already: since gatherInputs() gates on hasReadHeader(), a decode landing changes no input, and the connection's comment ("a layer becomes an input when its load lands") described the pre-F2 design. sourcePathChanged was likewise indirect — a path change matters only through the re-probe it kicks off, which reports through the probe edges. m_probingLayers stays a QSet: it counts layers that are not rows yet, because rescan() starts the probe (and the reload() that pulls frameFuture()) before beginInsertRows, and a linear scan of m_layers at that instant would miss the very probe that must open the epoch.

15. D20 implementation — automatic recentering (planned 2026-08-06)

The sequencing gate is satisfied: F1's universal async probe (2d7148b6) and F2's epoch (fad72b67) are in, so whenever the state machine runs against a closed epoch, every layer with a path holds a header and gatherInputs() is the complete set. The V1-shaped hazard D20 was sequenced behind — a still-loading layer making "nothing within R" spuriously true at project open — is retired.

Where the rule lives — the Frozen branch, and only there

evaluateFrame() ends today with the comment "Frozen: a frame with nothing left to follow. Only the user moves it." — and D20 deletes the manual action that sentence assumed. The recenter check replaces that comment: after the Ungeoreferenced anchor attempt, a Frozen state with non-empty inputs calls maybeRecenter(inputs). A case walk shows the "none within R" condition can never fire anywhere else, so a single call site is the whole rule:

  • Anchored, anchor among the inputs: anchor within R → an input is within R, so the rule is vetoed. Anchor beyond R → the existing edited-anchor rule re-derives at the anchor first, which puts the anchor at the origin. Either way "none within R" is false by the time the rule could run. The anchor stays authoritative: a user who corrects the anchor by 100 km must land the frame on the corrected anchor, not on a median that stale tiles drag back toward the mistake.
  • Anchored, anchor witnessed-deleted: something nearby → freeze, and an input is within R. Nothing nearby → anchorToFirstUsable hands the role on, and the new origin sits on that input. Kept as-is, a decision this section records: §4's green edge ("re-derive from the first remaining") predates D20 and stays — median-freezing here instead would trade a live anchor for a dead frame on the one path where the user is demonstrably editing inputs.
  • Ungeoreferenced: no origin to be far from.
  • Open epoch: evaluateFrame() returns before the branch is reached, so a recenter can never run against a partial header set — the same barrier that protects the first anchor protects every recenter.

New surface

cwGeoReference::recenter(const QString& localCS) — the fourth mutator: writes {Frozen, localCS, null Anchor} together, and refuses an empty string the way anchorTo does. It rides setLocalProjection's existing change detection and signal order (localCoordinateSystemChanged before localProjectionChanged), so the clouds re-decode before convergence recomputes, exactly as on an anchor move. Nothing new persists: Frozen + CS + no anchor is already a storable combination, so the proto and save/load are untouched.

On the manager: a private maybeRecenter(const QList<Input>&), plus a localPointOf(const Input&) helper returning std::optional<cwGeoPoint> that distanceFromOrigin() refactors onto — same transform, but the recenter needs the point itself, not just its magnitude. The component-wise median is a file-local function in the .cpp.

The algorithm

  1. One pass, veto first. Transform each input into the current frame (memoized transformPoint), collecting the points that transform. The first point within R returns immediately — the veto is the common case and the cheap one, and fixes lead the input order, so a Frozen project sitting on its data usually pays one transform and one hypot per evaluate().
  2. Unanswerable is neither near nor far. An input whose CS can't be related to the frame contributes nothing: it can't veto and it can't vote. Zero relatable points → return; the frame is not provably wrong, and moving it on no evidence is exactly what the stored-frame rule forbids.
  3. Component-wise median of the relatable local points: sort the x's and the y's independently, average the middle two on an even count; z = 0 (derivation is horizontal-only, D5). Median rather than mean so a single wrong-county tile at 300 km pulls the center by meters, not halfway to the wrong county. With one relatable input the median is that input and the frame lands on it — the "re-derive at the data" degenerate case, still Frozen.
  4. Derive on the frame's own datum: candidate = cwLocalProjection::deriveFrom(currentLocalCS, medianPoint). Handing the current frame as the anchor CS is what pins the datum: the median is in frame coordinates, and the frame carries the datum pinned at first anchor — inputs on mixed datums vote on position, never on datum. (deriveFrom's x-first contract is met for free; transformPoint output is already normalized x-first.)
  5. Guards: median within R of the origin → return; empty candidate → return (leave the frame alone rather than half-move it, matching anchorTo). Amended during implementation (2026-08-06): this section had planned the second guard as a string comparison — candidate equal to the current frame → return — and called that the termination proof, rejecting a distance test. Implementing it showed the string comparison does not terminate cheaply. A recenter lands the origin on the median, and recomputing the median in the new frame leaves it a few millimeters off (the frames are not related by a translation), while PROJ writes lat_0 to ten decimal places — about 0.01 mm. So the string keeps differing: the frame walks in on a geometric sequence, 25 m → 6 mm → µm, and every step of it re-decodes every cloud in the project, one step per evaluate tick. Comparing against R instead terminates in one move and needs no new constant: the origin moves when it is meaningfully wrong, which is the same test the rest of this class makes. The degenerate case the string guard was for — inputs spread either side of the origin, all beyond R, median on the origin — is covered by the same comparison.
  6. Commit: geoReference->recenter(candidate), then the bookkeeping every frame move records: m_lastAnchor = geoReference->anchor() (now the null anchor), m_anchorSeen = false.

Downstream, all synchronous

recenter → localCoordinateSystemChanged → reloadAll → each reload() pulls frameFuture(); the state is Frozen, so the epoch is closed and the future arrives already finished with the new string — decodes start immediately, no epoch involvement and no re-entrant evaluate() (a reload re-reads points, never the header, so no probe edge fires). Then localProjectionChanged → convergence recompute. The full re-decode sweep is the cost that keeps R at 50 km rather than a softer "off-center" trigger (the churn rationale in the D20 row).

Self-heal (D7's replacement): an old dev project restores a frame far from its data; setLoading(false) runs one evaluate(). A Frozen frame recenters right there if the headers are already in, or on the probe falling edge otherwise; an Anchored frame heals through the edited-anchor rule once its anchor is witnessed. Either way, exactly one reload sweep.

Tests (test_cwLocalProjectionManager.cpp, one integration case in test_cwLocalProjectionFrame.cpp)

  • Fabricating "Frozen and far" uses restore() — the load path is the only honest way to reach a frame the state machine wouldn't produce from the current inputs, and it is exactly the old-dev-project shape D20 exists to heal.
  • Recenters at the median: three inputs, frame restored 200 km away → Frozen, anchor invalid, the median input reads ~0 in the new frame.
  • Fires once: a SignalSpy on localCoordinateSystemChanged counts the load's move and the recenter, and stays there across further evaluate() ticks.
  • Data spread around the frame stays put: inputs 55 km south and 60 km north of the origin → every input past R, median 2.5 km out, no signal. The offsets are uneven on purpose: a test written with the inputs balanced north–south cannot fail. The fixtures are UTM zone 12 eastings of 500000, which is the zone's own central meridian, so the frame derived there shares it — and two transverse Mercators on one ellipsoid sharing a central meridian are related by an exact affine map. The median of the projected coordinates then lands on the origin to 3e-9 m whatever the guard does. Measured, not assumed: a temporary probe printed both medians.
  • One input within R vetoes: the §4 wrong-county-tile invariant — a good fix near the origin plus a tile at 300 km → frame stays, tile keeps its outlier flag.
  • Unanswerable is neither near nor far: an unrelatable-CS input alone neither vetoes nor moves anything; paired with one far readable input, the frame lands on the readable one.
  • Clouds follow the frame (integration): Frozen-far project with a synthetic LAZ; after the recenter the tile's decoded points sit near the origin. Reuse utmZoneWkt/waitForLazLayerModelSettled and FixStationFixtureHelper; real-world fixture coordinates depend on centerHeaderOffsets.
  • Falsification pass, run: disabling the veto fails the wrong-county case (and §4's "a frozen frame stays put when new data arrives"); disabling the R comparison on the median fails the spread case; taking the first input instead of the median fails both the spread case and "moves to the middle of it".
  • One older test had to change: "Loading a project keeps the frame the file carries" stored a frame in Cape Town for a project in Utah, which is now exactly what the recenter heals. Its point — a load restores rather than re-derives — is kept by storing a frame 10 km from the data instead: still nothing the project's own inputs could derive, and still describing where the project is.

Costs and non-changes

  • Frozen projects gain per-evaluate work that used to be zero: transforms until the first within-R input. Memoized transforms and keystroke-rate calls keep it negligible.
  • Untouched: the Anchored edited-anchor rule, the deleted-anchor handoff, the epoch machinery, the persistence schema, and all UI — D20 is invisible except through the frame moving. It also softens P4.2's "the first cave always reads 0.000°": once other inputs pull the median away, a recentered frame gives the original cave a non-zero convergence.

16. P4 step 5 — the read-only frame display (shipped 2026-08-06)

The last step of P4: the project info box on DataMainPage.qml now says where the project's frame is centered, what datum it is on, and what its elevations are measured from. Read-only, and never an editor — D4's reasoning is that a datum picked by hand can only disagree with the data it describes, since every input already declares its own.

What it shows

RowValueWhen
LocationThe frame's origin as latitude, longitude to six decimals (~0.1 m — a projection parameter, not a placed point, so coarser than the picker's eight)Always; reads "Not georeferenced" with no frame

The help text says CaveWhere derives its own projection per project, that the datum is inherited rather than chosen, and — for §5 — that elevations are passed through exactly as given and never converted between height systems.

How the frame describes itself

Two new statics on cwLocalProjection, both answering from the stored string alone, so nothing has to be re-derived to describe it:

  • datumName(cs) — the horizontal half's geodetic base, then proj_crs_get_datum_forced. Forced matters: WGS84 is a datum ensemble in modern PROJ and plain proj_crs_get_datum answers nothing at all for one. It also answers for an input CS, not just a frame.
  • origin(localCS) — asks the frame where its own (0, 0) lands, which is the origin only because the LDP has no false easting or northing. Handing it a UTM zone answers for a point 500 km west of that zone's center. Returns x-first (longitude, latitude) on the frame's own datum, so no datum shift creeps into a readout of a number that was planted, not measured. Shares toGeographicTransform() with deriveFrom, which builds the same transform in the other direction.

cwGeoReference exposes datumName, hasOrigin, originLatitude and originLongitude, all notified by localProjectionChanged. They are read out of the frame once inside setLocalProjection — the only writer the frame has, so the only writer they need — rather than on every binding that describes it. Latitude and longitude cross to QML as two named doubles rather than one point, so the axis-order trap that deriveFrom documents has nowhere to hide at the boundary.
