Live-Link Retirement IN PROGRESS

The in-project copy is the only file. CaveWhere stops watching, probing and offering to re-copy from a remembered external source; the user replaces the attachment explicitly, and edits to the project's own copy are what the watcher reacts to. Filed 2026-08-04.
Status 2026-08-11: commits 1, 2, 3, 3b and 4 have shipped (§6 carries the hashes) — the retirement is complete in the code. Commit 5, this doc reconciliation, is the last row.
Related: master plan (§5 copy workflow, §8.8 q16), Phase 2 (commit 7 shipped the stale/updateFromSource work; §16 B7 is this plan's prerequisite), scan-time station harvest (§6 follow-ups, several of which this collapses).

1. Why — two premises are in the codebase at once

The 2026-07-16 direction change (Phase 2, commit 7) declared the in-project copy the source of truth and dropped auto-reconcile: a source-side edit now only raises a flag, and the user triggers the copy. That was the right direction and it did not go far enough. The watcher, the freshness probe, the Update button and two banners all remained (all since deleted, §6), and every one of them was built on the opposite premise — that the external file still holds authority and the project copy is a cache of it.

The two premises met in one predicate. Staleness was defined as "the reconcile plan has pending copies" — in the freshness probe cwExternalCenterlineManager ran per owner, deleted in commit 2 — and a copy is planned whenever destinationMatchesSource is false (cwExternalCenterlineSync.cpp, which survives as the test attach runs after its copies to verify they landed): 

if (!dstInfo.exists())                    return false;
if (srcInfo.size() != dstInfo.size())     return false;
return srcInfo.lastModified() <= dstInfo.lastModified();
The predicate is symmetric; the affordance is directional.
It answers “do these two files differ?” The button built on it does “push the source into the project.” The only term carrying direction is the lastModified comparison, and it is ANDed behind size equality — so for any edit that changes the file's length, which is nearly all of them, the function returns on line 2 and the mtime ordering never runs. The manager therefore cannot distinguish the source moved forward from the project copy moved forward. It sees drift and always attributes it to the source.

1.1 The two hazards that fall out

Both are the same bug seen from different ends: both mean “the copy moved forward,” and both are read as “the source is newer, offer Update.”

H‑A — in-place edit clobber H‑B — pull-then-Update clobber
Trace User fixes an error directly in the in-project copy. Sizes now differ, so the probe flags stale and Update appears; clicking it copies the old source back over the fix. User B edits the copy, commits, pushes. User A pulls; the copy carries B's bytes and a checkout mtime. Sizes differ, so A is flagged stale on open; clicking Update writes A's untouched source over B's work, and reconcile's GC (cwExternalCenterlineSync::computePlan) deletes any file B added to the closure.
What is lost The user's own local edit. A collaborator's committed, pushed work.
Who notices The person who made it. Possibly nobody. The reversion is a legitimate-looking commit.
How ordinary Uncommon. The normal collaboration path for a git-backed .cwproj.

1.2 Why not just fix the predicate

Because a two-point comparison cannot carry direction. Telling source moved from copy moved needs a third point: a recorded baseline of what the copy was at the last successful reconcile, per machine, maintained across every sync, invalidated correctly on attach, detach, replace, external edit and pull. cwExternalSourceSettings stores an ownerId → sourcePath and nothing else, so that baseline is new state with new invariants and new ways to be wrong.

Deleting the second file deletes the question instead of answering it. That is the whole proposal.

1.3 The asymmetry this also removes

cwExternalSourceSettings is per-user and per-machine, so it does not travel in the project. Today that gives two people looking at the same attachment structurally different capabilities: whoever attached it has a source, a stale flag and an Update button; whoever cloned the project has none of them and can only edit the copy. Nothing in the UI explains why, and nothing could — the cause is a settings file one of them happens to have. Under this plan they are the same user.

2. The model afterwards

  • One file. The attachment is <project>/<Cave>/trips/<Trip>/external-centerline/<entry>.svx and its closure. It is what the solve includes, what the harvest reads, what the error banner names, and what git versions.
  • Edits to it are live. Already implemented: a project-side watcher event recomputes the dependency set and re-solves (cwExternalCenterlineManager::onWatchedFileChanged). This half of the proposal is existing behavior, not new work.
  • Replace is explicit. A new verb re-runs the attach path against a freshly picked file, swapping the closure in one operation. It is the only way an outside file enters the project after the initial attach.
  • The remembered path becomes a breadcrumb. Kept purely to pre-fill the Replace file dialog. No watching, no probing, no staleness, no banner. When it goes missing, the dialog just opens somewhere unhelpful — which is all a forgotten path should ever cost.
What the user gives up, honestly stated
The caver who maintains master survey data in Survex text outside CaveWhere goes from edit, click Update to edit, click Replace, confirm the pre-filled path. That is one extra click on a workflow that was already explicit after the 2026-07-16 change. They also gain the option of editing the project's own copy, which re-solves with no click at all.

3. Prerequisites — Phase 2 §16 B7 and B8 (both met 2026-08-04)

Both prerequisites have shipped.
B7 landed as 386cee62 and B8 alongside it, each with its own regression suite. The gate below is satisfied — commit 1 is unblocked. Read the two entries that follow for what the fixes actually do, since the B8 one grew a discriminator the description here does not mention: a discard, a sync's pull, and a checkout rewrite the same watched files, so “a watcher event means the user edited something” is only true once CaveWhere's own writes are filtered out.

Both were real defects, independent of this plan. Both are on the path this plan promotes from “possible” to “sanctioned”, so shipping the retirement without them would have been advertising a workflow whose guard rails were missing.

B7 — a project-side *include can escape the attachment directory. Today someone has to reach for it; afterwards it sits on the main path.

B8 — an external edit to the in-project copy does not mark the project modified. Confirmed 2026-08-04: cwProject::setModified(true) is driven solely by cwSaveLoad::localMutationOccurred (cwProject.cpp:227-233), and every emitter of that signal lives inside cwSaveLoad where a job is queued. The manager's watcher-driven recompute enqueues no jobs, so the bit never flips — even though the edit re-solves and the plot visibly updates.

This one is load-bearing for the whole plan.
“Edits to the in-project copy are live” is the benefit being traded for the Update button. If those edits do not mark the project dirty, the trade is a downgrade: the user sees the plot update, quits, is not prompted, and — in a bundled .cw, whose extracted tree is only re-zipped on save — loses the edit outright. B8 must land before commit 1, not merely before release.

4.1 Detach

The panel's Detach… action comes out too. Once the copy is the only file, detaching leaves a trip that has nothing in it — the survey data lived in the attachment, and CaveWhere never lets the user edit an external trip's shots by hand. Removing the trip on the Cave page reaches the same end in one step users already know, so the panel keeps the two verbs that are actually about the file: Reload now and Replace….

Removing the trip also cleans up: the attachment dir is rooted under the trip's own directory (externalCenterlineDir(trip) resolves through dirPrivate(trip)), and trip removal already enqueues removeDirectory(trip) (cwSaveLoad.cpp:3490), so the copied closure goes with it rather than lingering as an orphan.

What the two verbs do differ in is worth stating plainly rather than discovering later: detach kept the trip and its name, date, team, and calibration; removing the trip discards all of it. That difference only matters to a user who wants to keep a trip's metadata and swap what fills it — which is Replace, not detach-then-attach. No workflow this plan knows of needs an emptied-but-surviving external trip.

cwExternalCenterlineManager::detachCenterline and cwRootData::detachTripCenterline stay. The panel's RemoveAskBox is their only caller today, but detach is still the correct teardown for an owner (it clears the settings entry and the attachment-dir map synchronously so a queued operation cannot resurrect files), and the manager tests cover it directly. This is a UI removal, not an API one.

5. What goes in

5.1 Replace

attachCenterline(cwTrip*, sourcePath) already does the whole job: scan the picked file, reconcile its closure into the owner's attachment dir, GC what is no longer referenced, re-solve. Replace is that call against an owner that already has an attachment, guarded by isOwnerBusy like every other filesystem operation for an owner.

The open detail is whether it routes through detach-then-attach or reuses the existing reconcile-with-GC. Reconcile-with-GC is preferable: detach drops the settings entry and attachment-dir map entry synchronously (per the detachCenterline header comment), so a detach/attach pair briefly leaves the owner in a state where an interleaved scan sees no attachment at all.

5.2 Breadcrumb semantics

Keep the store, drop the meaning. Nothing reads it except the Replace dialog's initial folder. Detach already clears the entry, which stays correct. A breadcrumb pointing at a file that no longer exists is not an error state and raises no banner — the dialog opens at the default location instead.

7. Open questions

  1. What happens when the in-project copy itself goes missing? RESOLVED The scan now reports the owner's missing entry file (ExternalCenterlineManager.missingCopyPath, notified by missingCopiesChanged), and the trip panel banners it by project-relative path with a Replace… button; the report clears on the next recompute — which Reload now runs through the new rescanAttachments() — or when a Replace lands. History: missingSourceOwners covered a missing source and was deleted with the live link; a missing copy was the one state left worth surfacing, and the one case where a “re-attach” prompt is genuinely the right answer.
  2. Should Replace warn when the project copy has local changes? RESOLVED No — without a baseline we cannot detect local changes, so ReplaceCenterlineDialog (itself the confirmation step) carries a plain statement (replaceExplainerText): replacing swaps the files copied into the project for the picked file and everything it includes, the current copies including any edits are replaced, and files the new one leaves out are removed. The statement is only true because attach and replace reconcile under CopyPolicy::Overwrite: the picked file's version of every file in its closure is copied over whatever is there, whatever its size and mtime. Under the older up-to-date skip, an edit to the project copy that kept the byte size looked current and survived the swap.
  3. Release note wording for users whose Update button disappears. MOOT No release ever shipped the Update button, so there is no user to write the note for.
