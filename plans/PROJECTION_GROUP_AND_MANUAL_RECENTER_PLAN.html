Projection Group Box and Manual Recenter

Parent plan: plans/LDP_AUTO_COORDINATE_SYSTEM_PLAN.html (the LDP lifecycle, decisions D4, D8, D20, §16). This plan builds on the completed P4 step 5 read-only frame display (commit 221b3e6d): two user-facing features and one derive-time policy change, in four phases:

  1. Phase 1 — Projection group box. Restructure the Project info box on DataMainPage.qml so Units, Location, Centered on, Datum, and Elevations read as one visual group; make the datum rows always visible once the project is georeferenced; add a "Centered on:" attribution row that names the anchor station and its cave.
  2. Phases 2–3 — Manual recenter. In edit mode, the Location row gains a "Recenter…" control that opens a picker listing the project's fix stations (grouped by cave, "A42 — Roppel Cave") plus a "Center of data" option. Picking a station re-anchors the frame on it; picking Center of data freezes the frame at the component-wise median of all georeferenced inputs.
  3. Phase 4 — plate-fixed frame datum. When the anchor's coordinate system resolves to the WGS84 datum ensemble (what the UI stamps on every typed lat/long), derive the frame on the plate-fixed datum customary at that location instead — NAD83(2011) in the US, ETRS89 in Europe — via a small curated location table. Declared non-WGS84 systems are untouched.

1. Settled design decisions

The datum is never pickable (D4 stands). Recentering keeps whatever datum the chosen anchor's coordinate system declares — mixed-datum effects are ~1–1.5 m, below the accuracy of the workflow, and CaveWhere ships PROJ grids so transforms are machine-independent. No datum UI is added by this plan.
Picking a fix station uses the existing Anchored state via cwLocalProjectionManager::anchorTo(Input) — no new lifecycle state, no proto/persistence change. The chosen station becomes the anchor: small later corrections to it leave the frame alone, a >50 km correction re-derives, deleting it hands off to Frozen — all existing behavior. Picking Center of data uses the existing cwGeoReference::recenter() path to Frozen.
A station whose pick would put the median of the project's georeferenced data more than 50 km from the new origin is disabled in the picker with a short explanation. No fourth "user-pinned" state. (The Anchored state never auto-recenters, so D20 would not literally undo such a pick — but a frame 50+ km from the data is a bad frame, which is the same reason kAnchorThresholdMeters exists.)
A WGS84-labeled anchor gets a plate-fixed frame datum by lookup (2026-08-08, after the RTK discussion). WGS84's modern realizations are Earth-fixed, so the ground — cave, benchmarks, lidar — drifts through them with the plate at ~2 cm/yr (~0.8 m over 40 years), while national datums like NAD83(2011) and ETRS89 are plate-fixed and hold still. RTK and lidar data arrive in those national frames, so a plate-fixed frame also makes their transforms slop-free, where crossing into a WGS84 frame costs the ~1–2 m ensemble ambiguity. The location can't tell us what datum a measurement is in — but the frame's datum is CaveWhere's own choice, and "WGS84" on an anchor is a label of convenience (the CS picker stamps EPSG:4326 on every typed lat/long), never a deliberate frame preference. This is a derive-time default only — not the rejected "datum upgrade" event: no new lifecycle event, no persisted flag, and stored frames never move on their own.
The "Centered on:" row shows only in the Anchored state, resolved live from the persisted anchor id — so it survives save/load and follows renames. A Frozen frame (auto- or manual center-of-data) has no anchor and shows no attribution row; the Location row still gives its coordinates.

5. Phase 2 — recenter backend (C++, no UI)

5.1 Manager: public recenter API

The manager keeps only what needs its private lifecycle state and its view of the whole project. Building the picker's rows is the model's job (5.2); what the manager publishes are the two actions and the three facts the model needs to do it:

//! The frame's reach, which is the same rule that decides a station is worth
//! centering on and that an origin has ended up somewhere the project isn't.
//! kAnchorThresholdMeters stays private in the .cpp.
static bool isWithinReach(const cwGeoPoint& center, const cwGeoPoint& point);

//! Built on first access; a project that never opens the picker never pays for it.
cwRecenterCandidateModel* recenterCandidates();

//! The component-wise median of every input the frame can place, in the frame's
//! own coordinates. Empty with no frame, or nothing the frame can place.
std::optional<cwGeoPoint> dataCenter() const;

//! Where \a fix sits in the project's frame. Empty when the fix has no
//! coordinate the frame can read — folding "not a usable fix" and "can't be
//! transformed" together, because neither is a station you can center on.
std::optional<cwGeoPoint> localPointOfFix(const cwFixStation& fix) const;

//! Re-anchor the frame on the station \a stationId, making it the input the
//! lifecycle follows from now on. Refuses (returns false) an unknown id, an
//! unusable station, and an ineligible one — the picker grays those out, and
//! the project may have changed between showing the list and the click.
Q_INVOKABLE bool recenterOnStation(const QUuid& stationId);

//! Freeze the frame at dataCenter() — the same point maybeRecenter() steers to,
//! applied because the user asked rather than because the data drifted.
Q_INVOKABLE bool recenterOnDataCenter();

dataCenter() implementation. For every input from gatherInputs() (stations and layers), localPointOf(input); skip inputs that don't transform; median x and median y via cwMedian (cwMath.h). Empty when nothing transforms — which also covers "no frame", since localPointOf answers nothing without one. maybeRecenter() loses its own copy of the median and calls this, after its veto scan.

localPointOfFix() is usableFixStation(fix) (the file-local Valid + isValidCS filter, shared with gatherFixInputs() so the two can't drift) then localPointOf(inputOf(fix)). Extracting inputOf() as the one place a fix becomes an Input is what keeps the picker and the lifecycle reading a station the same way.

recenterOnStation(): take a fresh dataCenter(), find the station, refuse unless isWithinReach(center, local) — the same predicate the model draws its rows with, so the check and the display can't disagree — then call the existing private anchorTo(inputOf(fix)), which already derives, writes, and maintains m_lastAnchor/m_anchorSeen. It deliberately does not refresh the model: an action that mutates what the picker is displaying is a surprise, and re-deriving the one station's eligibility is cheaper than rebuilding every row.

recenterOnDataCenter(): compute the median as above, then follow the tail of maybeRecenter() exactly (cwLocalProjectionManager.cpp:307-319): deriveFrom(localCS, median), refuse an empty result, geoReference->recenter(candidate), m_lastAnchor = geoReference->anchor(); m_anchorSeen = false;. Do not copy the two early-return guards from the top of maybeRecenter():

The "something within 50 km of the origin" veto and the "median already within 50 km" termination check in maybeRecenter() exist so the automatic path only moves a frame that is provably wrong. The manual path is the user explicitly asking — with those guards copied in, "Center of data" would silently do nothing in the most common case (origin on the first station, data nearby), which is precisely the situation the button exists for.
Deriving from the median keeps the current frame's datum (deriveFrom(localCS, …) — the median is in the frame's own coordinates), so "Center of data" never changes datum. Picking a station re-derives on the station's CS, so it adopts that station's datum — that is the existing anchor rule, not a bug; the datum display simply follows. Leave both as they fall out of the existing calls.
A recenter re-decodes every LAZ layer (it rides localCoordinateSystemChanged → reloadAll). That is intended and already asynchronous; add no progress plumbing and no extra reload call.

5.2 The candidate model, and the QML surface

The region owns the manager; it does not wrap it. It gains one property, exactly like the four subsystem properties it already exposes:

Q_PROPERTY(cwLocalProjectionManager* localProjection READ localProjection CONSTANT)

and the manager becomes the QML-facing object — QML_NAMED_ELEMENT + QML_UNCREATABLE, the way cwFixStationValidator is:

Q_PROPERTY(cwRecenterCandidateModel* recenterCandidates READ recenterCandidates CONSTANT FINAL)

cwRecenterCandidateModel is a new QAbstractListModel (cwRecenterCandidateModel.h/.cpp, picked up by the source glob) with roles stationId, stationName, caveName, eligible — the same shape every other list in this codebase crosses to QML in. It owns the question the picker is asking, not just the rows that answer it:

struct cwRecenterCandidate { QUuid stationId; QString stationName;
                             QString caveName; bool eligible = false; };

cwRecenterCandidateModel(cwLocalProjectionManager* manager, cwCavingRegion* region);

//! Rebuild against the project as it stands. It reprojects the project's inputs.
Q_INVOKABLE void refresh();

refresh() takes manager->dataCenter(), walks the region's caves, and keeps every station manager->localPointOfFix() can place, marking it with manager::isWithinReach(). It runs in the constructor, so the model is correct the moment the property is first read, and the popup calls it again in its onOpened.

Eligibility is isWithinReach(center, station) — a horizontal distance against the 50 km threshold, both points in the current frame. It stands in for "how far the data would sit from the origin of the would-be new frame": recentering moves the origin onto the station, and tmerc distortion over these distances (≤ ~11 ppm at 30 km) is noise against a 50 km threshold — so one median and one subtraction per station replaces deriving a candidate frame and re-transforming every input per station.
The rows are deliberately not kept current between opens — no connections to the fix-station models. Eligibility reprojects every station in the project, and nothing is displaying the list between opens, so recomputing it per keystroke would be real work for nobody. refresh() on open is the contract; a test that appends a station and expects the count to follow is asserting the wrong thing.
No QVariantList/QVariantMap, and no pass-through invokables on cwCavingRegion. Untyped rows violate the QML rules in CLAUDE.md, and a region that forwards calls to a subsystem it owns is a facade the region's existing design deliberately avoids — consumers read region.geoReference, region.lazLayers, region.fixStationValidator, and now region.localProjection.

5.3 Phase 2 tests (C++, tag them so they run as a subset)

Extend the existing manager test file (find it: grep -rl cwLocalProjectionManager testcases/), new SECTIONs or a new TEST_CASE tagged [cwLocalProjectionManager][cwRecenter]. Model the fixtures on the existing ones in that file (they already build regions with fix stations in known CRSs). Cases:

  1. Recenter on a station: two stations A and B a few km apart, frame anchored on A (first). recenterOnStation(B.id) → returns true, state Anchored, anchor().id == B.id, origin latitude/longitude within ~1e-6° of B's geographic position, and localCoordinateSystemChanged fired exactly once (SignalSpyChecker).
  2. Lifecycle follows the new anchor: after recentering on B, edit A by a small amount → frame untouched; delete B → frame goes Frozen (the existing hand-off), proving the pick joined the normal lifecycle.
  3. Center of data: stations at known offsets; recenterOnDataCenter() → true, state Frozen, anchor() invalid, origin at the component-wise median. Test-geometry trap (from D20): with symmetric inputs the median sits where a mean would too, so a wrong statistic can't fail — use an asymmetric set (e.g. three stations where median ≠ mean by a testable margin) so the assertion can actually catch a regression.
  4. Eligibility: a cluster near the origin plus one station > 50 km out: that station's candidate has eligible == false, and recenterOnStation() on it returns false leaving the frame byte-identical. The clustered stations are eligible.
  5. Refusals: unknown id → false; ungeoreferenced project → recenterCandidates() empty and both actions false.
  6. Datum follows the pick: A declared on EPSG:32616, B on EPSG:26916, a couple of km apart so only the declared datum differs → after recenterOnStation(B.id), datumName() contains "North American Datum 1983". Its mirror: after recenterOnDataCenter() on a mixed-datum project, the datum is unchanged.
  7. The rows are a snapshot: read recenterCandidates(), append a station, the count holds; refresh() and it follows. This is what pins the deliberate staleness — without it, someone "fixes" the model by wiring it to the fix-station models.
Axis order. Everywhere in these tests, cwGeoPoint is x-first (x = easting/longitude). originLatitude() is m_origin->y. When computing expected origins by hand, a transposed pair usually still "looks plausible" — assert against coordinates whose latitude and longitude bands don't overlap (the existing tst_DataMainPage_Georeference fixture was chosen for exactly this: lat ≈ 37, lon ≈ −84).
Tests must survive concurrent processes: temp projects use QTemporaryDir/pid-suffixed names, as the existing fixtures in this file already do. Run with ASAN_OPTIONS=detect_container_overflow=0 on macOS Debug.

7. Phase 4 — plate-fixed frame datum for WGS84-labeled anchors

Independent of Phases 1–3; it can land before or after them. Everything in this phase lives in cavewherelib/src/cwLocalProjection.cpp plus tests and docs.

7.1 The rule

In cwLocalProjection::derive(), after resolveGeodeticFrame(datumCS) succeeds: if the resolved base's datum is the WGS84 ensemble, look up the plate-fixed datum for (latitude, longitude). If the lookup answers and its CS resolves, re-derive the frame on that base — transforming the origin point across — and otherwise keep WGS84 exactly as today. Anchors on any other datum (declared NAD83, ETRS89, a state plane, a specific WGS84 realization like G2139) are untouched.

Detection: proj_crs_get_datum_forced(context, base) → proj_get_name(datum) equals "World Geodetic System 1984". That string is what the forced call answers for the ensemble (already verified in the step-5 work); a specific realization answers its own longer name and is deliberately left alone — someone who typed a realization meant it.

The trigger is the resolved datum, never the CS string. The WGS84 label arrives as EPSG:4326 from the CS picker (CSPicker.qml:58 commits CoordinateSystem.wgs84()), as EPSG:326xx for WGS84 UTM zones, as an empty string (test/API paths — the existing empty→cwCoordinateTransform::Wgs84 fallback runs first and then this rule fires on its result), and as WKT from some imports. Matching on the datum name catches all spellings with one rule.

7.2 The lookup table

A file-local function in the anonymous namespace of cwLocalProjection.cpp:

//! The plate-fixed geodetic CRS customary where (\a latitude, \a longitude)
//! is, or "" where no entry covers it — the caller then keeps WGS84. A static
//! table rather than a PROJ database query, so the answer depends only on the
//! shipped binary, never on which proj.db a machine has.
QString plateFixedDatumFor(double latitude, double longitude);

Backed by a constexpr array of coarse bounding boxes, first match wins (order entries most-specific first). Candidate entries — verify every EPSG code and its forced datum name against the vendored proj 9.3.1 before trusting this table (a throwaway test that calls cwLocalProjection::datumName("EPSG:xxxx") and prints with -s is enough):

  • Bboxes are deliberately coarse; on a US/Canada border overlap the first match wins and the two frames differ by centimeters — harmless. Do not try to encode precise borders.
  • The WGS84 lat/long is used directly for the bbox test (the ~1.4 m datum offset can never flip a continental bounding box).
  • These national frames get replaced on decade scales (NAD83 → NATRF2022 is coming). A stale table only affects newly derived frames — stored frames never re-derive — so updating an entry later is safe and expected.

7.3 Implementation shape in derive()

// after resolveGeodeticFrame(datumCS) succeeds:
double lat0 = latitude;
double lon0 = longitude;
if (/* forced datum name of frame->base == "World Geodetic System 1984" */) {
    const QString plateCS = plateFixedDatumFor(latitude, longitude);
    if (!plateCS.isEmpty()) {
        if (auto plateFrame = resolveGeodeticFrame(plateCS)) {
            // transform (longitude, latitude) x-first from the WGS84 base to
            // plateFrame->base via toGeographicTransform-style normalized
            // crs-to-crs; on success adopt plateFrame and the transformed
            // lat0/lon0, on any failure keep the WGS84 frame untouched
        }
    }
}
// tmerc conversion, cartesian CS, projected CRS as today, using the adopted
// frame->base and lat0/lon0
Failure direction is the opposite of the declared-CS rule. derive() refuses a declared CS PROJ can't read, because the data is on a datum we failed to identify. The plate lookup is CaveWhere's own suggestion — if its CS doesn't resolve or the point transform fails, fall back to the WGS84 frame silently; never return "" because of it. A refusal here would break georeferencing for users the table was supposed to quietly help.
Axis order, again. The crs-to-crs transform must be proj_normalize_for_visualization-ed (see toGeographicTransform()'s comment), and after it the coordinate is x-first: xy.x is the longitude, xy.y the latitude — proj_create_conversion_transverse_mercator then takes latitude first. Transposing here centers the frame in the wrong hemisphere; the tests below use a point whose latitude and longitude bands don't overlap so a transpose cannot pass.

Transforming the origin point (rather than reusing the WGS84 numbers as-is) keeps two documented invariants exact: the frame's origin is the anchor's position on the frame's own datum, and origin() reads back the point derive() was handed. The moved distance is the ~1.4 m ensemble offset — irrelevant to centering, load-bearing for the docs' honesty.

10. Out of scope, on purpose

  • Any datum picker, horizontal or vertical (D4; discussed and re-affirmed 2026-08-08 — with shipped PROJ grids the frame datum choice is ~1 m of absolute placement that the align-to-lidar workflow cancels, and loop closure is datum-independent at the millimeter level).
  • A "datum upgrade" event when lidar joins a stations-first project (considered, rejected for the same reason). Phase 4 is not this event: it changes what a new frame derives to, never moves a stored frame, and adds no state. Likewise, no migration of existing WGS84-framed projects.
  • Typing coordinates as the center (D8), undo/redo of a recenter, and recentering an ungeoreferenced project.
  • Attribution for Frozen frames ("centered on the middle of your data") — no persisted record exists and none is added.
