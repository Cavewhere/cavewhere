Per-page tool rail in the main sidebar

Modal tools leave the 3D scene and live in the main sidebar, contributed per page. Selecting a tool opens a sidebar-hinged property flyout; the task list and Auto-update merge into one stateful footer whose running state pops out a task flyout to the side. Three responsive sizes — Wide, Mid, and Compact (phone, no sidebar) — each get their own treatment.

What we're building

  • Tool rail in MainSideBar — icon-only, grouped (e.g. Point Cloud → Clip), instant tooltips, scrolls.
  • Per-page tool contract — the active page publishes a tool model; the sidebar renders it.
  • Sidebar-hinged property flyout; on phone it's a bottom sheet.
  • Merged footer: Auto-update toggle ⟷ "Update needed · Run" ⟷ "⟳ Running n Tasks ›". Clicking it pops a task flyout beside the sidebar — no inline expansion.
  • Three sizes: Wide (80px) · Mid (50px) · Compact (no sidebar — Tools joins View/Layers as a top-right button that opens the shared drawer).

1 · The design — click through it

Switch page to swap per-page tools. Switch size across Wide / Mid / Compact — Compact drops the sidebar and reveals the phone controls (and the Phone tools selector). Drive the footer through its states; in the running state, click the footer to pop the task flyout. Click a tool to open its flyout; hover for the instant tooltip.

In Compact, tap the top-right Tools button (below View/Layers) to open the tool drawer; pick a tool to arm it — the button then shows the active tool.

2 · Task flyout — pops out, doesn't expand inline

Per your note, clicking the footer's Running n Tasks no longer grows the footer downward. Instead it opens a flyout hinged to the sidebar's right edge, aligned to the footer — the same motion as a tool's property flyout, just anchored at the bottom. Set the footer to Running above and click it to see it.

3 · Compact / phone — Tools drawer beside View & Layers

At LayoutSize.Narrow the app hides MainSideBar and moves View/Data/Map into the top LinkBar hamburger. The View page already floats a top-right column of round buttons (Camera/View + Layers) that open a right-edge drawer. The fix is simply: add Tools as a third button in that column, opening the same drawer — a grouped tool list, plus the active tool's options below it.

Why this beats a bottom tray or a top-left button

  • Consistency — reuses the exact pattern View & Layers use on mobile; nothing new to learn, and it drops into the existing floatingButtonsId column.
  • Reachable — top-right, not top-left, and the Tools button sits lowest in the column, so it's an easy right-thumb tap.
  • Scene stays clear — no persistent bottom strip covering the cave; the drawer is summoned only when needed.
  • Modal state stays glanceable — once a tool is armed, the floating Tools button shows that tool's icon and highlights, so you always know what's active without opening anything. Tap it again to put it away.

Rejected: a bottom tool tray (covers the view, doesn't match the app's mobile idiom) and a top-left button (hard to reach, hides active state). Per-tool live readouts that must stay visible during interaction (e.g. the measurement distance) remain small scene overlays; only the editable options live in the drawer.

4 · Per-page tool contract

The sidebar doesn't hardcode 3D tools — the page hands it a model; the sidebar (and the phone tray) render it. One model entry per new tool; new pages get the same home for free.

RenderingView { property list<ToolItem> tools: [ pickTool, measureTool, clipTool ] }   // View page

Repeater {

}

Appendix A · The "Update needed" signal — audit + dirty model

The footer's amber state needs a real "derived data is stale" signal. Audit of cavewherelib/src confirms your read: the current mechanism is one-way and silent.

What exists today

  • Four separate automaticUpdate flags, not one. Canonical is cwJobSettings::automaticUpdate (the setting the checkbox writes). cwRootData fans it out to only cwLinePlotManager + cwScrapManager (cwRootData.cpp:204-214). cwNoteLiDARManager keeps its own auto-update island, never wired to the setting; cwSketchManager has its own markDirty too.
  • Line plot = pure fire-and-forget. Every survey edit calls runSurvex(), which early-returns when auto is off (cwLinePlotManager.cpp:475) and records nothing. No dirty flag survives. Nothing to subscribe to.
  • Scraps = a real dirty set, but hidden. cwScrapManager::DirtyScraps (cwScrapManager.h:149) does accumulate while auto is off — but it's a bare QSet with a non-Q_PROPERTY getter and no change signal, so QML can't observe it.
  • No aggregator. Nothing unions line-plot + scrap (+ LiDAR + sketch) staleness. There is no user-facing "update needed" signal anywhere today.
  • Don't conflate with cwProject::modified — that's unsaved-changes (needs save), a different axis from derived-data-stale (needs recompute).

Latent bug the audit surfaced

The existing "Solve" (CavernOutputPage.qml → rerunSurvex()) and "Compute Scraps" (FileMenu.qml → updateAllScraps()) buttons are gated by the same automaticUpdate flag, so they no-op while auto-update is off — the only way to force a recompute today is to toggle the setting back on. A footer "Run" button needs an explicit path that bypasses the gate, so this gets fixed either way.

Proposed: one coordinator owns policy + aggregation

Neither host should own this state. cwRootData is already a god-hub, and cwJobSettings is a passive settings bag — the auto-update policy doesn't belong in either. Introduce a dedicated owner and invert control: managers become pure mechanism (compute + report dirty); a coordinator decides when to run and aggregates staleness.

1 · A tiny contract each pipeline implements — cwUpdatable

⚠️ Superseded by Stage 1 (A1), 2026-07-22. The as-shipped contract is the three-state updateState() observable below (not the original needsUpdate() + isUpdating() split) — see the "update-coordinator redesign follow-up" section for the authoritative description. This block and §2 are updated to match what shipped.

class cwUpdatable {
public:
    enum class State { Clean, Dirty, Working };
    virtual ~cwUpdatable() = default;
    virtual State updateState() const = 0;  // one observable: pending (Dirty) / running (Working) / done (Clean)
    virtual void update() = 0;              // recompute NOW — unconditional, no auto gate
    // (the QObject subclass also declares:  NOTIFY updateStateChanged() )
};

A survey edit now just marks dirty + emits updateStateChanged; the manager no longer decides whether to run and drops its automaticUpdate mirror + internal gate. update() does the work unconditionally — which also fixes the Solve / Compute-Scraps no-op bug. All three pipelines carry a pending-since-dispatch bit + an in-flight bit, so each reports a real Working while its async task runs (line plot via m_solving; scraps/LiDAR via m_taskRunning, added in R1) and Dirty for a fresh edit that arrives mid-run.

2 · The owner — cwUpdateCoordinator (new QObject)

class cwUpdateCoordinator : public QObject {
    Q_OBJECT
    Q_PROPERTY(bool automaticUpdate READ automaticUpdate WRITE setAutomaticUpdate NOTIFY automaticUpdateChanged)
    Q_PROPERTY(bool needsUpdate     READ needsUpdate                              NOTIFY needsUpdateChanged) // aggregate
public:
    template<class T> void add(T* u, QList<cwUpdatable*> dependsOn = {}); // register + connect + declare edges
    bool needsUpdate() const;           // any registered updatable is Dirty
public slots:
    void updateNow();                   // give up on the pass in flight, build its replacement, observe it
    void setAutomaticUpdate(bool on);   // toggling ON flushes everything dirty
private:
    void onChildStateChanged(cwUpdatable* u); // step aside if a cascade runs; else honour automaticUpdate()
    void finishCascade();               // clear the running flag, re-apply policy; skipped if the pass was given up on
    bool cascadeRunning() const;
    void dropRunningCascade();          // abandon() then deleteLater() the pass in flight
    void flushAfterCascade();           // re-apply policy to anything dirtied after its own node finished
    QPointer<cwUpdateCascade> m_cascade;
};

Superseded three times. This sketch originally showed the m_forcing run-until-settled latch (anyWorking(), clearForcingIfSettled()), deleted when the Stage-2 task tree was adopted 2026-07-25. It then showed that tree's surface (buildCascadeRecipe(), taskTreeRunning(), m_taskTreeRunner), all of which was deleted 2026-07-26 when the cascade moved to a pure AsyncFuture future DAG — see "TaskTree removed" below. It then showed the graph itself (startCascade, cascadeNode, driveToClean, waitForRun, and the quint64 generation threaded through them, plus m_cascadeGeneration), all of which moved out to cwUpdateCascade when the DAG was extracted 2026-07-26 — see "Extract the cascade DAG" below. The shape above is what the coordinator actually has: policy only. Ordering is the dependency edges themselves, and it is the cascade that follows them; supersede/abandon is dropping the pass object, not bumping a counter.

It owns the policy (the automaticUpdate flag, persisted to the same QSettings key so existing prefs migrate) and the aggregation. Auto-on: a child going dirty runs immediately. Auto-off: accumulate, and expose needsUpdate.

Follow-up — update-coordinator redesign (out of scope for #601; two sequential stages, from the F1 review): the F1 forced-cascade latch works but leans on two implicit facts — the coordinator reads different signals per pipeline (needsUpdate() for scraps/LiDAR, isUpdating() for the line plot), and settle-detection is an emergent effect of re-driving whatever became dirty rather than a known-complete signal. Stage 1 (contract level) — ✅ DONE (2026-07-22, enum shape, user-chosen over peer-signal). Unified per-pipeline staleness + busy into one observable: cwUpdatable now exposes a single pure-virtual State updateState() const returning enum class State { Clean, Dirty, Working } (replacing needsUpdate() + the defaulted isUpdating()), plus a peer-renamed updateStateChanged() signal. Dirty takes priority over Working — a pipeline re-edited mid-run reports Dirty so the coordinator re-drives update() and the restarter coalesces (no stale-flash). Structural F1-invariant enforcement: no default, so no pipeline can silently clear its dirty marker yet forget it is busy (the old isUpdating()==false trap is gone). The finishSolving() smell is gone too — it now emits updateStateChanged() on the real Working→Clean/Dirty transition, not a value-unchanged re-pulse. At Stage 1, only the line plot was observably Working (it clears dirty at update() start), while scraps/LiDAR held their dirty set to taskFinished and reported Dirty→Clean; the settle latch rested on that persistent Dirty. R1 (2026-07-22) closed that asymmetry — scraps and LiDAR gained the same two-bit model (m_workPending + m_taskRunning), so all three pipelines now report a real Working while their task runs and Dirty only for an uncovered edit; the in-flight bit is cleared on every completion path (finishScrapTask() at the scrap run-lambda's early returns + taskFinished; the LiDAR completion callback) so a leaked flag can't wedge the latch. Task-architecture investigation — Stage 2 engine (Qt 6.11, 2026-07-22): the async machinery sorts into three layers, and keeping them straight is the whole decision. (1) Reactive/dirty layer — the Clean/Dirty/Working observable and dirty propagation. This is Stage 1 and it is always ours: no task engine has any notion of data staleness, so nothing below can replace it. (2) Orchestration engine — runs the DAG, coalesces bursts, cancels superseded runs. This is Stage 2's swappable half. (3) Task primitives — QFuture/QtConcurrent/AsyncFuture Deferred, the low-level futures both engines sit on. The key architectural move: design the Stage 1 node contract (state() + a run() that returns a future) as the seam, so the Stage 2 engine is pluggable — AsyncFuture combine() today, a declarative recipe later — without touching Stage 1.

Two engine candidates. (a) AsyncFuture (already in the tree, we control it): observe(f).context(this,…) for edges, combine() (asyncfuture.h:1628) for fan-in joins, and Restarter (asyncfuture.h:1834, already the engine behind TriangulateRestarter) for burst-coalescing. Sits at the QFuture layer. (b) QtTaskTree (Qt 6.11 module Qt6::TaskTree, Technical Preview; upstreamed from Qt Creator, hardened there since 2022 across 100+ ops) — a declarative DAG engine that sits above the QFuture layer (it adapts QtConcurrent/QFuture as tasks). You describe an immutable Group recipe (nested sequential/parallel groups, WorkflowPolicy stopOnError/continueOnError/finishAllAndSuccess, typed Storage<T> for inter-stage data, per-task setup/done handlers) and hand it to a runner. The runner family covers the coalescing gap natively — a correction to the earlier note, which was scoped to raw QFuture::then() chains (single-shot, no restart): QSequentialTaskTreeRunner (enqueue queues while running, cancelCurrent() supersedes the in-flight run — exactly what AsyncFuture::Restarter does) and especially QMappedTaskTreeRunner<Key> (cancelKey/isKeyRunning/start(key,…)) which maps directly onto per-cwScrap* triangulation restart in cwScrapManager. Our cascade would be roughly Group{ sequential, linePlotTask, Group{ parallel, scrapTasks… }, sketchTask }, and the m_forcing latch is replaced by the runner's done-handler + isRunning().

Verdict: QtTaskTree is the right conceptual tool for Stage 2 — it is a declarative DAG engine and it fills the burst-coalescing gap, which is exactly Stage 2's shape. Two things hold it back from being the default right now: it is Technical Preview in 6.11 (API churn risk on a foundational subsystem — the real concern, not the maintainer), and we control AsyncFuture but not TaskTree (a softer risk, since Qt maintains it and Creator hardened it). Plan: do Stage 1 now in AsyncFuture, designed with the pluggable-engine seam above. For Stage 2, build a throwaway spike expressing the current line-plot → scraps → sketch cascade as a Group recipe driven by a QSequential/QMapped runner behind the Stage 1 seam; if it is clean and preview-stability looks acceptable, adopt it; otherwise ship Stage 2 on AsyncFuture combine() and revisit TaskTree once it leaves Technical Preview. Because Stage 1 is the seam, that engine swap is cheap either way.

RESOLVED AGAINST — 2026-07-26. The outcome is this paragraph's own "otherwise" branch. TaskTree was adopted 2026-07-25, then removed 2026-07-26; Stage 2 now ships on AsyncFuture, with combine(AllSettled) doing the fan-in joins exactly as the fallback predicted. Everything below describing TaskTree as the engine is historical record, not current design — read it for the reasoning, not for what the code does. What decided it: once D1 gave cwUpdatable::run() a QFuture, the adapter (cwUpdatableTask) existed only to convert that future back into a done() signal so a framework could rebuild a completion graph we already had. Removing it cost ~6 net lines of production C++ and bought back: a true per-node DAG instead of depth layers (a dependent waits on its own parents), no Technical-Preview churn risk on a foundational subsystem, no add-on install for every developer and CI image, the Conan-Qt build path unblocked in principle (see issue #635), and an engine written in the idiom the maintainer reasons in. What it cost: 3 extra event-loop turns to settle (6 vs 3), and finishAllAndSuccess — one word in TaskTree — became three hand-built pieces (AllSettled, a dual-handler .context(), and an explicit Deferred). Tradeoffs found by building it — the real costs, in priority order. (1) Cancellation — but the gap is PRE-EXISTING, not TaskTree's fault (corrected 2026-07-25 after reading the AsyncFuture docs + our tasks). Cancelling or resetting the tree destroys cwUpdatableTask and stops us waiting while the pipeline keeps computing — but that is not a TaskTree limitation, it is true of our pipelines already. AsyncFuture does propagate cancellation ("Full chain cancellation propagation"; chain.cancel() flows back to the source, and Restarter bakes cancel-in-flight in). Two things stop it landing: the documented context() fence — "destroying the context object only cancels the Observable's returned future — it does not back-propagate to the upstream worker" (asyncfuture/README.md:877; cross it with an explicit chain.cancel() or Restarter) — and, more fundamentally, QtConcurrent workers never abort mid-function unless they poll promise.isCanceled(), which requires a QPromise<T>& parameter. Verified: cwLinePlotTask.cpp, cwTriangulateTask.cpp and cwScrapManager.cpp contain zero QPromise/isCanceled — both dispatch plain callables through cwConcurrent::run. So today "cancel" anywhere in the cascade means discard the result, not stop the CPU (cwScrapManager.cpp:113 already calls TriangulateRestarter.future().cancel() in its destructor — flag flips, result dropped, worker runs on). Conclusion: cancellation is NOT an argument against adopting TaskTree. It is three independent layers: (a) tree cancel destroys the node — have it; (b) the D1 run()→future seam — landed 2026-07-26; the node holds the pipeline's future, and a cancelled run now ends the node instead of hanging it, though nothing calls cancel() on that future yet; (c) cooperative workers actually stop the work — missing and orthogonal to TaskTree. Feasibility of (c) differs sharply per pipeline: triangulation is amenable (per-scrap cwConcurrent::run, poll between scraps; cwConcurrent::run forwards to QtConcurrent::run which already supports the QPromise overload, so it is a per-task lambda change, not a wrapper change), whereas the line plot is effectively uncancellable mid-solve — its real work is one blocking cwCavernRunner::run(svxPath, output3dPath) call into the survex C library, so it can only be cancelled between phases. The pipeline we would most want to cancel (a big-cave solve) is the one we cannot, without survex hooks. The QPromise pattern is already established elsewhere in the tree (14 files: LAZ loading, geometry intersecter, sketch manager, compass importer). (2) The add-on is not in a stock Qt install, so every developer and CI image must install it. The optional-CMake pattern avoids hard-breaking those machines, but the cost is that we then carry two cascade implementations behind an #ifdef — worse long-term than either alone. Adoption should mean deleting the latch path and requiring the add-on, not keeping both. (3) Technical Preview churn. The API surface we actually depend on is modest and mostly structural: Group/GroupItems, sequential/parallel, finishAllAndSuccess, QCustomTask + QDefaultTaskAdapter, withLog, QSingleTaskTreeRunner, and the SetupResult/DoneResult/DoneWith enums. A rename sweep would be mechanical; a semantic change to workflow policies would not be. (4) No timeout — decided 2026-07-25. The spike briefly carried withTimeout(60s) as a hang guard; it is now removed. A timeout is the wrong tool here on both halves: our tasks are not cancellable mid-run (see (1)), so firing one abandons the wait while the work continues regardless, and a big cave's solve or a full re-triangulation is legitimately long, so any fixed ceiling eventually turns correct behaviour into a spurious error. A node that never reaches Clean is a bug in that pipeline's state reporting — it should be fixed there, not papered over with a deadline. This raises the stakes on the per-node done signal (that is why A1/R1's Working bit had to be exactly right), and it removes the one place the tree would have produced an Error result. (5) Recipes are immutable per run, so any dynamic DAG is rebuilt each time — fine at our scale (3 pipelines), and it is what makes the start-time dirty check correct.

Late-edit gap — found and FIXED 2026-07-25. A recipe is fixed once the tree starts, so a pipeline dirtied after its own node reported done (but while the tree is still alive on a sibling) was skipped: onChildStateChanged() defers to the running tree, and nothing re-drove it when the tree ended. With automatic update on that stranded the edit until an unrelated later trigger — a real defect, since auto-update promises to recompute. Fix is cwUpdateCoordinator::flushAfterCascade(), posted Qt::QueuedConnection from the tree's done handler (starting a cascade inline would destroy the tree mid-emission — the same hazard QMappedTaskTreeRunner works around with release() + deleteLater() in its own done handler). Deliberately gated on automaticUpdate(): a forced Run resolves the cascade it started (derived dirtying is ordered by the dependency edges) but does not chase edits the user made after pressing it — that is what the staleness report is for. New testcases/test_cwUpdateCoordinator.cpp covers both halves with fake pipelines; the first case was negative-checked (fails 3 assertions with the flush removed).

DAG re-arch — QBarrier makes a true DAG expressible (found 2026-07-25). The obvious reading of TaskTree is that nested Groups can only describe series-parallel graphs, so per-node readiness would have to be hand-rolled in cwUpdatableTask — which would hollow out the reason to adopt the add-on. That reading is wrong: QtTaskTree/qbarriertask.h ships the cross-branch join. QBarrier is a counting barrier (setLimit() / advance() / done()), QStoredBarrier = Storage<QStartedBarrier> puts one in tree Storage so sibling branches share it, and barrierAwaiterTask(storedBarrier) is a node that does nothing but block until the barrier is satisfied. Also present: signalAwaiterTask(sender, signal) (a node that finishes on any QObject signal) and the When(kicker) >> Do(...) sugar. The DAG shape is therefore: one parallel Group holding every pipeline, each pipeline's branch being Group { sequential, barrierAwaiterTask(depA), barrierAwaiterTask(depB), pipelineTask }, with each pipeline task advancing its own barrier when it completes. Per-node readiness, no layer barriers, arbitrarily many dependencies each.

Recommendation: take the API half now, defer the execution half. The reason is that today it would buy exactly nothing measurable. There is precisely one root (LinePlotManager) and one dependent layer of two, so a barrier after a single-node layer is the real dependency — layering and a full DAG produce identical schedules. Over-synchronization only starts costing wall-clock when a second independent root appears with a different duration (a coordinated cwImageCompressionUpdater, a keyword index, sketch derivation). Second reason: this ordering is work-avoidance, not correctness. If scraps ran before the solve they would triangulate against stale positions, then stationPositionInScrapsChanged would dirty them and they would re-run — wasteful, self-correcting, never persistently wrong. The data dependency is enforced by the signals; the declared edge is an optimization restating it. So: (a) DONE 2026-07-25 — m_dependencies is now QHash<cwUpdatable*, QList<cwUpdatable*>>, add() takes QList<cwUpdatable*> dependsOn = {} (call sites read add(ScrapManager, {LinePlotManager})), and dependencyDepth() is now max over parents rather than a single-parent chain walk — a pipeline lands one layer below its deepest dependency, so it can never share a layer with a dependency that is itself still waiting. Recursion is bounded by remainingHops (pipeline count) so a mis-registered cycle terminates. The destroyed-handler now also purges the pipeline from every other pipeline's dependency list, so a survivor is not left ordered behind something freed. Execution strategy is unchanged (still depth layers). New test "A pipeline runs after its deepest dependency, not its first" builds root → middle → leaf with leaf depending on both; negative-checked by reverting to first-parent-wins, which fails it (leaf.updateCount() 1 vs 0). A companion case now also pins that a mis-registered cycle terminates rather than recursing until the stack runs out; (b) trigger for the execution half, the first second-independent-root or first two-dependency pipeline. Invariants the AsyncFuture cascade introduced (added 2026-07-26)

Four things the code now depends on that are not obvious from reading it, recorded because each one is easy to "simplify" back into a bug. Where they live: waitForRun(), completeWith(), joinNodes(), driveToClean() and pipelineName() all moved from cwUpdateCoordinator.cpp to cwUpdateCascade.cpp when the DAG was extracted 2026-07-26; the names below are unchanged, only the file is.

(1) A pipeline's run future is shared, and no consumer may cancel it. run() and currentRun() hand out the pipeline's own QPromise future, and AsyncFuture's observe().context() pushes a cancel back up the chain it observed — so one node giving up would cancel the run itself, and with it every other waiter's work. This is why waitForRun() observes AsyncFuture::shield(run). shield() and its enum class CancelPropagation { Propagate, Blocked } are new to the asyncfuture submodule and CaveWhere-authored (bumped ed7f3c5a → 45f55f7b, pushed to origin/master of the fork); the change is additive — the policy parameter defaults to Propagate, reproducing the old path exactly — so no existing AsyncFuture site in the tree is affected. Note what shield does not do: the policy only removes the upstream pushCancel watcher (asyncfuture.h:596); the onCanceled → cancel() watcher at :583-591 is installed unconditionally, so a canceled upstream still settles the shield — measured, it arrives as a completion, which is why waitForRun()'s cancel branch is currently unreachable. The shield could instead be cached at the producer (beginRun()) so no consumer anywhere can cancel; see the follow-up below for why the naive version of that breaks things.

(2) "Already finished ⇒ complete synchronously" is correctness, not optimization. completeWith() and joinNodes()'s all-settled short-circuit exist because Deferred::complete(QFuture) and combine() always install a QFutureWatcher, even for a finished input — and updateNow()'s pass.isFinished() branch depends on that short-circuit reaching it. A cascade that found nothing to do must end synchronously: otherwise it is still "running" for one event-loop turn, and an edit arriving in that turn is deferred by onChildStateChanged() to a cascade that has already ended, so the edit never runs. This regression was real and was caught only by a cwLinePlotManager test, never by a coordinator test; there is now a coordinator case for it ("A cascade with nothing to do ends before the next edit arrives", negative-checked — removing the shortcut gives updateCount 0 vs 1).

(3) Supersede and abandon are one mechanism, and it takes two halves: abandon() then deleteLater(). This was the generation counter, m_cascadeGeneration, until the DAG was extracted 2026-07-26. It covers the same three cases — pressing Run twice, a registered pipeline being destroyed, and the coordinator's own destruction — and is still deliberately not a cancel: a canceled continuation still runs its body, and it is exactly the one that would read the pipeline the pass was dropped because of. Destroying the cascade is what drops those queued continuations unrun, since each is bound to it as its context object. But destruction alone is not enough, because a pass can be given up on while its own walk is still on the stack — driving a pipeline can destroy one, which lands in dropRunningCascade() — so the object has to outlive that frame. abandon() is what keeps it inert while it does: driveToClean()'s if(m_abandoned) check, placed before any dereference, is what makes the rest of the walk a no-op over a snapshot that may now hold a freed pointer — load-bearing for memory safety, not tidiness. Both halves are pinned by test: removing the check segfaults "A pass given up on from inside its own walk stops reading its snapshot". updateNow() checks isAbandoned() on both its completion paths for the same reason — a pass given up on must not report itself finished from under the replacement that superseded it.

(4) The cascade has no failure channel. With AllSettled joins and node.complete() on cancel, a cascade always succeeds; staleness is the only report of what still needs work. That is continuity with TaskTree's finishAllAndSuccess, not a change — but with DoneResult/DoneWith gone there is no longer anywhere in the code that says so.

Follow-ups from the 2026-07-26 review

Extract the cascade DAG out of cwUpdateCoordinator — DONE 2026-07-26. The class had grown to ~172 of 324 lines of graph/future algebra (completeWith, joinNodes, startCascade, cascadeNode, driveToClean, waitForRun) against ~90 lines of actual policy. That algebra now lives in cwUpdateCascade (cwUpdateCascade.{h,cpp}), built from (QList<cwUpdatable*>, QHash<cwUpdatable*, QList<cwUpdatable*>>) and driven by one start() returning one QFuture<void>. The coordinator is down to policy: automatic-update flag, staleness aggregate, registration, and the decision to start a pass. The object is the epoch, as planned: m_cascadeGeneration and the quint64 generation parameter threaded through four signatures are gone, every continuation is bound to the cascade as its context object, and superseding a pass is dropping it.

One thing the plan did not anticipate: destruction alone is not enough, so the epoch needs abandon() alongside it. start() drives pipelines synchronously, and a pipeline destroyed from inside a drive reaches cwUpdateCoordinator::dropRunningCascade() — so a pass can be given up on while its own walk is still on the stack, which is exactly when the object must not be deleted. dropRunningCascade() therefore sets the flag, then deleteLater()s: the flag makes driveToClean() a no-op from that instant (the same role the generation compare had, in the same place, before any dereference), and the deletion is what drops the queued continuations. The two are not redundant. The window between them is real and is not only a test artifact: a deferred delete posted at loop level N is not delivered inside a nested loop at N+1, and the pipeline destructors pump exactly such a loop (#638). updateNow()'s completion handler checks isAbandoned() for the same reason — a superseded pass that settles in that window would otherwise clear m_cascadeRunning out from under its replacement, handing the run decision back to onChildStateChanged() while a cascade is still driving. Both halves are mutation-checked (removing either fails a case; removing abandon() fails two).

Two behavior changes the 2026-07-27 review pass added, both in the coordinator's policy half. (1) Both completion paths are guarded, not one. The extraction moved the supersede check out of finishCascade() and re-attached it only to the asynchronous handler, so the synchronous pass.isFinished() branch lost a guard the generation compare had covered. A pass given up on during its own walk finishes immediately — every node left short-circuits — so that branch is exactly the one an abandoned pass takes. Latent rather than live: nothing re-enters updateNow() synchronously today (onChildStateChanged steps aside on cascadeRunning(), flushAfterCascade is queued, the destroyed handler only drops), and CP6's Run button is the caller that would make it reachable. (2) Giving up on a pass now re-applies policy to the survivors. dropRunningCascade() served two meanings — "a replacement is coming" (updateNow) and "give up entirely" (the destroyed handler) — and only the first left anything to pick the work back up. So destroying one registered pipeline gave up on every other pipeline's ordered work too, and with automatic update on those survivors waited for whatever edit happened to arrive next, having already been told their edit was in hand. The destroyed handler now queues a flushAfterCascade() after scrubbing; queued both so the fresh pass starts off a clean stack rather than inside a destructor, and so it is dropped if the coordinator is going down too. This is what makes (1) safe: the guard stops the give-up path reporting a finish, and the flush is what replaces it. Pre-existing — the generation bump had the same hole — but the extraction made it cheap to see and to close.

Move shield() to the producer. Today it is at the consumer (waitForRun), so the invariant in (1) above is one every future consumer must remember — CP6's footer, the scoped force, a test. It belongs to the owner of the run. The naive version breaks correctness: shield() always routes through a watcher (watch() never short-circuits on isFinished()), so a blanket return shield(m_run->future()) is never synchronously finished — which defeats invariant (2) and reintroduces the deferred-edit bug. The version that works caches the shielded future in beginRun() and returns QtFuture::makeReadyVoidFuture() when idle, preserving the documented not-running semantics exactly. Residual cost needing sign-off: the shielded future finishes one turn after endRun(), so "Working lasts exactly as long as the run's future" becomes approximate.

Fix the always-install-a-watcher behavior upstream in AsyncFuture. completeWith() and the all-settled short-circuit are workarounds for Deferred::complete(QFuture) and combine() installing a QFutureWatcher even for already-finished inputs. The fork is ours. Doing it upstream deletes ~20 lines here and fixes it for every other AsyncFuture site (cwSaveLoadPrivate, cwSketchManager, cwScrapManager). It became worth doing at the point the workaround turned correctness-load-bearing (invariant 2) rather than merely a saved event-loop turn. Kept out of the engine-swap commit: shared dependency, own test suite.

The re-drive chain retains one link per iteration. When a run finishes with the pipeline Dirty again, completeWith(node, driveToClean(...)) takes the node.complete(next) branch, and DeferredFuture::complete(QFuture) holds a strongRef per watcher — so link k cannot be released until link k+1 settles. Each link is roughly a DeferredFuture + 3 watchers, plus shield()'s deferred and its 2, so N re-drives hold ~8N QObjects live at once, collapsing only when the pipeline finally reports Clean. The deleted cwUpdatableTask did not have this — it re-armed with emit done() rather than completing one deferred with the next one's future. Retention, not a leak, and bounded by how long a user can hold a pipeline dirty; recorded as a real cost of the future-chain formulation that the AsyncFuture-vs-TaskTree comparison did not capture.
