The Coordinate String Is the Source of Truth

A fix station stops storing easting/northing/elevation and stores only the string the coordinate was written as. The numbers become a derived, in-memory reading of that string under the row's current coordinate system. Follow-on to bca9c14f "Keep the coordinate string the user typed", which this plan partly reverses.

Where this came from. Commit 12 stored the typed string beside the three numbers, which forced a second stored field — coordinateTextAxisOrder — to record which axis the string led with, because the row's CS can change after the text was typed. The question "isn't the axis order implied by the coordinate system?" is the thread that unravelled it: the order is implied, but only if the string is re-read every time the CS changes — which is only safe if the string, not the numbers, is the thing being stored. Removing the duplication removes the field.

2. Why — the duplication and what it cost

After bca9c14f a fix station stores two representations of the same coordinate: three doubles, and a string. Whenever two fields can disagree, code appears whose only job is to stop them disagreeing. All of the following exist for that reason and no other:

MechanismWhereExists only because…
coordinateTextAxisOrdercwFixStation, proto field 10 …the string's meaning depends on an order the CS already implies, but the stored string was read under a possibly-older CS.
clearCoordinateText() in all three component setterscwFixStation.cpp:100-106 …any write to a number makes the string a lie.
rendersRowAsIscwFixStationModel.cpp:263 …a machine-generated string must not be mistaken for the user's, or every opened-and-closed cell would store one.
keptText/keptOrder normalizationcwFixStationModel.cpp:277 …"no stored text" has to be a single state or two equal fixes compare unequal.
The identity guard's order clausecwFixStationModel.cpp:253 …re-committing a byte-identical string is a no-op unless the CS flipped underneath it.

None of that is wrong. It is all correct, tested, and each piece is individually justified — which is exactly what makes it the wrong shape: five interlocking guards maintaining an invariant that disappears if the second representation does. The transposition bug they collectively work around is not fixed by any of them; it is merely reported (the domain check flags it and the user retypes).

The whole change in one picture. The bottom half has one stored field where the top half has two, and the box on the right stops being a defect report and becomes a repair.

3. The data model after the change

class cwFixStationData : public QSharedData {
    QUuid   Id;
    QString StationName;
    QString InputCS;
    double  HorizontalVariance = 0.0;
    double  VerticalVariance   = 0.0;

    QString Coordinate;                 // the truth

    // Derived from (Coordinate, InputCS). Never serialized. Recomputed by
    // refresh(), which is the only writer.
    double  Easting  = 0.0;
    double  Northing = 0.0;
    double  Elevation = 0.0;
    bool    HasElevation = false;
    cwFixStation::CoordinateState State = cwFixStation::Empty;
};

refresh() is called from exactly two setters — setCoordinate() and setInputCS() — and does:

void refresh() {
    if (Coordinate.trimmed().isEmpty()) { Easting = Northing = Elevation = 0.0;
                                          State = Empty; return; }
    const auto result = cwCoordinateText::parse(Coordinate, cwUnits::Metric,
                                                cwCoordinateText::axisOrderFor(InputCS));
    if (result.hasError())               { Easting = Northing = Elevation = 0.0;
                                          State = Unreadable; return; }
    const auto c = result.value();
    Easting = c.easting; Northing = c.northing;
    HasElevation = c.hasElevation;
    Elevation = c.hasElevation ? c.elevation : 0.0;
    State = Valid;
}
Why cwUnits::Metric and not the project's unit system. A stored string always spells out its elevation unit — textToStore() already guarantees that, and §5's migration and §6's component setters both produce strings that do. A bare elevation therefore cannot reach refresh(), so the unit system it would have been resolved against is irrelevant, and passing Metric unconditionally keeps cwFixStation free of a dependency on project settings it has no business reading. This is load-bearing: it is what makes a fix's meaning independent of the project's display units. Guard it with a test that flips the project to Imperial and asserts the numbers don't move.

operator== drops the three doubles and compares Coordinate. They are a pure function of (Coordinate, InputCS), both already compared, so including them would be redundant — and would make an equality that could never fail into one that silently depends on refresh() having run.

4. Coordinate states

The Unreadable state exists because of a requirement that arrived late and is easy to under-serve:

A hand-edited file must not lose the user's text. Projects are readable on disk. If someone edits a coordinate by hand and gets it wrong, CaveWhere flags it in the UI and writes the same bytes back on save — it never drops the string, never "repairs" it, and never silently substitutes a number. parse() is therefore authority on the editor path only (cwFixStationModel::setCoordinateText refuses before storing); on the load path the bytes are taken as-is.

All four reach the UI as of commit 4. 2026-07-28 The cell renders the text rather than the zeros the row reports whenever there is a coordinate error, tints it, and puts the message in the same inline warning the domain check uses — the two can never both speak, since the domain check defers on any state but Valid. Unreadable carries parse()'s own reason, read in the row's axis order, rather than a restatement that would drift from it. The whole surface is one role, cwFixStationDiagnosticsModel::CoordinateErrorRole, so the page and the popup cannot disagree.

Empty is the exception, deliberately. It has no coordinate error, so it falls through to CoordinateText.format(0, 0, 0, …) and renders "0, 0, 0m" — not a blank cell, whatever earlier drafts of the table above said. That rendering is load-bearing: cwFixStationModel.cpp:293-302 compares against it so that opening the cell and leaving it can't turn "not entered" into "entered at the origin". The row is still indistinguishable on screen from a fix genuinely at the origin — the same complaint that motivated the NoSystem fallback — but nothing has decided that a row nobody has filled in yet deserves a warning.
§11's resolution adds a fourth condition. shipped in §11.1 as NoSystem A row with a blank inputCS is an error: with no coordinate system there is no axis order, so the two numbers cannot be said to mean anything. The string is kept and the components are not derived — behaviorally identical to Unreadable, but for a different reason, and it wants a different message ("choose a coordinate system", not "this text can't be read"). It went in as the fourth state() value rather than a separate predicate, with refresh() returning early on a blank CS: every consumer already switches on state(), and the guard state() != Valid that cwFixStationDiagnostics uses picks it up for free.
This row is not rare, and an earlier draft of this section said it was. The claim was "only reachable from a hand-edited file once §11.1 lands, since new rows default to Lat/Long". Three ordinary paths produce a NoSystem row: fromProtoFixStation on any project saved before this work, cwSurvexImporter::parseFix on an svx whose *fix has no *cs before it (the ordinary local-grid survey), and every row the old picker's Local mode wrote, which is what a blank CS used to mean. Only the last of those is anything like a hand edit.

That understatement had a cost: it is why nothing checked state() before writing *fix, and a CS-less fix exported as *fix <name> 0 0 0 — silently moving the whole cave to the origin — until the §11.1 review caught it. Treat "the numbers are kept as text" as a claim about storage only. Every consumer that reads easting()/northing()/elevation() gets 0 on any state but Valid, so each one needs its own guard until R1 gives them a shared predicate.

4.1 The elevation has its own "not entered"

decided A two-component string — "46.1, -115.6", the shape a coordinate copied off a map arrives in — means the elevation was not entered, and stays that way across a save. This is parse()'s existing hasElevation flag, promoted from a transient parse detail to a persistent property of the fix, and it settles the old question of what a two-component paste does to an elevation already on the row: nothing, because the string now says so out loud.

enum CoordinateState { Empty, Valid, Unreadable, NoSystem };

CoordinateState state() const;
bool hasElevation() const;   // false for a two-component coordinate
double elevation() const;    // 0.0 when !hasElevation()
Downstream this is a diagnostic distinction, not a computational one — say so plainly rather than letting callers discover it. Survex's *fix takes three numbers; there is no way to anchor a station in two. So every consumer — cwSurvexExporterUtils::writeFixStations, cwFixStationValidator.cpp:243,476, cwGridConvergence.cpp:141, cwTripCalibration.cpp:266 — keeps reading elevation() and keeps getting 0.0, which is exactly what they get today. Nothing about the solve changes. What changes is that the row can now say its elevation is missing instead of claiming it is sea level, so the diagnostics can flag it the way they already flag a half-entered horizontal pair ("One zero is not two" — test_cwFixStationDiagnostics.cpp:103).

Whether a missing elevation should actually raise a warning is a product question, not a technical one, and it is deliberately not decided here: the state makes the warning possible. Adding it is a one-line follow-up once you have looked at a real project and decided whether it would be useful or merely noisy.
The trap this state exists to avoid. cwFixStationDiagnostics currently infers "nothing entered yet" from the coordinate being at the origin — see the section "A fix still on the origin has no coordinate to judge" in test_cwFixStationDiagnostics.cpp:84. If an unreadable string fell back to (0, 0, 0), that guard would read a corrupted coordinate as an unentered one and show no warning at all — the exact failure the hand-edit requirement is meant to prevent. So the guard must stop inferring intent from a value and ask state() == Empty instead. That is a strictly better rule anyway: it also stops treating a legitimately-entered "0, 0, 0" as unentered, which is a real (if rare) coordinate in some local grids.

5. Proto schema

5.1 Target shape

message FixStation {
    optional string id                 = 1;
    optional string stationName        = 2;
    optional string inputCS            = 3;

    reserved 4, 5, 6, 10;
    reserved "easting", "northing", "elevation", "coordinateTextAxisOrder";

    optional double horizontalVariance = 7;
    optional double verticalVariance   = 8;

    // The coordinate, as it was written. The only stored form: the three
    // numbers are read back out of this under the axis order inputCS implies.
    // Kept verbatim even when it doesn't parse. Absent ⇒ no coordinate.
    optional string coordinate         = 9;
}

The AxisOrder enum goes with field 10 — nothing else referenced it. Renaming field 9 coordinateText → coordinate is free: protobuf identity is the field number, so the rename alone needs no conversion.

No in-app migration. decided The numbers come out of the schema completely, and the one existing project with fix stations is converted once by the script in §5b before it is ever opened by a build that has this change. fromProtoFixStation therefore has no legacy branch at all: it reads field 9 and nothing else. This is what "remove them entirely" buys — the alternative kept four dead fields alive in the schema to serve a conversion that runs exactly once.
"Never shipped" is verified, for all five fields. 2026-07-27 This is the fact the whole removal rests on, and it is easy to talk yourself out of, because origin/dev does carry easting/northing/elevation and the version map labels the current version {9, "2026.4"} — which reads like the fields went out in the 2026.4 release. They did not:
  • git show 2026.4.3:cavewherelib/src/cavewhere.proto | grep FixStation → no match. Same for 2026.4, 2026.4.1, 2026.4.2.
  • git ls-tree -r --name-only 2026.4.3 | grep cwFixStation → 0 files. No release contains any fix-station code at all.
  • git merge-base --is-ancestor 3619b2e3 <tag> → NO for all four tags. "Add fix-station data model…" (2026-05-09) never reached the release branch, even though 2026.4.3 was cut on 2026-05-24, two weeks later.
So no released build can write a FixStation message, and fields 4, 5, 6, 9 and 10 are equally unshipped. The only files that carry them were written by dev-branch builds since 2026-05-09. Nothing here is a compatibility obligation to a user base; the script exists to protect working projects.
The consequence: version 9 names two different schemas. protoVersion() was already 9 when fix stations landed on dev and was never bumped, so a v9 file written by 2026.4.3 has no FixStation message while a v9 file written by a dev build has one full of numbers. The version number alone cannot tell them apart, and that is what shapes the gate below — a plain fileVersion < 10 ⇒ refuse would reject every legitimate 2026.4.x project, none of which needs migrating.
The hazard this creates, and the guard it needs. loadMessage() parses with ignore_unknown_fields = true (cwSaveLoad.cpp:957). So a build with this change opening an unmigrated project does not fail — it silently discards every easting/northing/elevation key, shows every fix station as having no coordinate, and writes that loss back on the next save. One mis-ordered step (open before migrate) destroys the coordinates.

So the version gate is not optional and is not a nicety. At cave load (cwSaveLoad.cpp:2751), if fileVersion.version < 10 and fixstations_size() > 0, refuse the load with an error naming the script. It is the only thing standing between a stale checkout and the project, so it should be a hard failure, not a warning that can be clicked through.

Both halves of that test are load-bearing, and neither can be dropped. Without fixstations_size() > 0 the gate rejects every 2026.4.x project, which is at version 9 and has nothing to migrate (see the ambiguity callout above). Without fileVersion < 10 it rejects projects it has already migrated. And there is no third, more precise test available: once the fields are reserved, ignore_unknown_fields eats the numbers before the loader can look at them, and a fix station with no coordinate is indistinguishable on the wire from a genuinely empty "Mark Station as Fixed" row. The unit the gate can reason about is the file, not the row — any file that has fix stations and is still at version 9 has not been through the script, and that is exactly the set at risk.
Deferred to the pre-release save/load audit: the version bump and the gate. decided 2026-07-28 Commit 2 as built reserves the fields and ships the script, and does not touch cwRegionIOTask::protoVersion() or cwSaveLoad. The version number is being bumped once, deliberately, in a save/load audit before release rather than piecemeal per schema change — and the gate above is written in terms of that number, so it has to travel with it.

What that leaves standing, stated plainly: the hazard two callouts up is unguarded. A build with this change opening an unmigrated project silently reads every fix station as coordinate-less and writes that loss back on the next save. Until the audit lands, the script is the only protection, and it has to be run before the project is opened rather than after. The one project this applies to is in git, and the script writes a .bak besides, so a mis-ordered step is recoverable — but it is recoverable by hand, not prevented.

When the audit does bump the number, the gate is the paragraph above, unchanged: the two-part test is what makes it correct, and the ambiguity that forces it does not go away with time.

A row with no coordinate system is the one the migration has to be most careful with 2026-07-28, and the user's own project has one (an svx *fix with no *cs before it — an ordinary local grid, not corruption). Three things had to hold, and each now has a test that a mutation kills: the numbers are written down easting-first, because they are all that is left of the fix; nothing asks PROJ for an axis order that does not exist, since asking raises MissingProjError and aborts the whole run on a machine with no PROJ, over a row whose answer never depended on it (a CS of nothing but spaces is the same non-answer); and the round-trip check still covers the row, because a silent drop here is invisible to everything else — the application will read no numbers back out of a NoSystem row at all. That last point is the trap worth stating plainly: the script's round-trip check and the application's reading of the row disagree on purpose. The check reads the text easting-first and finds the numbers; the application refuses to read it at all until the user names a system. The numbers survive as text, not as a coordinate. On the C++ side the matching gap was that a CS-less row holding text that also can't be parsed must still be NoSystem, not Unreadable — the two are behaviorally identical (string kept, components 0) and want opposite messages, which is what commit 4 leans on.

The axis order needs PROJ, and the script gets it from PROJ rather than guessing. This is the one thing a pure JSON transform can't answer for itself: axisOrderFor is cwCoordinateTransform::isGeographic, which is proj_create plus proj_get_type. The script takes pyproj if it is importable and falls back to PROJ's own projinfo command (geographic ⇔ the WKT2 it prints begins GEOGCRS[), and refuses to run rather than assume when it has neither. A CS PROJ can't create at all is not geographic, which is what isGeographic answers and therefore what the application will read the row back under. The conversion tests stub this out, so they run anywhere; one test pins the stub to the real resolver and skips when no PROJ is installed.

The conversion rule per fix station, in the order the branches must be tested:

Commit 1 sharpened the middle test, and the script should follow it. The tree below decides whether to keep the user's string by asking whether coordinateTextAxisOrder matches axisOrderFor(inputCS). Ask instead whether the string, parsed under axisOrderFor(inputCS), reproduces the row's three numbers exactly — same question in the common case, but it also catches a case the order test misses: a two-component string ("46.1, -115.6") sitting beside a non-zero elevation, which bca9c14f could produce and which the order test would keep, silently dropping the elevation. cwProtoUtils::fromProtoFixStation already applies the sharper rule, so the script and the loader agree branch for branch.
The tree is missing a branch, and without it the script destroys a hand-edited coordinate. Its first test asks for three zeros and no coordinateText. A row with three zeros and a string that doesn't parse — the hand-edited file §4 is about — therefore falls through to the reproduce-the-numbers test, fails it (unreadable text reproduces nothing), and gets the numbers written out as "0, 0, 0m". The user's text is gone, which is the one thing §4's callout says must never happen. The loader does not have this hole: its rule is !text.isEmpty() && (!hasNumbers || saysWhatTheNumbersSay()), so with no numbers to fall back to it keeps the text unconditionally, including text it can't read. Test the branches in this order, which is the order the loader tests them:
  1. No coordinateText and all three numbers zero ⇒ emit no coordinate key (never filled in).
  2. coordinateText present and all three numbers zero ⇒ keep it verbatim, whether or not it parses. There is nothing else the row could mean.
  3. coordinateText present and it reproduces the three numbers exactly under axisOrderFor(inputCS) ⇒ keep it verbatim.
  4. Otherwise ⇒ write the three numbers out with format(), in meters.
The figure below still draws the old middle test (coordinateTextAxisOrder == axisOrderFor(inputCS)) and omits branch 2 — read this list, not the diagram.
The script's decision per fix station. The red branch is the one that is easy to get wrong: a row created by "Mark Station as Fixed" and never filled in has three zeros and no string, and emitting "0, 0, 0m" for it would convert not entered into entered at the origin.
The conversion is bit-exact, and that is checkable rather than hopeful. Python's repr(float) is the shortest round-tripping representation — the same guarantee QLocale::FloatingPointShortest gives shortestNumber() — so each horizontal reproduces the identical double. The elevation is written in metres, so C++ will read it back through convert(x, Meters, Meters) = x * 1.0 / 1.0, exactly x, dodging the m→ft→m ulp loss that costs ~12.5% of doubles an ulp on the imperial path. Verify it rather than asserting it: have the script re-read what it wrote and compare against the original doubles, and fail loudly on any row that doesn't reproduce.

6. Component setters and the CS-first precondition

setEasting() / setNorthing() / setElevation() survive, because ~30 call sites use them and both importers write components directly. They invert: instead of writing a number and clearing the string, they write a number and re-format the string from the three current values under axisOrderFor(inputCS()), in Metric.

This introduces a precondition that did not exist before and must be documented on the header:

An earlier draft said "so no importer change is needed". That was wrong, and §11.1 had to change cwSurvexImporter anyway. Setting the CS first is necessary but not sufficient: on a fix that has no CS at all, the one-at-a-time setters don't compose. Each writes the string and reads it straight back, and with no axis order the read returns nothing — so the second setter spells out what the first lost, and the third spells out what the second lost. Three writes leave one number.

An svx *fix with no *cs before it is exactly that case, and it is the ordinary local-grid survey. The fix is cwFixStation::setCoordinate(double, double, double) — one write, one read-back — and any caller holding three numbers must use it. Three real callers were hit: fromProtoFixStation, cwSurvexImporter::parseFix, and a test helper whose silent zeroing of a survey's world origin is how the whole thing was noticed. Walls is genuinely unchanged, since it always sets a CS first — so the statement about Walls survives; the one about svx does not.
Set inputCS before any component. A bare number has no meaning without an axis order, and the order comes from the CS. Writing a component while inputCS is still empty formats the string as easting-first; setting a geographic CS afterwards then re-reads it latitude-first and the two horizontals swap. Both importers set the CS on the line before the components — cwSurvexImporter.cpp:1106 and cwWallsImporter.cpp:85,96 — and a test should pin that ordering so a future edit can't quietly reverse it.

The Walls geographic path is worth tracing because it looks wrong and is right: it sets a geographic CS, then setEasting(longitude) and setNorthing(latitude). format() under LatitudeLongitude writes northing first, producing "lat, lon, elev" — and parse() under the same order reads it straight back. The round trip holds. The intermediate states are nonsense (after setEasting() alone the string is "0, <lon>, 0m") but only the final state is ever observed.

9. Commit sequence

Each commit is independently green. The order is chosen so the risky refactor lands alone, with the proto untouched, so a bisect can separate "the derivation is wrong" from "the migration is wrong".

#CommitContents

10. Test plan

The existing [FixStation] suite is the safety net for commit 1 — but not assertion-for-assertion. Roughly a dozen of its cases assert the invariant this change deletes ("writing a component drops the string", "changing the CS writes nothing", "the machine's own rendering is not a string worth keeping"), and those invert rather than survive. The suite is a safety net in the sense that everything around the coordinate — persistence, the exporters, the diagnostics, the line plot — must stay green untouched.

New coverage:

C++

  • test_cwFixStation.cpp — the derivation: a string in, the right numbers out, under both axis orders; setInputCS re-derives; the three states; component setters produce a string that re-reads to the numbers just written (a property test over adversarial doubles, not one example); project units flipped to Imperial does not move any number (§3's load-bearing claim).
  • test_cwFixStationModel.cpp — a fix with an unparseable string survives a save/load round trip byte-identical; a two-component coordinate reloads with hasElevation() == false.

11. Open decisions

Q1 (component normalization) and Q3 (deprecated vs reserved) are resolved 2026-07-27 and folded into §4.1 and §5 respectively. Q1 went the opposite way from my recommendation: rather than normalizing a two-component paste up to three, the elevation gets its own "not entered" state, so the string keeps meaning exactly what it says. That is the better answer — normalizing would have invented an elevation the user never typed, and this preserves the original intent (a map coordinate says nothing about elevation) without needing the numbers to remember anything the string doesn't. Q3 resolved to full removal plus an external one-shot script, which is what the "only one project uses fix stations" fact makes affordable — and which §5's tag audit has since verified rather than assumed: no released build contains fix-station code at all.

Q2 — What unit does the popup show for a machine-written string?

FixStationPage is unaffected: its cell renders from the numbers in project units and only the editor uses the string. The popup has no display half — one field is both — so it shows the stored string directly. After this change every fix has a string, and an imported fix's string is metric, so an imperial project's popup would read "…, 304m" where the page's cell reads "…, 997.4ft".

Recommendation: accept it for now and file it. The value is not wrong and the unit is spelled out, so nothing is ambiguous — it is an inconsistency, not a defect. Fixing it properly means the popup learning the same display/edit split the page has, which is A3's "the popup grew a third role" work and does not belong in this change.

Q4 — Should a missing elevation raise a warning?

§4.1 makes the state available without deciding whether the UI acts on it. A fix with no elevation still anchors the survey at elevation 0, which may be exactly what you want for a cave mapped on a local grid, or may be a half-finished entry. Recommendation: ship the state, look at your real project, then decide — this is a one-line follow-up either way and guessing now risks adding noise to a page whose whole purpose is to make real problems visible.

Q5 — Does the axis order follow inputCS() or effectiveCS(globalCS)?

raised by the commit 1 review, 2026-07-27 §6 documents the CS-first precondition but assumes the row has a CS. Commit 1 reads and writes the coordinate under axisOrderFor(inputCS()) — while cwFixStationDiagnostics::domainCheck and cwSurvexExporterUtils::writeFixStations both judge the same fix under effectiveCS(globalCS), which cwFixStation.h's own doc calls a rule every consumer has to answer the same way. A row that leaves its CS blank under a geographic project CS is therefore entered easting-first and exported latitude-first.

Confirmed, and wider than the blank-CS case. cwCoordinateTransform::isGeographic("LONG-LAT") is false — as is "UTM13N" — and cwSurvexImporter::parseCS stores survex's *cs spellings verbatim by design. So a *cs LONG-LAT / *fix import is spelled out easting-first, and the moment the user corrects the row to EPSG:4326 — which they must, since LONG-LAT is unusable downstream — the horizontals swap and the cave moves ~12,000 km. Before commit 1, setInputCS wrote nothing and the numbers survived.

Resolved: inputCS(). Commit 1 was right and the other two call sites are wrong. 2026-07-27 Both candidate answers on the table — cwFixStation takes the effective CS on write, or the derivation moves up to cwFixStationModel — existed only to serve an implicit fallback that should not exist. A blank inputCS is an error, not a request to use the project's CS. Without a coordinate system there is no axis order, so there is nothing the two numbers can be said to mean; the string is kept and the components are not derived. Once blank stops being a fallback, nothing consults globalCS on a fix station's behalf, and the fix is subtraction rather than plumbing:

  • cwFixStationDiagnostics::domainCheck — judge under inputCS().
  • cwSurvexExporterUtils::writeFixStations (cwSurvexExporterUtils.h:214, reached from cwSurvexExporterCaveTask; the cwSurvexExporterRule copy is a dead prototype) — emit *cs from inputCS(). No spelling change is needed: it already writes the row's CS verbatim, so a row holding EPSG:32613 emits *cs EPSG:32613.
  • cwFixStation::effectiveCS() — deleted, not reinterpreted. It had six callers, not none — this bullet originally said "it has no callers left", and that undercount is why §8's blast radius is short by fourteen files. The six: cwFixStationValidator (twice), cwFixStationDiagnostics, cwGridConvergence, cwTripCalibration, and cwSurvexExporterUtils. Removing it also deleted both globalCoordinateSystemChanged connections in cwCavingRegion, cwCave::refreshFixStationDomainErrors(), and cwFixStationDiagnosticsModel::fallbackCS().

The picker rework is what makes a blank unreachable — see §11.1. And the deadline lifted: Q5 no longer gates commit 2. The migration script converts each row under axisOrderFor(<that row's CS>), and the two readings can only differ on a row with no CS of its own — where today's axisOrderFor("") is EastingNorthing and axisOrderFor(globalCS) is also EastingNorthing, because the project's CS is constrained to projected (DataMainPage.qml:199 sets allowGeographic: false — survex's cavern only emits projected output). They agree on every row the UI can produce, so the script writes the same bytes either way. Caveat: that constraint is enforced in the picker only — cwGeoReference::setGlobalCoordinateSystem does not check it — so a hand-edited geographic globalCS would break the equivalence.

11.1 — The coordinate-system picker: remove Local, add Project

decided 2026-07-27 Issues #625 (remove the local option) and #618 (make it easy to match the project's CS) are the same change, and it is what retires the blank inputCS.

Today Local literally commits the empty string (CSPicker.qml:56), and effectiveCS() then falls back to globalCS. So blank means two contradictory things at once — "this row has no coordinate system" and "this row follows the project's" — which is the whole of Q5. Splitting them apart:

ModeCommits
Lat/Long default EPSG:4326. New rows start here, so a blank is never created.
UTMEPSG:326NN/327NN from the zone and hemisphere controls, unchanged.
Project new The project's global CS, copied into the row.
CustomArbitrary EPSG via CSCustomDialog, unchanged — it is the only route to British National Grid, state plane, and the rest.
Project copies, it does not link. Once a coordinate has been entered under a system, that row stays on that system — changing the project's projection afterward must not move a fix station that was entered in UTM. So Project is an action, not a stored mode: it stamps the project's CS into inputCS and the row holds it from then on. This is also why there is no resolvedCS member and no globalCS-changed re-derivation path — inputCS is always already resolved.

Displaying it needs no stored state either. The picker shows Project whenever the row's value equals the project's global CS, and the action stamps that value in. Change the project's projection and the row no longer matches, so it displays as UTM — or Custom, if the project moved to something the picker has no mode for. "It basically becomes Custom" falls out of a display rule rather than a migration.
Local stays for the project, goes for fix stations. decided 2026-07-27 CSPicker is shared: DataMainPage drives the project's global CS with it, CSComboBox drives fix-station rows. #625 is scoped to fixed stations, and a project that isn't georeferenced — the normal state for most caves — needs Local to say so. Project is the mirror image: meaningless on the project's own picker. So the mode list becomes per-host, exactly as allowGeographic already is:
HostModes
DataMainPage (project globalCS) Local · UTM · Custom  unchanged
CSComboBox (fix-station row) Lat/Long default · UTM · Project · Custom
Two more booleans beside allowGeographic (allowLocal, allowProject) is the consistent move, but three flags means eight combinations and CSPicker.qml:89-100 currently hardcodes two array literals for modes/model in parallel. Build both by filtering one ordered (mode, label) list instead, so a future flag needs no new literal — the same spirit as oneLineWidth, which already sums the Flow's children generically rather than naming them.
Implementation notes — gathered 2026-07-27, before any code was written
  • The C++ enum only grows. Mode { Local, LatLon, UTM, Custom } → append Project, keeping existing values stable. Local is not removed — the project picker still needs it, and parseCS (anonymous namespace, cwCoordinateTransform.cpp:449) defaults mode = Local for an empty string, which modeFor() returns verbatim. Removing it would have needed a new answer there.
  • modeFor() can never return Project — it doesn't know the project's CS. Worth a doc line on the enum, since it breaks the round-trip property the other three modes have. The display rule lives in CSPicker.currentMode instead: value !== "" && value === projectCS ? Project : modeFor(value). The value !== "" guard keeps an unset row out of Project when the project has no CS either.
  • CSPicker has no access to the project's CS today — it needs a new projectCS property, passed by the three fix-station hosts (FixStationPage.qml:173 and :454, FixStationPopup.qml:237 — the same three that set allowGeographic: true). Where they read it from is not a walk up the object tree: RootData.region.geoReference.globalCoordinateSystem is a singleton path reachable from any QML file, and FixStationPage.qml:234 already writes through it. Passed as a property rather than read inside the picker, so a picker stays testable without a region behind it.
  • Local is referenced in exactly three places, all in CSPicker.qml (lines 56, 90, 93). The blast radius really is that small.
  • Don't disturb the lazy CSCustomDialog loader (CSPicker.qml:164). Every fix-station row instantiates a picker, and the dialog's CRSSearchModel loads ~7000 EPSG rows from proj.db on first use.
What the implementation found — 2026-07-27, both suites green
effectiveCS() had six callers, not two. The plan said "cwFixStationDiagnostics and cwSurvexExporterUtils::writeFixStations" and undercounted by four: makeDeclinationContext (cwSurvexExporterUtils.h:45), cwTripCalibration::resolveAuto, cwFixStationValidator.cpp:238 and cwGridConvergence::update. Each took a globalCS/fallbackCS parameter that existed only to feed effectiveCS(), so deleting it deleted the parameter too — and with it cwFixStationDiagnosticsModel::fallbackCS(), refreshDomainErrors(), cwCave::refreshFixStationDomainErrors() and the two globalCoordinateSystemChanged connections in cwCavingRegion::insertCaves. Nothing in a cave follows the region's CS any more, which is the design stated as a property of the signal graph rather than of a function.
The component setters don't compose on a row with no CS — three callers hit it, one of them the ordinary local-grid survey. setEasting/setNorthing/setElevation each write the coordinate out and read it straight back, so once refresh() returns early for a blank CS the first write comes back as nothing and the next two spell that nothing out: 610016.792, 5615117.075, 304m becomes 0, 0, 304m. Three callers do exactly this — fromProtoFixStation, cwSurvexImporter::parseFix (a *fix with no *cs before it is a local grid, which is the common case), and test_cwCavingRegion_worldOrigin's makeFix. The last one is how it was caught: the fix silently placed the whole survey's world origin at 0.

Fixed at the class rather than at each call site — cwFixStation::setCoordinate(double, double, double), one write for a caller that holds all three numbers. The one-at-a-time setters keep their existing contract and their existing documented caveat. The numbers then survive as text on a row that says it has no system, which is what §4 asks for: naming the system the row was always in brings all three back, and there is a test for exactly that on each of the two production paths.

This is a data-loss trap, not a cosmetic one. It is the same shape the header already documented for Unreadable, but reachable from ordinary files rather than only from a hand edit — which is why the fix is an API and not a comment.

Defaulting new rows to WGS84 flips the axis order under every test that assumed a blank CS. A blank CS reads easting-first (axisOrderFor("") == EastingNorthing), so a row created by addFixStation() and then handed 46.12113, -115.59902 used to land easting-first and now lands latitude-first. Seven QML cases and four C++ ones asserted the old reading; each now names a projected CS explicitly. Two of them — the diagnostics fallback tests — were testing the deleted rule and were rewritten rather than repaired.
Two more consumers resolved the CS themselves and had to change with the rest. cwCavingRegion::recomputeWorldOrigin reaches the fixes through cwFixStationValidator::candidates(), so it inherited the fallback without naming it — a fix with no CS used to place the whole survey's world origin under the region's projection, and now is skipped. cwCave::recomputeGridConvergence is the other. Both had tests asserting the fallback; both were rewritten, and each now asserts the positive half too so it can't pass by always deferring.
Defaulting a new row to WGS84 broke the survex export in two ways, and only the full suite caught them. Both are real bugs the old blank CS was hiding, not test churn:
  • makeDeclinationContext read the first fix whether or not it had a coordinate. "Mark Station as Fixed" makes a row before the user types anything, and that row now carries a CS from birth — so the export emitted *declination auto 0 0 0 under *cs EPSG:4326: the Gulf of Guinea, not the cave (cavern duly reported grid convergence: inf°). Worse, that *cs lands after the fallback *fix, which cavern rejects outright — "Station … fixed before CS command first used". Now it skips to the first fix that has both a CS and a readable coordinate.
  • resolveOutputCS fell back to a geographic fix CS. Cavern refuses one: "Coordinate system unsuitable for output", the ok_for_output == NO branch at survex/src/commands.c:2672. So *cs out EPSG:4326 fails the whole solve, and the fallback now skips geographic and emits nothing — cwFixStationValidator::needsOutputCS already exists to ask the user for a projected one.

Verify this against cavern's source, not by inspection. A grep for proj_angular_output finds nothing and reads as "survex accepts geographic output"; the check is there under another name, and the error only appears once you read a real cavern log. Both bugs were found from the log, not from the diff.

A consequence the user will see: an ungeoreferenced project plus one named fix station no longer solves. The row is on WGS84, cavern can't output geographic, and there is no project CS to fall back to — so the line plot fails until the output CS is picked. That is what needsOutputCS and OutputCSPrompt are for, and the prompt now fires as soon as a fix row exists rather than once it has a coordinate. Defaulting a new row to the project's CS when it has one would avoid the prompt in the common case, but cwFixStationModel has no route to the region, so it is a separate change.
A mode this host doesn't offer shows an empty combo, not the first entry. indexForMode returned 0 for an unknown mode, which after this change would have labelled a blank fix-station row "Lat/Lon" — naming a system the row is not on. It now returns -1, so the combo shows nothing. The same applies to the project picker if a globalCS is hand-edited to a geographic CRS.

Out of scope decided 2026-07-27: the survex importer. It stores *cs spellings verbatim (cwSurvexImporter.cpp:1069), so LONG-LAT — whose datum is anyone's guess — and UTM13N both arrive as strings isGeographic() reads as projected. Mapping them onto real EPSG codes on import is the right fix and is not part of this work. Nor is migrating existing Local rows: no such files exist.

12. Risks & rejected alternatives

RiskAssessment
A parse regression takes fixes out of the solve Not data loss — the string is on disk, on screen, and flagged. The numbers are recomputable from it the moment the parser is right again. This was raised as the strongest objection to the design and does not survive the fact that setCoordinateText refuses to store anything parse() rejected, and that both format() and parse() are C-locale — so there is no write/read asymmetry to regress on.
An unmigrated project is opened by a new build The single largest risk in this plan, and the only one that destroys data. ignore_unknown_fields = true turns "old schema" into "no coordinates" with no error, and the next save persists it. The load-time version gate (§5) is what mitigates it — and that gate is deferred to the pre-release save/load audit (§5.3, decided 2026-07-28), so as of commit 2 this risk is unmitigated in code. What stands between it and the project is procedure: run the script before opening. Migrating a copy first, and keeping the original untouched until the migrated copy opens correctly, costs nothing and is now the difference between a recovery and a loss.
Derived state goes stale Real, and the reason refresh() has exactly two callers and the fields are private with no setter. Worth a test that calls every mutator and asserts the numbers agree with the string.
Component-setter ordering Materialized — this row said "the risk is a future one" and it was already present. Not a call-site ordering risk at all: on a CS-less fix the setters don't compose, so three writes keep one number. It cost silent data loss on three real callers and needed a new API (setCoordinate(double, double, double)), not a test. See §6.

Rejected: keep the numbers as a cache

Serialize both, treat the string as authoritative, and use the numbers only to detect a parse regression. Rejected on the grounds that it keeps every guard in §2 alive to maintain agreement between two stored fields — the exact cost this change exists to remove — in exchange for a failure mode that §12 shows is already benign.

Rejected: parse lazily on read

easting() parses on demand instead of caching. Rejected: easting() is called per-station in the solve and per-frame in the plot, and a regex parse behind a const getter is a performance trap disguised as simplicity. Deriving on write is one parse per edit.

F22 — naming a geographic CS on a NoSystem row transposes it done in commit 4

The NoSystem doc claimed the numbers are kept as text either way, "so naming the system reads all three straight back." That holds only for a projected system. A CS-less row has no axis order and nothing records the one its text was written in — cwSurvexImporter::parseFix stores a *fix with no preceding *cs easting-first — so choosing a geographic CS afterward reads it latitude-first and the first two components swap. The doc is corrected; the behavior is not.

Corrected 2026-07-28. This entry first said the fix belongs in commit 2, "which already adds coordinateTextAxisOrder to the proto for exactly this class of problem". That is backwards: §5.1 shows commit 2 reserving field 10 and deleting the enum end to end. After commit 2 there is no stored axis order at all, by design — the order is derived from inputCS, and a NoSystem row has no inputCS to derive it from. Persisting one would re-add the field commit 2 exists to remove.

So this is not a storage problem and it has no schema fix. It is commit 4's work, and it is a UI affordance: commit 4 is what brings NoSystem to the page and the popup, and the moment it offers a geographic CS on such a row it has to say how the existing text will be read — show the reading it is about to commit to, and let the user swap the first two components if that isn't what they meant. Nothing else can recover the information, because the information was never written down.

Shipped as CoordinateOrderAskBox.qml. 2026-07-28 Both readings are shown as the user's own text — as written, and with its first two numbers exchanged — rather than as re-rendered numbers, which is what cwCoordinateText::swapHorizontal() is for: a textual swap keeps the elevation, its unit, the separators, and the fact that a two-component coordinate has no elevation at all, none of which survive a round trip through format(). Applying it twice returns the original string, so taking the offer and changing your mind costs nothing.

Three things this design turns on, each of which was a live bug in an earlier draft:
  • CoordinateOrderUnknownRole must be read before the CS is committed. The write is what gives the row an axis order, so a handler that reads it afterwards never asks anything — and the tests pass either way unless one of them pins the ordering.
  • The predicate lives in askAbout(), not at the call sites: was the order unknown, is the new system geographic, and does the text swap at all. The page's two coordinate-system cells funnel through one commitCS(), so there are two callers, not three — but a rule left to each host is how the two entry surfaces diverged inside one commit before (P1).
  • swapHorizontal() asks whether the text parses, not whether it holds two numbers. "N 46 07 16 W 115 35 56" holds six and is not a coordinate; a count-based version offers to rewrite it.
  • Every reason not to ask must be settled before the dialog's row/coordinate/CS are written. An earlier draft set them and then bailed on "nothing to swap", which repoints a question already on screen at a row it declined to ask about. Only modality keeps that unreachable today.
The dialog is hosted at page level, not in the row delegate — a table delegate is destroyed as its row scrolls out of view, which would take the open question down with it.
Two things the shipped design does not own, both found by commit 4's review.
  • The read-before-write ordering is still per-host, and cannot move into askAbout() — by construction it receives values already snapshotted. The two hosts implement it differently: FixStationPage.qml relies on JS argument evaluation at the commitCS(...) call, FixStationPopup.qml snapshots into two local consts, and they read the coordinate by different routes (a bound delegate role vs a fresh model.data() through storedCoordinate()). A third host gets it wrong for free. Closed by R3, or structurally by A2 below.
  • The page-level hosting note doesn't cover the popup's instance. FixStationPopup.qml nests its own CoordinateOrderAskBox inside a QC.Popup the user can close — the same lifetime class the note warns about. Mitigated for now by having swapRequested carry the row and write to that row, but hoisting the dialog once is the real answer (R3).
Committing the swap uses stored units, not the project's. The result goes back through setCoordinateText(), which reads a bare elevation in whatever unit system it is handed, while cwFixStation reads the stored string under kStoredUnits = Metric. Only the load path can produce a bare elevation (setCoordinateText() spells the unit out before storing), so this is exactly the hand-edit population §4 exists for — and in an imperial project the swap would have re-read "…, 304" as feet and dropped the fix 211 m, for a gesture that offered only to exchange two horizontal numbers. Both hosts therefore commit through Units.Metric.

R3 — a named FixStationCSPicker

CSComboBox claims the host policy is "fixed by this shell rather than left to each host", but FixStationPopup.qml:238 repeats allowLocal: false / allowProject: true by hand, and projectCS: RootData.region.geoReference.globalCoordinateSystem is now written at three sites (FixStationPage.qml:174, :456, FixStationPopup.qml:240). Four host-policy flags is where "one component, N booleans" stops paying. One new QML file plus three host edits — and commit 4 touches the same three hosts, so do it once, after.

Commit 4 made this materially bigger, and it is now "after". 2026-07-28 Every host must additionally perform a commit-then-ask sequence carrying a load-bearing ordering rule, and the two implementations already differ: FixStationPage.qml factors it into commitCS() and snapshots by argument evaluation; FixStationPopup.qml open-codes it into two local consts and reads the coordinate by a different route (storedCoordinate()'s fresh model.data() vs a bound delegate role). Each host also instantiates its own CoordinateOrderAskBox with its own post-swap follow-up. That is two routes to the same two values and two hand-written orderings of the same trap — see F22's second callout, and A4 for the structural alternative.

Also unblocked by this: the narrow layout's delegate is a third code path that had zero test coverage before commit 4's review added one — no test in tst_FixStationPage.qml had ever manipulated the window width.

A1 — a cwCoordinateSystem value type

A coordinate system is a bare QString with no normalization owner, and commit 3 made string identity load-bearing: CSPicker.qml:44 decides the Project display with value === projectCS (exact, case-sensitive, untrimmed) while cwFixStationValidator asks whether the same two strings are the same system with compare(..., Qt::CaseInsensitive). Add seven fresh .trimmed().isEmpty() sites and an isGeographic() that answers false for anything PROJ can't parse — that last one has already cost a workaround: cwSurvexExporterUtils::isUnusableAsSurvexOutputCS is a hand-kept list of survex's own CS keywords, living in the exporter because there is no type to hang it on. A value type owning trim, case and spelling collapses all of it. Blast radius: large — cwFixStation, the transform, the validator, both exporters, the picker, ~40 tests.

A2 — enforce "the project's CS is projected"

DataMainPage.qml sets allowGeographic: false; cwGeoReference::setGlobalCoordinateSystem does not check. Commit 3 raised the stakes twice: Project copies globalCS verbatim into a fix row, and resolveOutputCS now silently emits nothing when the only candidate is geographic. So a hand-edited or imported geographic globalCS propagates into fix rows and then vanishes from *cs out with no diagnostic. Blast radius: small — a validity check plus an error surface — but it needs a decision about existing files that already carry one.

A3 — give the row's state a role, so QML stops branching on a sentence

from commit 4's review cwFixStationModel::Roles has no state role and cwFixStation::CoordinateState is not Q_ENUM'd, so the only way QML can ask "does this row have numbers?" is coordinateError !== "" — testing a tr() string for emptiness. That one expression decides what the cell renders (text vs formatted numbers), whether it is tinted, and which warning speaks, at 8 sites. A message that came back empty would silently restore the "renders as 0, 0, 0 with no complaint" behavior commit 4 exists to remove.

CoordinateOrderUnknownRole is the tell: it is one state bit projected into a bool because the state itself isn't reachable. A CoordinateStateRole generalizes it, returns the message to being purely presentational, and lets "these two can't both speak" be a state test rather than a comment plus two string tests. Blast radius: small-medium — Q_ENUM registration, one role, ~8 QML expressions, no C++ consumer changes. Latent today only because CaveWhere ships no translation infrastructure.

A4 — make the model report the pre-write state, instead of requiring a pre-read

from commit 4's review CoordinateOrderUnknownRole is a fact that the very write consuming it destroys, and the rule "read it first" is documented in prose and held up by argument-evaluation order in one host and two local consts in another (see F22's second callout). Reading it afterwards was a live bug whose tests pass either way.

The structural fix: have the model report the consequence of the write rather than requiring a pre-read — a Q_INVOKABLE on cwFixStationModel that commits the CS and returns what the row was (order unknown, and the text as stored). Then no host can sequence it wrongly and askAbout() genuinely owns the whole rule. Blast radius: small — one model method plus the hosts (or one host, after R3).

R6 — cwFixStation should carry its own parse reason

from commit 4's review cwFixStationDiagnosticsModel.cpp:48 re-runs cwCoordinateText::parse(fix.coordinate(), Metric, axisOrderFor(fix.inputCS())) purely to recover the message, and its comment has to explain that Metric is chosen "exactly as cwFixStation does" — i.e. the model reproduces refresh()'s argument list by hand, from a different translation unit. refresh() already holds that exact Result and discards the error before storing State = Unreadable. The duplicated argument list is the one thing that can silently drift and make the message disagree with the verdict.

Keeping the reason on the fix (an errorMessage() beside state()) removes the drift risk and a regex re-parse from a data() path. Out of scope for commit 4 because it changes cwFixStation's public surface and refresh()'s stored data, which commit 1 deliberately isolated.

R7 — a second origin guard survived commit 1's sweep

from commit 4's review §4 states the principle: a guard "must stop inferring intent from a value and ask state() == Empty instead… it also stops treating a legitimately entered 0, 0, 0 as unentered, which is a real (if rare) coordinate in some local grids." Commit 1 moved the cwFixStationDiagnostics guard, but cwFixStationValidator::updateOutputCSPrompt() still carries if (p.x == 0.0 && p.y == 0.0) { continue; } // coordinate not entered yet at cwFixStationValidator.cpp:491 — three lines after a state() != Valid check at :485 that already excludes Empty.

Consequence: a fix genuinely entered at 0, 0, 0 in a local grid contributes no output-CS suggestion. Small and self-contained, but not a mechanical deletion — the check was also guarding against a freshly-picked CS reading as an invalid coordinate, so it needs a replacement decision.

R8 — the raw-text cell clips instead of eliding

from commit 4's review CoreClickTextInput only propagates the field width to its label when autoResize is true, and FixField never sets it, so textAreaId.width == implicitWidth and its elide: ElideRight can never fire. Overflow is cut by WideCell.clip at the 300 px coordinate column. Before commit 4 the cell only ever held format() output, sized for a UTM triple; now it can hold any stored string, so a long NoSystem coordinate truncates mid-glyph with no ellipsis and no hint that more text exists. The fix belongs in CoreClickTextInput's width propagation, which is shared across the app — hence its own commit.

Accepted, not defects

ItemDecision
New rows default to WGS84, not to the project's CS kept Most people take points off WGS84, so it is the right default. The consequence is real and accepted: an ungeoreferenced project with a filled-in geographic fix emits *cs with no *cs out, cavern refuses the solve, and the plot stays blank until an output CS is picked — which is what needsOutputCS prompts for. An empty scaffold row no longer triggers it, since such a row is now dropped from the export. Superseded in future by automatic project-level CS selection, which may need a custom local CS with no EPSG code rather than anything in the registry.
Mode mixes "what this CS is" with "how it was chosen" kept Project is the one value modeFor() can never return. Asymmetric but correct, and the enum is Q_ENUM'd across C++ and QML.
